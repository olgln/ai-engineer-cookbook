# 11.1 · Docker: упаковать проект  (AIL-66)

> **Неделя 11** · Продакшен · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Ревьюер твоего портфолио не будет ставить нужную версию Python, uv, Langfuse и векторную БД по README из пятнадцати шагов. Он скопирует `git clone && docker compose up` — и либо увидит работающий ассистент, либо закроет вкладку. На собеседованиях вопрос «как ты это деплоишь?» звучит почти всегда, и ответ «Dockerfile + compose, секреты через окружение, образ без ключей внутри» — минимальный ожидаемый уровень.

## Теория

### Что такое контейнер, в терминах, которые ты уже знаешь

Твоё арбитражное приложение запускается через `node server.ts` на Маке, и работает оно потому, что на Маке стоит Node 26, лежит `node_modules`, рядом лежит `.env` и файл базы уровнем выше. Перенеси папку на другую машину — и половины этого не будет.

Контейнер — это процесс, которому ядро ОС показывает **собственную файловую систему** (с нужным Python, библиотеками и твоим кодом), собственную сеть и собственное дерево процессов. Это не виртуальная машина: ядро общее, поэтому контейнер стартует за доли секунды.

| Понятие | Аналогия из Node | Что это |
|---|---|---|
| **Image** (образ) | собранный `.next` + `node_modules` + сам Node, упакованные в архив | неизменяемый «снимок» файловой системы + команда запуска |
| **Container** | запущенный `node server.ts` | процесс, запущенный из образа; его изменения файлов пропадают при удалении |
| **Dockerfile** | `package.json` scripts + инструкция «как поставить» | рецепт сборки образа, по шагам |
| **Layer** (слой) | кэш `npm ci` | каждый шаг Dockerfile — слой; неизменившиеся слои берутся из кэша |
| **Volume** | папка уровнем выше с `arbitrage.db` | хранилище, которое живёт дольше контейнера |
| **docker compose** | твой `server.ts`, который поднимает Next + socket.io + cron | файл, описывающий несколько сервисов, их сеть, переменные и тома |

На Маке контейнеры Linux работают внутри лёгкой виртуальной машины. Её даёт Docker Desktop (бесплатен для личного использования и небольших компаний — проверь условия лицензии) или альтернативы вроде OrbStack и colima. Это программа с правами в системе, поэтому до первого запуска — та же проверка, что для любого приложения: скачивать с официального сайта, `codesign -dv` и `spctl -a -vv` на `.app`.

### Слои и кэш: почему порядок строк в Dockerfile важен

Docker выполняет Dockerfile сверху вниз и кэширует результат каждой инструкции. Если входы шага (файлы, которые он копирует, сама команда) не изменились — шаг берётся из кэша. Как только один шаг изменился, **все следующие** пересобираются.

Отсюда главный приём: сначала копируешь только файлы зависимостей (`pyproject.toml`, `uv.lock`) и ставишь зависимости, потом копируешь код. Правишь код — переустановки 300 МБ зависимостей не происходит.

```
плохо                          хорошо
-----                          ------
COPY . /app          ← код     COPY pyproject.toml uv.lock  ← редко меняется
RUN uv sync          ← каждый  RUN uv sync --no-install-project
                       раз     COPY . /app                  ← часто меняется
                       заново  RUN uv sync                  ← быстро: только сам проект
```

### Dockerfile для Python-проекта с uv

В главе AIL-2 ты собрал проект на uv. У uv есть официальный гайд по Docker, и его паттерн выглядит так (версию uv закрепи ту, что актуальна в гайде на момент работы):

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim

# Copy the uv binary from the official image; pin the version (or a digest)
COPY --from=ghcr.io/astral-sh/uv:<VERSION> /uv /uvx /bin/

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_NO_DEV=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# 1) Dependencies only: cached until uv.lock / pyproject.toml change
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project

# 2) The project itself
COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked

# Run as an unprivileged user, not root
RUN useradd --create-home app && chown -R app /app
USER app

ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8501
CMD ["streamlit", "run", "app/ui.py", "--server.address=0.0.0.0", "--server.port=8501"]
```

Что здесь важно:

- `--locked` — сборка падает, если `uv.lock` не соответствует `pyproject.toml`. Это аналог `npm ci`: в образ попадают ровно те версии, что ты проверял.
- `--mount=type=cache` — кэш uv живёт между сборками, но не попадает в образ.
- `UV_NO_DEV=1` — pytest, ruff и прочие dev-зависимости в образ не идут.
- `PYTHONUNBUFFERED=1` — иначе `print` и логи буферизуются и в `docker compose logs` появляются с задержкой или не появляются вовсе.
- `--server.address=0.0.0.0` — внутри контейнера приложение **должно** слушать все интерфейсы контейнера, иначе проброс порта не достучится. Это не то же самое, что выставить сервис в интернет: наружу его выставляет `ports:` в compose, и там ты указываешь `127.0.0.1`.
- `CMD` в exec-форме (JSON-массив) — тогда твой процесс получает SIGTERM при `docker compose down` и может корректно завершиться.

### .dockerignore — обязательный файл

`COPY . /app` копирует всё из контекста сборки. Без `.dockerignore` в образ уедут `.env` с ключами, `.venv` с Мака (бинарники не под Linux), `.git`, копия базы и ноутбуки с выводом. Образ потом публикуется или передаётся — и ключ утёк.

```
.env
.env.*
.venv/
.git/
__pycache__/
*.db
*.db-wal
*.db-shm
data/private/
notebooks/.ipynb_checkpoints/
```

### Секреты: правило одно

**Ключи никогда не попадают в образ.** Ни через `COPY`, ни через `ENV ANTHROPIC_API_KEY=...`, ни через `ARG` (значения `ARG` видны в истории образа: `docker history`). Ключи передаются в момент **запуска** контейнера:

- `env_file: .env` в compose (а `.env` в `.gitignore` и `.dockerignore`);
- или `environment:` с подстановкой `${ANTHROPIC_API_KEY}` из окружения shell;
- для настоящего продакшена — секреты оркестратора (Docker secrets, Kubernetes Secrets, менеджер секретов облака).

Если секрет нужен на этапе **сборки** (например, приватный пакет), используется `RUN --mount=type=secret,...` — он доступен только этому шагу и в слой не записывается. В твоих учебных проектах такой нужды быть не должно.

В репозиторий кладёшь `.env.example` — список переменных без значений. Это и документация, и проверка: человек со стороны видит, какие ключи ему понадобятся.

### docker compose: несколько сервисов одной командой

`compose.yaml` описывает сервисы, и compose сам создаёт для них общую сеть, где **сервисы видят друг друга по имени**. Это главное отличие от локального запуска: внутри контейнера `localhost` — это сам контейнер, а не твой Мак и не соседний сервис.

```
             твой Мак (host)
  ┌──────────────────────────────────────────────┐
  │  127.0.0.1:8501 ──► rag-app:8501             │
  │  127.0.0.1:3001 ──► langfuse-web:3000        │
  │                                              │
  │   сеть compose:                              │
  │   rag-app ──http://langfuse-web:3000──► langfuse-web
  │   rag-app ──http://qdrant:6333────────► qdrant (если есть)
  │   rag-app ──http://host.docker.internal:11434──► Ollama на Маке (AIL-47)
  └──────────────────────────────────────────────┘
```

Каркас для RAG-ассистента:

```yaml
services:
  rag-app:
    build: .
    env_file: .env
    environment:
      LANGFUSE_BASE_URL: http://langfuse-web:3000   # service name, not localhost
    ports:
      - "127.0.0.1:8501:8501"                       # only reachable from this machine
    volumes:
      - ./data/index:/app/data/index                # vector index survives restarts
    depends_on:
      langfuse-web:
        condition: service_started
    restart: unless-stopped
```

Пара деталей:

- `ports: "127.0.0.1:8501:8501"` — без `127.0.0.1` Docker публикует порт на всех интерфейсах, и на сервере это означает «в интернет». Это та же логика, по которой твоё арбитражное приложение никогда не слушает `0.0.0.0`.
- `depends_on` управляет **порядком запуска**, а не готовностью. Чтобы ждать готовности, у зависимого сервиса нужен `healthcheck`, а в `depends_on` — `condition: service_healthy`. Но надёжнее, если приложение само переживает недоступность Langfuse: трейсинг не должен ронять ответ пользователю (подробно — в AIL-46).
- `volumes` — индекс эмбеддингов и прочие данные, которые нельзя терять при `docker compose down`. Команда `docker compose down -v` удаляет именованные тома — с Langfuse это значит «все трейсы пропали».

### Langfuse рядом с приложением

Langfuse (ты подключал его в AIL-30) можно запускать self-hosted. Официальный способ — их `docker-compose.yml` из репозитория `langfuse/langfuse`: там веб-сервис, воркер и хранилища (базы данных, MinIO для объектов). Все чувствительные строки в нём помечены `# CHANGEME` — пароли и секреты надо заменить на длинные случайные (`openssl rand -hex 32`) и вынести в `.env`.

Два способа объединить его со своим приложением:

1. **`include`** в своём `compose.yaml` (поддерживается в современных версиях Compose):
   ```yaml
   include:
     - langfuse/docker-compose.yml
   services:
     rag-app: ...
   ```
2. Два файла и флаг: `docker compose -f compose.yaml -f langfuse/docker-compose.yml up`.

Первый вариант лучше для README: остаётся «одна команда».

Конфликт, который ты встретишь сразу: веб-интерфейс Langfuse по умолчанию на порту **3000** — том же, что твоё арбитражное приложение. Если оно запущено, compose упадёт с `port is already allocated`. Перемапь хостовый порт (`127.0.0.1:3001:3000`) и не забудь обновить `NEXTAUTH_URL` (или аналогичную переменную адреса в их файле) на новый адрес.

Альтернатива для демо-версии в портфолио — Langfuse Cloud (бесплатный тариф): тогда в compose остаётся только твоё приложение, а ключи Langfuse в `.env`. Выбери одно и напиши в README, что именно.

### Чистая машина: как проверить «поднимается одной командой»

«Работает у меня» не считается. Типичные причины, почему на чужой машине не стартует:

- в образ не попал файл, потому что он в `.dockerignore` или `.gitignore` (например, индекс или датасет);
- приложение ждёт файл, который у тебя лежит, а в репозитории его нет (копия реальной базы — и правильно, что нет);
- архитектура: на Mac M-серии образ собран под `arm64`; Linux-сервер с `amd64` его не запустит, если ты публикуешь готовый образ (сборка из исходников через `build: .` этой проблемы не имеет; иначе `docker buildx build --platform linux/amd64,linux/arm64`);
- переменная окружения не описана в `.env.example`.

Проверка: свежий `git clone` в другую папку → `cp .env.example .env` → вписать ключи → `docker compose up --build`. Ещё строже — `docker builder prune` перед этим, чтобы не помог кэш.

## DeepSeek и Ollama: как это сделать у нас

Для Docker провайдер почти не важен — меняются переменные окружения и появляется вопрос «где живёт Ollama». Факты про Ollama в Docker проверены по [docs.ollama.com/docker](https://docs.ollama.com/docker) и [FAQ](https://docs.ollama.com/faq) в ноябре 2026.

**Переменные.** Провайдер выбирается окружением, а не кодом — тогда один образ работает с любым из них:

```
# .env.example - names only, no values
LLM_PROVIDER=            # deepseek | ollama
DEEPSEEK_API_KEY=
DEEPSEEK_MODEL=          # e.g. deepseek-flash, check the pricing page for current names
OLLAMA_BASE_URL=         # http://host.docker.internal:11434/v1 on a Mac
OLLAMA_MODEL=            # a tag from `ollama list`
ANTHROPIC_API_KEY=       # optional, for the comparison runs only
```

**Ollama на Маке — нативно, а не в контейнере.** В Docker Desktop на macOS GPU недоступен (нет проброса GPU), поэтому контейнер `ollama/ollama` на Маке работает только на CPU — в разы медленнее нативного приложения, которое использует Metal. Схема для твоего Мака: Ollama установлена как обычное приложение и слушает `127.0.0.1:11434`, контейнер ассистента ходит к ней по `http://host.docker.internal:11434` (как на схеме выше). Менять `OLLAMA_HOST` на `0.0.0.0` ради этого не нужно и нельзя (глава 11.4). Если у тебя colima или OrbStack и соединение не проходит, сначала прочитай их документацию про доступ к хосту, а не открывай Ollama в сеть.

**Ollama в контейнере — для ревьюера и Linux-сервера.** Чтобы человек без Ollama мог поднять проект одной командой, добавь сервис под профилем — он стартует только по запросу:

```yaml
services:
  ollama:
    image: ollama/ollama:<pinned-version>     # official image; pin the tag, never latest
    profiles: ["local-llm"]                   # started only with --profile local-llm
    volumes:
      - ollama:/root/.ollama                  # models survive `down` (not `down -v`)
    # no `ports:` - only rag-app needs it, via the compose network at http://ollama:11434
volumes:
  ollama:
```

`docker compose --profile local-llm up -d`, затем один раз скачать модель: `docker compose exec ollama ollama pull <model:tag>`. Приложение в этом режиме получает `OLLAMA_BASE_URL=http://ollama:11434/v1`. Порт наружу не публикуется: если всё-таки нужен с хоста — только `127.0.0.1:11435:11434` (11434 на Маке уже занят нативной Ollama). Для GPU NVIDIA на Linux в документации — `--gpus=all` и NVIDIA Container Toolkit.

**DeepSeek в контейнере** — обычный исходящий HTTPS, ничего особенного. Помни про данные: контейнер с доступом к копии базы сделок (Проекты 1 и 4) не получает `DEEPSEEK_API_KEY` вообще — тогда уйти в облако ему физически нечем.

| Что для этой главы | Claude / OpenAI | DeepSeek | Ollama |
|---|---|---|---|
| Что положить в `.env` | ключ | ключ | ничего секретного, только `OLLAMA_BASE_URL` и модель |
| Где работает на Маке | облако | облако | нативно (GPU через Metal); в Docker на Маке — только CPU |
| Адрес из контейнера | публичный API | `https://api.deepseek.com` | `host.docker.internal:11434` (нативная) или `ollama:11434` (сервис compose) |
| Что хранить в томе | — | — | модели (`/root/.ollama`), гигабайты |

## Маршрут изучения

1. Открой [Docker: Get started](https://docs.docker.com/get-started/) → пройди разделы про концепции (что такое контейнер, образ, registry, compose) и workshop до шагов про multi-container apps и volumes (≈60 мин). Обрати внимание на разницу между bind mount и named volume — она понадобится для индекса и данных Langfuse.
2. Открой [Using uv in Docker](https://docs.astral.sh/uv/guides/integration/docker/) → прочитай разделы про установку uv в образ, кэширование и intermediate layers, `.dockerignore`, `UV_COMPILE_BYTECODE` (≈25 мин). Возьми оттуда актуальную версию uv для `COPY --from`.
3. Открой [Docker Compose docs](https://docs.docker.com/compose/) → разделы про `services`, `ports`, `env_file`/`environment`, `depends_on`, `include`, и страницу про переменные окружения в Compose (≈30 мин). Запомни приоритет: что перекрывает что, если переменная задана в нескольких местах.
4. Открой [Langfuse self-hosting: Docker Compose](https://langfuse.com/self-hosting/deployment/docker-compose) → прочитай, какие сервисы поднимаются, какие порты, где строки `# CHANGEME` (≈20 мин). Отметь, какой порт конфликтует с твоим приложением.
5. Открой [Ollama: Docker](https://docs.ollama.com/docker) → команды запуска, том для моделей, вариант для GPU (≈10 мин), и в [Ollama FAQ](https://docs.ollama.com/faq) — абзац про GPU в Docker Desktop на macOS и про `OLLAMA_HOST` (≈10 мин).
6. В тех же docs Docker найди раздел про build secrets (`--mount=type=secret`) — только прочитать, чтобы понимать разницу между секретом сборки и секретом запуска (≈10 мин).

## На что обратить внимание

- **`.env` в образе.** Самая частая и самая дорогая ошибка. После сборки проверь: `docker run --rm <image> ls -la /app` — `.env` там быть не должно.
- **`localhost` внутри контейнера** — это контейнер. К соседнему сервису — по имени сервиса, к Ollama на Маке — `host.docker.internal`.
- **`0.0.0.0` внутри, `127.0.0.1` в `ports`.** Внутри контейнера слушать все интерфейсы; на хосте публиковать только на loopback, пока нет причины иначе.
- **Root в контейнере.** По умолчанию процесс — root. Если в приложении уязвимость (а LLM-приложение с инструментами — именно такое место, см. AIL-64), лишние права ему ни к чему. `USER app`.
- **Огромный образ.** `python:3.12` (не slim) плюс torch из зависимостей легко дают 5+ ГБ. Если эмбеддинги считаются через API — torch в образе не нужен; проверь, кто его тянет (`uv tree`).
- **Незакреплённые теги.** `FROM python:latest` и `uv:latest` — сегодня собирается, через месяц нет. Закрепляй версии; для паранойи — digest `@sha256:...`. Это тот же принцип, что пиннинг npm-пакетов.
- **Сторонние образы** — это сторонний код. Бери только официальные (`python`, `ghcr.io/astral-sh/uv`, образы Langfuse из их репозитория), смотри, кто публикует, не тяни «удобные» сборки неизвестных авторов.
- **Данные Langfuse** живут в томах. `docker compose down -v` их стирает. Модели Ollama в томе — тоже: это гигабайты повторной загрузки.
- **Ollama в контейнере на Маке** — без GPU. Не делай выводы о скорости локальной модели по такому замеру.
- **Модели Ollama в образе** (`RUN ollama pull` в Dockerfile) — образ на многие гигабайты; модели — в томе, скачиваются после запуска.
- **Ключ DeepSeek в контейнере, который видит копию базы сделок** — лишний путь для утечки. Такому контейнеру ключ облака не передавай.
- **Реальные данные сделок не попадают в образ и в репозиторий.** Демо в портфолио — на фейковых данных; если какой-то проект читает копию реальной базы, она монтируется томом только локально, только для чтения (`:ro`), и создаётся через `VACUUM INTO`, не `cp`.

- Свежий клон + `.env` из `.env.example` + `docker compose up --build` поднимает ассистента и Langfuse без ручных шагов.
- В образе нет `.env`, ключей и реальных данных; `docker history` чистый.
- Порты опубликованы на `127.0.0.1`; приложение работает от не-root пользователя.

## Ответы

1. Слои кэшируются, и изменение одного шага инвалидирует все последующие. Зависимости меняются редко, код — часто; при таком порядке правка кода не вызывает переустановку зависимостей.
2. `localhost` внутри контейнера — это сам контейнер. К соседнему сервису compose обращаются по имени сервиса: `http://langfuse-web:3000` (порт контейнерный, не хостовый).
3. `down` удаляет контейнеры и сеть, тома остаются. `down -v` удаляет и именованные тома — пропадут данные Langfuse и всё, что хранится в томах.
4. `latest` не закреплён; ключ через `ARG`/`ENV` запекается в образ и виден в `docker history`/`docker inspect`; `COPY . /app` без `.dockerignore` тащит `.env` и `.venv`; зависимости ставятся после копирования кода (нет кэша) и без lock-файла; `CMD` в shell-форме плохо принимает сигналы; процесс работает от root.
5. b. Для готовности нужен `healthcheck` у зависимости и `condition: service_healthy`, а лучше — устойчивость приложения к недоступности зависимости.
6. Порт контейнера доступен снаружи только через проброс; если слушать `127.0.0.1` внутри контейнера, проброшенный трафик не дойдёт. Наружу сервис открывает `ports:`, и там ты указываешь `127.0.0.1:...`, то есть только для своей машины.
7. Падает, если lock-файл не соответствует `pyproject.toml`, и ставит точные версии из lock. Аналог — `npm ci`.
8. Образ собран под `arm64`. Нужна мультиархитектурная сборка `docker buildx build --platform linux/amd64,linux/arm64` или сборка на сервере из исходников.
9. c. `host.docker.internal` работает в Docker Desktop и большинстве альтернатив на Маке; на Linux его, возможно, придётся добавить через `extra_hosts: ["host.docker.internal:host-gateway"]`.
10. Без него stdout Python буферизуется, и логи в `docker compose logs` появляются с задержкой или теряются при падении.
11. Трейсинг — вспомогательная функция; если из-за недоступного Langfuse пользователь не получает ответ, наблюдаемость стала точкой отказа. Проверка — остановить контейнер Langfuse и убедиться, что ассистент отвечает.
12. В Docker Desktop на macOS нет проброса GPU, контейнер работает на CPU и в разы медленнее; нативная Ollama использует GPU Apple Silicon через Metal.
13. Нативная: `http://host.docker.internal:11434/v1`. Сервис compose: `http://ollama:11434/v1` — по имени сервиса в общей сети, без публикации порта.
