## Зачем это AI-инженеру

README Проекта 3 — главный артефакт для собеседований из всего плана: он показывает умение не просто собрать RAG, а **измерять и улучшать** его. Фраза «подняли correctness с X% до Y%, и вот таблица, как» с честными цифрами, разбросом и выводами отличает кандидата от сотен с «чат-ботом по PDF». Ревьюер тратит на README пару минут, поэтому история должна читаться с первого экрана.

⚠️ Публичны в проекте только выдуманные вещи: база знаний `kb/`, набор `eval/golden.jsonl` и прогоны на нём. Прогон можно публиковать, только если в нём нет ни одного настоящего сообщения клиента; `outputs/handoff.jsonl`, логи бота и снимки базы магазина в репозиторий не попадают никогда.

## Теория

### Что ищет читатель

Неделя 8 оставила после себя журналы `experiments/EXP-*.md`, прогоны в `eval/runs/` и таблицу всех прогонов `eval/RESULTS.md`. Всё это — сырьё; README превращает его в историю, которую чужой человек прочтёт за пару минут. Начинаем с того, что этот человек ищет. Нанимающий инженер, открыв репозиторий, хочет за 1–2 минуты понять:

1. **Задача**: что за система и какая проблема.
2. **Как измеряется качество**: набор, метрики, судья и его проверка.
3. **Результат**: откуда стартовали, куда пришли, на чём.
4. **Как думает автор**: гипотезы, что не сработало, что удивило, ограничения.
5. **Можно ли это запустить**: одна команда для evals.

Пункт 4 недооценивают. Таблица, где всё помогло, выглядит подозрительно; честное «реранкер большой модели ничего не дал, а маленькой дал +N п.п.» и «улучшение на 3 п.п. в пределах шума, не засчитываем» говорят о зрелости больше, чем любая цифра.

### Таблица экспериментов

Сердце README — таблица, где каждая строка — один эксперимент недели 8. Колонки — те же метрики, что в журналах `EXP-*.md`: качество поиска и ответа, цена, латентность и вывод по правилу значимости:

| # | Эксперимент | hit@5 | correctness | faithfulness | $ / 100 q | p50 / p90, с | Вывод |
|---|---|---|---|---|---|---|---|
| 0 | Baseline: fixed-512, гибрид + переформулировка, модель L | 0,71 | 0,64 ± 0,02 | 0,83 | … | … | — |
| 1 | Chunking по заголовкам (EXP-01) | 0,84 | 0,72 ± 0,02 | 0,86 | … | … | Принято: +13 п.п. hit (11/2, p≈0,02) |
| 2 | Модель S без реранкера (EXP-02) | … | … | … | … | … | Отклонено: ниже порога качества |
| 3 | Модель S + реранкер (EXP-02) | … | … | … | … | … | Принято: качество в пределах шума от L, в N раз дешевле |
| 4 | Фильтр по товару (EXP-03, из разбора ошибок) | … | … | … | … | … | … |
| **Final (holdout)** | | … | … | … | … | … | Честная цифра |

(Цифры иллюстративные — у каждого будут свои.) Правила:

- **Кумулятивная или независимая?** Указываем явно. Обычно строки кумулятивны (каждая добавляет изменение к предыдущей принятой), отклонённые эксперименты помечены и не переносятся дальше.
- **Разброс** в формате «± половина размаха трёх прогонов» или «(min–max)»; формат объясняем под таблицей.
- **Колонка «Вывод»** с правилом значимости из [AIL-62](AIL-62.md): принято / отклонено / тенденция и парные расхождения.
- **Holdout отдельной строкой.** Если цифра на holdout ниже dev — так и пишем; это ожидаемо и честно.
- **Версия набора.** Если `golden.jsonl` менялся (исправления после [AIL-34](AIL-34.md)), либо перепрогоняем все строки на финальной версии (лучше, если недорого), либо указываем версию в каждой строке.

Таблица генерируется скриптом из `summary.json` прогонов, а не вручную: ручное копирование чисел — источник ошибок. Скрипт `eval/make_table.py` читает список прогонов из `experiments/runs.yaml` (пути к папкам `eval/runs/<timestamp>_<index>_<retriever>_k<k>/`) и печатает markdown. `eval/RESULTS.md` остаётся журналом всех прогонов подряд, а таблица в README — отобранной историей.

### Один график

Таблица точна, но динамику и компромиссы глаз схватывает быстрее на картинке. Один хороший график стоит половины текста. Варианты:
- «качество против стоимости» с точками конфигураций и фронтом Парето (из [AIL-33](AIL-33.md));
- «correctness по шагам» — столбцы baseline → … → final с отрезками разброса.

Подписи осей, единицы, легенда; PNG в `docs/` или `experiments/`, вставлен в README.

### Раздел «Как измеряется качество»

Цифрам в таблице поверят, только если понятно, как они получены. Этот раздел — коротко, но конкретно:
- **Набор**: сколько вопросов, типы и категории (матрица «тип × категория» из [AIL-28](AIL-28.md)), ловушки (архивная страница, таблицы тарифов, похожие товары, противоречие порога бесплатной доставки), сколько ручных и сколько синтетических, все проверены человеком, dev/holdout. Вопросы выдуманы, база знаний тоже.
- **Метрики**: hit@k, MRR, correctness, faithfulness, правильные отказы, `archived_in_context` — по одной строке определения.
- **Судья**: бинарный, с критикой; согласие с ручной разметкой на N примерах: X% (TPR/TNR). Отказы проверяет код, а не судья.
- **Шум**: разброс повторных прогонов, правило значимости.

Об этом спросят на собеседовании, поэтому формулировки здесь — заготовки для ответов.

### «Что помогло, что нет, что удивило»

Таблица отвечает «что изменилось», этот раздел — «чему научились»: пункт 4 из списка вопросов читателя. 3–6 пунктов, каждый с цифрой и объяснением механизма. Примеры формата (не результаты):
- «Чанкинг по заголовкам дал самый большой прирост: таблица тарифов по весу и зоне перестала отрываться от своего заголовка».
- «Реранкер не помог большой модели (в пределах шума), но маленькой дал +N п.п.: она хуже игнорирует лишний контекст».
- «Удивило: 13% провалов были ошибками набора (устаревшие эталоны после правки `kb/`), а не системы».

### Раздел «Как запустить evals»

Последний вопрос читателя — можно ли это запустить. Ревьюер должен суметь повторить. Минимум:

```markdown
## How to run evals

    uv sync                                  # versions pinned in uv.lock
    cp .env.example .env                     # fill in your API keys
    uv run python ingest.py                  # builds index.db from kb/ (committed)
    uv run python eval/run.py --config eval/configs/final.json        # dev split
    uv run python eval/compare.py eval/runs/<A> eval/runs/<B>
    uv run python eval/make_table.py experiments/runs.yaml

A full run on the dev split costs about $X and takes ~Y min (prices as of <date>).
```

`.env.example` содержит **имена** переменных без значений. Указываем, сколько стоит прогон: это забота о читателе и показатель того, что автор считает деньги.

### Гигиена публичного репозитория

README готов, но публичный репозиторий показывает не только его, а всю историю коммитов. Перед push проверяем:

- **Секреты.** `.env` в `.gitignore`; поиск по истории: `git log -p | grep -iE "sk-|api_key|secret"` (и аналогично по рабочей копии) или gitleaks из [AIL-25](AIL-25.md). Если ключ хоть раз попал в коммит — **отзываем ключ** у провайдера; удаление из истории не помогает, если репозиторий уже был публичным. После push смотрим, не пришло ли предупреждение от GitHub secret scanning.
- **Никаких данных магазина и клиентов.** Проект 3 про выдуманную базу знаний и выдуманный набор. Никаких `shop.db`, `analytics.db` и путей к `../shop-live/` из проекта 1, `outputs/handoff.jsonl`, логов бота с вопросами клиентов, токенов Telegram. Прогоны в `eval/runs/` публикуем, только если они сделаны на `golden.jsonl` без единого настоящего сообщения; прогон, куда хоть раз попали реальные вопросы, остаётся локально. Данные магазина в курсе выдуманы, но обращаемся с ними как с настоящими.
- **База знаний и чужой контент.** `kb/` и `golden.jsonl` коммитим: это наши выдуманные тексты, без них не собрать индекс и не повторить evals; короткие цитаты `evidence` в наборе — из своей же базы. Кэш `raw/web/` с чужой публичной страницей (необязательный пункт [AIL-20](AIL-20.md)) не коммитим.
- **Большие файлы.** `index*.db` (`index.db`, `index_ctx.db`, `index_fixed512.db`, `index_headings.db`), эмбеддинги, кеш судьи — в `.gitignore`. Коммитим `summary.json` и `config.json` прогонов (маленькие), `results.jsonl` — по желанию.
- **Версии зависимостей** закреплены (`uv.lock` или `requirements.txt` с точными версиями).

### Питч на 60 секунд

Та же история нужна и без экрана: на собеседовании её просят рассказать. README заодно служит сценарием устного рассказа. Репетируем вслух:

> Я сделал ассистента поддержки интернет-магазина, который отвечает по базе знаний со ссылкой на раздел, и построил для него систему оценки: 7x вопросов четырёх типов, проверенных вручную, метрики поиска и ответа, LLM-судья, сверенный с моей разметкой на N примерах. Провёл четыре эксперимента. Самый сильный эффект дал чанкинг по заголовкам, +X п.п. hit rate. Разбор ошибок показал, что 30% провалов — поиск находит страницу похожего товара, например гарантию «Свет мини» вместо «Свет»; фильтр по товару убрал большую часть. В итоге correctness выросла с A до B на отложенной выборке, а замена модели на маленькую с реранкером снизила стоимость в N раз без потери качества в пределах шума.

## DeepSeek и Ollama: как это сделать у нас

Структура README от провайдера не зависит. Меняется то, что читатель должен узнать о моделях, чтобы цифрам можно было верить и чтобы их можно было повторить. Факты о провайдерах сверены в ноябре 2026 по [api-docs.deepseek.com](https://api-docs.deepseek.com) и [docs.ollama.com](https://docs.ollama.com).

### Что обязательно написать про модели

- **Точные id и даты.** `deepseek-flash` / `deepseek-v4-pro` плюс `resp.model` из прогонов и дата: DeepSeek переназначает имена (сейчас `deepseek-flash` — это V4.1-Flash-1017), и через полгода «deepseek-flash» будет другой моделью.
- **Режим рассуждений** ответчика и судьи (thinking включён/выключен) — он меняет и качество, и цену, и шум.
- **Для Ollama — точный тег и железо.** «`qwen3:4b`, ноутбук с 8 ГБ RAM, без отдельной видеокарты, контекст 8k» — без этого латентность локальной модели ничего не значит. Указываем, что теги Ollama по умолчанию квантизованы.
- **Судья и его проверка.** «Judge: `deepseek-v4-pro`, thinking off, temperature 0; agreement with our labels X% on N answers; second opinion from <Claude/OpenAI model> on disputed cases». Если судья из того же семейства, что ответчик, пишем, как проверяли самопредпочтение.
- **Цена с оговорками.** Для DeepSeek: по ценам на дату, с учётом кеша, и в каком окне (пик или вне пика) делались прогоны. Для Ollama: «$0 API, runs on the user's device», рядом p50/p90 латентности.
- **Сравнение с Claude/OpenAI — только если оно действительно прогонялось.** Одна-две строки «для сравнения» на тех же вопросах сильно усиливают README; выдуманные или «по рейтингам» цифры его убивают.

В «How to run evals» добавляем шаги для локальной части: установить Ollama по официальной инструкции для своей ОС с ollama.com (на macOS — проверить приложение `codesign -dv` и `spctl -a -vv` перед первым запуском), `ollama pull <точный тег>` для ответчика и `ollama pull bge-m3` для эмбеддингов, и как задать контекст (`OLLAMA_CONTEXT_LENGTH`). Хороший жест для ревьюера: **конфигурация, которая работает вообще без облачных ключей** (локальный ответчик + локальные эмбеддинги, только метрики поиска и проверки отказов кодом), чтобы проект можно было запустить за 5 минут бесплатно. Указываем и стоимость полного прогона на DeepSeek (например, «≈$0.6 at peak prices, about half off-peak, as of <date>») — цифру берём из своих прогонов.

## На что обратить внимание

- **Цифры без разброса и размера набора** выглядят как маркетинг. Всегда «на N вопросах», «± разброс».
- **Только dev-цифры.** Финальный результат — holdout; если его нет, читатель-инженер это заметит.
- **Ручное копирование чисел** в таблицу — опечатки и расхождения с прогонами. Таблицу генерирует скрипт.
- **Несравнимые строки**: разные версии набора без пометки.
- **Скрытые неудачи.** Отклонённые эксперименты — тоже результат, их показывают.
- **README, который нельзя запустить**: нет `.env.example`, `kb/` не закоммичена, не закреплены версии.
- **Секрет в истории git** — отзывать ключ, а не только чистить историю.
- **Прогон с настоящими вопросами клиентов в `eval/runs/`.** Публиковать можно только прогоны на выдуманном наборе.
- **Стена текста.** Первый экран: абзац итога + таблица + график.
- **«deepseek-flash» без даты и `resp.model`** — через полгода цифры будет невозможно ни повторить, ни объяснить.
- **Латентность Ollama без железа** («p90 9 s») ничего не говорит: на ноутбуке с 8 ГБ и на сервере с GPU это разные числа.
- **Строки «Claude/OpenAI для сравнения» без реальных прогонов.** Только то, что прогнали сами на том же наборе.
