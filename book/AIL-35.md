# 8.5 · Проект 3: таблица экспериментов в README  (AIL-35)

> **Неделя 8** · Evals · ⏱ ~4 ч · Проект

## Зачем это AI-инженеру

README Проекта 3 — главный артефакт для собеседований из всего плана: он показывает, что ты умеешь не просто собрать RAG, а **измерять и улучшать** его. Фраза «я поднял correctness с X% до Y%, и вот таблица, как» с честными цифрами, разбросом и выводами отличает кандидата от сотен с «чат-ботом по PDF». Ревьюер тратит на README пару минут, поэтому история должна читаться с первого экрана.

## Теория

### Что ищет читатель

Нанимающий инженер, открыв репозиторий, хочет за 1–2 минуты понять:

1. **Задача**: что за система и какая проблема.
2. **Как измеряется качество**: набор, метрики, судья и его проверка.
3. **Результат**: откуда стартовал, куда пришёл, на чём.
4. **Как ты думаешь**: гипотезы, что не сработало, что удивило, ограничения.
5. **Можно ли это запустить**: одна команда для evals.

Пункт 4 недооценивают. Таблица, где всё помогло, выглядит подозрительно; честное «реранкер большой модели ничего не дал, а маленькой дал +N п.п.» и «улучшение на 3 п.п. в пределах шума, не засчитываю» говорят о зрелости больше, чем любая цифра.

### Структура README

```
# Exchange Docs Assistant: evals & experiments

One-paragraph summary: what it is + headline result
("correctness 0.6x → 0.8x on a 7x-question human-reviewed set, at N× lower cost")

## Results at a glance        ← table + one chart
## The system                 ← short diagram, link to Project 2
## How quality is measured    ← dataset, metrics, judge validation, noise
## Experiments                ← table with all experiments + per-experiment conclusions
## What worked, what didn't, what surprised me
## Error analysis             ← distribution of failure causes, the fix
## Limitations
## How to run evals           ← commands, env vars, cost of a run
## Repo layout
```

Заголовочный абзац и «Results at a glance» — самое важное: многие дальше не читают.

### Таблица экспериментов

Колонки из задачи плюс то, что требуют предыдущие главы:

| # | Эксперимент | hit@5 | correctness | faithfulness | $ / 100 q | p50 / p90, с | Вывод |
|---|---|---|---|---|---|---|---|
| 0 | Baseline: fixed-512, vector, model L | 0,71 | 0,64 ± 0,02 | 0,83 | … | … | — |
| 1 | Chunking по заголовкам (EXP-01) | 0,84 | 0,72 ± 0,02 | 0,86 | … | … | Принято: +13 п.п. hit (11/2, p≈0,02) |
| 2 | + гибрид и переформулировка | … | … | … | … | … | … |
| 3 | Модель S + реранкер (EXP-02) | … | … | … | … | … | Принято: качество в пределах шума от L, в N раз дешевле |
| 4 | Фильтр биржи (EXP-03, из разбора ошибок) | … | … | … | … | … | … |
| **Final (holdout)** | | … | … | … | … | … | Честная цифра |

(Цифры иллюстративные — у тебя будут свои.) Правила:

- **Кумулятивная или независимая?** Укажи явно. Обычно строки кумулятивны (каждая добавляет изменение к предыдущей принятой), отклонённые эксперименты помечены и не переносятся дальше.
- **Разброс** в формате «± половина размаха трёх прогонов» или «(min–max)»; объясни формат под таблицей.
- **Колонка «Вывод»** с правилом значимости из [AIL-62](AIL-62.md): принято / отклонено / тенденция и парные расхождения.
- **Holdout отдельной строкой.** Если цифра на holdout ниже dev — так и пиши; это ожидаемо и честно.
- **Версия набора.** Если набор менялся (исправления после [AIL-34](AIL-34.md)), либо перепрогони все строки на финальной версии (лучше, если недорого), либо укажи версию в каждой строке.

Таблица генерируется скриптом из `summary.json` прогонов, а не вручную: ручное копирование чисел — источник ошибок. Скрипт `evals/make_table.py` читает список прогонов из `experiments/runs.yaml` и печатает markdown.

### Один график

Один хороший график стоит половины текста. Варианты:
- «качество против стоимости» с точками конфигураций и фронтом Парето (из [AIL-33](AIL-33.md));
- «correctness по шагам» — столбцы baseline → … → final с отрезками разброса.

Подписи осей, единицы, легенда; PNG в `docs/` или `experiments/`, вставлен в README.

### Раздел «Как измеряется качество»

Коротко, но конкретно:
- **Набор**: сколько вопросов, типы и биржи (матрица из [AIL-28](AIL-28.md)), сколько ручных и сколько синтетических, все проверены человеком, dev/holdout.
- **Метрики**: hit@k, MRR, correctness, faithfulness, правильные отказы — по одной строке определения.
- **Судья**: бинарный, с критикой; согласие с ручной разметкой на N примерах: X% (TPR/TNR).
- **Шум**: разброс повторных прогонов, правило значимости.

Это то, о чём тебя спросят на собеседовании, поэтому формулировки здесь — заготовки для ответов.

### «Что помогло, что нет, что удивило»

3–6 пунктов, каждый с цифрой и объяснением механизма. Примеры формата (не результаты):
- «Чанкинг по заголовкам дал самый большой прирост: таблицы параметров endpoint перестали отрываться от описания».
- «Реранкер не помог большой модели (в пределах шума), но маленькой дал +N п.п.: она хуже игнорирует лишний контекст».
- «Удивило: 13% провалов были ошибками набора (устаревшие эталоны), а не системы».

### Раздел «Как запустить evals»

Ревьюер должен суметь повторить. Минимум:

```markdown
## How to run evals

    python -m venv .venv && source .venv/bin/activate
    pip install -r requirements.txt          # versions pinned
    cp .env.example .env                     # fill in your API keys
    python scripts/download_docs.py          # fetches public exchange docs
    python scripts/build_index.py --config evals/configs/final.json
    python evals/run.py --config evals/configs/final.json            # dev split
    python evals/compare.py evals/runs/<A> evals/runs/<B>

A full run on the dev split costs about $X and takes ~Y min (prices as of <date>).
```

`.env.example` содержит **имена** переменных без значений. Укажи, сколько стоит прогон: это забота о читателе и показатель того, что ты считаешь деньги.

### Гигиена публичного репозитория

Перед push проверь:

- **Секреты.** `.env` в `.gitignore`; поиск по истории: `git log -p | grep -iE "sk-|api_key|secret"` (и аналогично по рабочей копии). Если ключ хоть раз попал в коммит — **отзови ключ** у провайдера; удаление из истории не помогает, если репозиторий уже был публичным. После push посмотри, не пришло ли предупреждение от GitHub secret scanning.
- **Никаких торговых данных.** Проект 3 про публичную документацию бирж. Никаких файлов `arbitrage*.db`, логов арбитражного приложения, ключей бирж, реальных позиций и сделок. Если где-то нужен пример с данными — только выдуманные.
- **Скачанная документация.** Не коммить сами доки бирж целиком: это чужой контент. Коммить скрипт скачивания; короткие цитаты в наборе (`evidence`) допустимы как ссылка на источник.
- **Большие файлы.** Индексы, эмбеддинги, кеш судьи — в `.gitignore`. Коммитить `summary.json` и `config.json` прогонов (маленькие), `results.jsonl` — по желанию.
- **Версии зависимостей** закреплены в `requirements.txt`.

### Питч на 60 секунд

README заодно служит сценарием устного рассказа. Отрепетируй вслух:

> Я сделал RAG-ассистента по API-документации четырёх криптобирж и построил для него систему оценки: 7x вопросов четырёх типов, проверенных вручную, метрики поиска и ответа, LLM-судья, сверенный с моей разметкой на N примерах. Провёл пять экспериментов. Самый сильный эффект дал чанкинг по заголовкам, +X п.п. hit rate. Разбор ошибок показал, что 30% провалов — поиск находит похожий раздел другой биржи; фильтр по бирже убрал большую часть. В итоге correctness выросла с A до B на отложенной выборке, а замена модели на маленькую с реранкером снизила стоимость в N раз без потери качества в пределах шума.

## DeepSeek и Ollama: как это сделать у нас

Структура README от провайдера не зависит. Меняется то, что читатель должен узнать о моделях, чтобы цифрам можно было верить и чтобы их можно было повторить. Факты о провайдерах сверены в ноябре 2026 по [api-docs.deepseek.com](https://api-docs.deepseek.com) и [docs.ollama.com](https://docs.ollama.com).

### Что обязательно написать про модели

- **Точные id и даты.** `deepseek-flash` / `deepseek-v4-pro` плюс `resp.model` из прогонов и дата: DeepSeek переназначает имена (сейчас `deepseek-flash` — это V4.1-Flash-1017), и через полгода «deepseek-flash» будет другой моделью.
- **Режим рассуждений** ответчика и судьи (thinking включён/выключен) — он меняет и качество, и цену, и шум.
- **Для Ollama — точный тег и железо.** «`qwen3:4b` на Apple M2, 8 ГБ, контекст 8k» — без этого латентность локальной модели ничего не значит. Укажи, что теги Ollama по умолчанию квантизованы.
- **Судья и его проверка.** «Judge: `deepseek-v4-pro`, thinking off, temperature 0; agreement with my labels X% on N answers; second opinion from <Claude/OpenAI model> on disputed cases». Если судья из того же семейства, что ответчик, скажи, как ты проверял самопредпочтение.
- **Цена с оговорками.** Для DeepSeek: по ценам на дату, с учётом кеша, и в каком окне (пик или вне пика) делались прогоны. Для Ollama: «$0 API, runs on the user's device», рядом p50/p90 латентности.
- **Сравнение с Claude/OpenAI — только если ты его действительно прогонял.** Одна-две строки «для сравнения» на тех же вопросах сильно усиливают README; выдуманные или «по рейтингам» цифры его убивают.

### `.env.example` и «How to run» на нашем стеке

```text
# .env.example — names only, no values
DEEPSEEK_API_KEY=
# optional, for the comparison rows
ANTHROPIC_API_KEY=

# optional: Langfuse Cloud tracing

LANGFUSE_SECRET_KEY=
```

В «How to run evals» добавь шаги для локальной части: установить Ollama с ollama.com (для приложения на Mac — проверить `codesign -dv` и `spctl -a -vv` перед первым запуском), `ollama pull <точный тег>` для ответчика и модели эмбеддингов, и как задать контекст (`OLLAMA_CONTEXT_LENGTH`). Хороший жест для ревьюера: **конфигурация, которая работает вообще без облачных ключей** (локальный ответчик + локальные эмбеддинги, только метрики поиска и assertions), чтобы repo можно было запустить за 5 минут бесплатно. Укажи и стоимость полного прогона на DeepSeek (например, «≈$0.6 at peak prices, about half off-peak, as of <date>») — цифру возьми из своих прогонов.

No trading data, keys or account information is used anywhere in this project». Строку пишешь, только если это правда, и проверяешь перед push (раздел «Гигиена публичного репозитория» выше).

## На что обратить внимание

- **Цифры без разброса и размера набора** выглядят как маркетинг. Всегда «на N вопросах», «± разброс».
- **Только dev-цифры.** Финальный результат — holdout; если его нет, читатель-инженер это заметит.
- **Ручное копирование чисел** в таблицу — опечатки и расхождения с прогонами. Генерируй таблицу скриптом.
- **Несравнимые строки**: разные версии набора без пометки.
- **Скрытые неудачи.** Отклонённые эксперименты — тоже результат, их показывают.
- **README, который нельзя запустить**: нет `.env.example`, нет скрипта загрузки доков, не закреплены версии.
- **Секрет в истории git** — отзывать ключ, а не только чистить историю.
- **Стена текста.** Первый экран: абзац итога + таблица + график.
- **«deepseek-flash» без даты и `resp.model`** — через полгода цифры будет невозможно ни повторить, ни объяснить.
- **Латентность Ollama без железа** («p90 9 s») ничего не говорит: на M2 с 8 ГБ и на сервере с GPU это разные числа.
- **Строки «Claude/OpenAI для сравнения» без реальных прогонов.** Только то, что ты прогнал сам на том же наборе.
