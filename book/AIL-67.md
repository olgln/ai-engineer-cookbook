# 12.1 · Профиль GitHub и LinkedIn  (AIL-67)

> **Неделя 12** · Портфолио · ⏱ ~4 ч · Проект

## Зачем это AI-инженеру

Рекрутер и нанимающий менеджер сначала открывают профиль, а не код: за 20–60 секунд они решают, стоит ли кликать дальше. На рынке AI Engineer много кандидатов «прошёл курс по LangChain», и профиль — первое место, где видно, что у кандидата другое: опыт в своей предметной области плюс четыре LLM-проекта с измеренным качеством. На собеседовании профиль тоже всплывает: интервьюер часто открывает GitHub прямо во время звонка.

## Теория

### Как на самом деле смотрят профиль

Наём обычно идёт в три фильтра, и у каждого свой читатель:

```
Рекрутер / sourcer        Нанимающий инженер          Интервьюер
(20–60 сек, не пишет код) (2–5 мин, пишет код)        (перед звонком, 10 мин)
 ─ заголовок               ─ закреплённые репо          ─ конкретный проект
 ─ ключевые слова          ─ README: что, как, цифры    ─ код, коммиты, тесты
 ─ последняя роль/опыт     ─ схема архитектуры          ─ вопросы «почему так»
 ─ локация/формат          ─ есть ли evals/тесты
```

Отсюда главное правило: **каждый уровень должен работать без следующего**. Рекрутер, который не откроет ни одного репозитория, должен из заголовка и первых строк понять «AI / Backend Engineer, Python, RAG, агенты, evals». Инженер, который откроет один репозиторий, должен за минуту увидеть цифры качества. Это тот же принцип, что у API: публичный контракт понятен без чтения реализации.

### Рекрутеры ищут по ключевым словам

LinkedIn Recruiter и внутренние ATS — это, по сути, полнотекстовый поиск с фильтрами. Если в профиле нет слов «LLM», «RAG», «Python», кандидат не попадёт в выдачу, как бы хорош ни был код. Поэтому ключевые слова должны стоять в трёх местах: заголовок (headline), раздел About и навыки (Skills). При этом список из 40 технологий выглядит как спам; лучше 10–15 честных, сгруппированных.

Типичный набор ключевых слов для профиля после курса:

| Группа | Слова |
|---|---|
| LLM | LLM, RAG, embeddings, tool calling, agents, MCP, evals, prompt engineering |
| Стек | Python, свой основной язык, Pydantic, FastAPI (если использовали), SQLite/PostgreSQL |
| LLM API | OpenAI-compatible API (DeepSeek, Ollama), Anthropic/OpenAI API — только те, что реально вызывали |
| Инфра | Docker, Langfuse/promptfoo, Ollama (local LLMs), vector DB (какую реально использовали) |
| Домен | своя предметная область: e-commerce, логистика, финансы, медицина… — те слова, по которым в ней ищут |

### Позиционирование: одна фраза

Позиционирование — это ответ на вопрос «почему этот кандидат, а не другой джун в AI». Сильная комбинация — «своя предметная область + AI»: годы работы в какой-то области (e-commerce, логистика, банк, медицина, госсектор) плюс LLM-проекты с evals на задачах, похожих на её задачи. Проекты курса сделаны на интернет-магазине, но паттерны переносятся: ассистент по базе знаний, аналитик над базой, агент-разборщик инцидентов нужны почти везде — в профиле стоит назвать, где именно они нужны в своей области. Формула (пример для бэкграунда в e-commerce):

> **Backend / AI Engineer.** Строю LLM-продукты с измеримым качеством: RAG, агенты, evals. До этого — 5 лет бэкенда в e-commerce (заказы, платежи, интеграции со службами доставки).

Обратим внимание, чего здесь нет: «увлечённый», «быстро обучаюсь», «passionate about AI». Это слова, которые не несут информации. Вместо прилагательных — существительные и цифры.

### Что такое README профиля GitHub

Если создать публичный репозиторий с именем, совпадающим с логином (`<username>/<username>`), его `README.md` показывается вверху страницы профиля. Это «главная страница» кандидата. Под ним — до шести закреплённых (pinned) репозиториев или gist'ов.

Хороший README профиля короткий — помещается на один экран:

```markdown
# Имя Фамилия — Backend / AI Engineer

Строю LLM-приложения с измеримым качеством (RAG, агенты, evals) на Python.
Бэкграунд: 5 лет бэкенда в e-commerce — заказы, платежи,
интеграции со службами доставки.

**Проекты**
- **support-kb-rag** — ассистент поддержки магазина по базе знаний с цитатами;
  hit@5 0.71 → 0.89 после гибридного поиска и реранкера.
  Там же evals и эксперименты: golden set на 100 вопросов, LLM-судья, таблица результатов.
- **order-investigator-agent** — агент разбирает проблемные заказы (на демо-базе), evals на 20 случаях.
- **shop-analyst-bot** — Telegram-бот с tool calling поверх read-only снимка базы, $0.004 за ответ.

**Стек:** Python, Pydantic, SQLite, Docker, DeepSeek + Ollama (OpenAI-compatible),
Claude/OpenAI для сравнения.
**Пишу:** [статья на Хабре](...)  ·  **LinkedIn:** [...](...)
```

Цифры в примере — плейсхолдеры: ставим свои реальные, из evals глав недель 6–10. Проекты 2 и 3 живут в одном репозитории (`support-kb-rag`: RAG и его evals с экспериментами), поэтому четыре проекта — это три репозитория. Строку «Бэкграунд» пишем про свою область. Чего избегать: анимированных баннеров, счётчиков посетителей, «GitHub stats» карточек, «трофеев» и стены значков технологий. Для инженера-ревьюера это шум, а иногда и минус: видно, что на оформление ушло больше времени, чем на содержание.

### Закреплённые репозитории

Закрепляем ровно то, что хотим обсуждать на собеседовании. Порядок — по силе, а не по хронологии: самый впечатляющий первым (скорее всего, RAG с evals или агент). У каждого закреплённого репозитория должны быть:

- **description** (строка под названием) — одно предложение с глаголом и результатом;
- **topics** (теги репозитория): `llm`, `rag`, `evals`, `python` — по ним тоже ищут;
- README по шаблону из главы [12.2 · README, схемы и демо для всех проектов](AIL-50.md);
- никаких «Initial commit» и пустых веток как единственного содержимого.

Учебный репозиторий `ai-engineering-journey` с `notes/` можно оставить публичным, но не закреплять: он показывает процесс, а не результат.

### Что можно публиковать про свою работу

Опыт в своей области — сильный аргумент, но рабочий код и данные публиковать нельзя и не нужно: они принадлежат работодателю или клиенту, в них ключи, данные пользователей, внутренние цифры и логика, которая является преимуществом компании. В профиле такую работу описывают словами: что делает система, масштаб, свои технические решения и результат. Если хочется показать код из своей области — делаем отдельный маленький публичный пример на **выдуманных** данных (как демо-база магазина в курсе), а не выносим рабочий. Правило из всей книги действует и здесь: в публичном портфолио только демо-данные — ни снимка базы магазина, ни настоящих сообщений клиентов, ни скриншотов с именами, телефонами и суммами. Данные магазина выдуманы, но обращаемся с ними как с настоящими.

### LinkedIn: анатомия профиля

| Поле | Что писать | Ошибка |
|---|---|---|
| Фото | Лицо крупно, нейтральный фон, то же фото, что на GitHub | Фото с отдыха, логотип, пусто |
| Headline (заголовок) | «Backend / AI Engineer · Python · RAG, agents, evals» | «Ищу работу», «Open to work» вместо роли |
| About | 3 коротких абзаца: кто, что построил (с цифрами), что ищет | Автобиография с детства |
| Experience | Работа в своей области: что делает система, стек, масштаб, свой вклад | Пустой период без объяснения |
| Projects / Featured | 4 проекта со ссылками на GitHub, статья | Ссылки на курсы как на «проекты» |
| Skills | 10–15 навыков, верхние 3 закреплены: LLM, Python, RAG | 50 навыков, включая Excel |
| Open to work | Включить с указанием ролей и формата (remote/релокация) | Публичная зелёная рамка без ролей |

В About первая строка видна без клика «ещё» — в неё ставим позиционирование. Пишем на английском: LinkedIn — международная площадка, а русскоязычный рекрутер английский тоже прочтёт. Русская версия профиля возможна (LinkedIn поддерживает профиль на втором языке), но это необязательно.

### Единая идентичность

Одинаковые ник, фото, имя (в латинской транслитерации, одинаковой везде) и заголовок на GitHub, LinkedIn, Хабре, в Telegram для работы и в резюме. Это не косметика: рекрутер ищет кандидата по имени, и разные транслитерации («Ivan Petrov» / «Ivan Petroff») превращают одного кандидата в трёх неизвестных. Профили должны ссылаться друг на друга по кругу: GitHub → LinkedIn, LinkedIn → GitHub и статья, статья → GitHub.

### Безопасность профиля

- Включаем двухфакторную аутентификацию на GitHub и LinkedIn.
- В публичных репозиториях проверяем историю коммитов на секреты (`.env`, ключи API): удалённый в последнем коммите ключ остаётся в истории. Если ключ когда-либо попадал в коммит — отзываем его у провайдера, переписывать историю недостаточно.
- Включаем в GitHub настройку скрытия личного email в коммитах (Settings → Emails → «Keep my email addresses private») и используем выданный `noreply`-адрес.

## DeepSeek и Ollama: как это сделать у нас

Кода в этой главе нет, меняется подача. Проекты курса собраны в основном на DeepSeek (облако, дёшево) и Ollama (локально, бесплатно, для данных клиентов и снимка базы). Прятать это не нужно и извиняться тоже: подаём как осознанный выбор.

- **Мультипровайдерность — это сила.** Строка вроде «Provider-agnostic: one OpenAI-compatible client; DeepSeek for cloud runs, local models via Ollama for private data; compared with Claude/OpenAI on the same eval set» показывает то, что ценят в AI Engineer: абстракцию над провайдером, контроль стоимости, приватность данных и сравнение моделей на evals, а не на ощущениях.
- **В вакансиях чаще всего Claude и OpenAI.** Проверяем на 5–10 вакансиях, на которые реально будем откликаться (подробный словарь вакансий соберём в главе [13.1 · Резюме](AIL-53.md)): если там «Anthropic/OpenAI API», а мы их ни разу не вызывали, в профиль их не пишем. Лучше прогнать хотя бы один eval каждого проекта через Claude и через OpenAI (на демо-базе и выдуманной базе знаний, обычно это единицы долларов — считаем по текущему прайсу) и положить результат в таблицу сравнения. Тогда ключевые слова честные, и есть что рассказать.
- **Приватность как аргумент.** «Customer data never leaves my machine: local models via Ollama» — сильная строка, но только если это правда. DeepSeek по своей политике конфиденциальности хранит и обрабатывает данные в Китае (проверено в ноябре 2026), поэтому снимок базы и сообщения клиентов шли только в Ollama, а в облако — демо-база и публичная база знаний. Правило касается любого облачного провайдера.

| | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| Как часто в вакансиях | часто | часто | реже | реже; ищут как «local / self-hosted LLM» |
| Как писать в профиле | «Anthropic API», если вызывали | «OpenAI API», если вызывали | «DeepSeek (OpenAI-compatible API)» | «Ollama, local LLMs» |
| Что доказывает | знание основного стека рынка | то же | контроль стоимости, абстракция над провайдером | приватность, работа офлайн, self-hosted |
| К какому вопросу готовиться | «чем отличается от других API» | то же | «китайский провайдер — а данные?» | «насколько хуже качество и почему» |

## Маршрут изучения

1. Открываем https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/managing-your-profile-readme → читаем целиком (≈10 мин). Важно: репозиторий должен быть публичным, с именем ровно как логин, и с `README.md` в корне.
2. Открываем https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/pinning-items-to-your-profile → (≈5 мин). Выносим: максимум шесть закреплений, порядок меняется перетаскиванием.
3. Открываем 5–7 профилей AI-инженеров, которые нравятся (находим через авторов статей из глав про evals и RAG, например Eugene Yan, Hamel Husain, Jason Liu — на их сайтах есть ссылки на GitHub/LinkedIn) (≈30 мин). Для каждого записываем: заголовок, первую строку About, что закреплено. Цель — увидеть, как мало текста у сильных профилей.
4. Открываем https://www.techinterviewhandbook.org/ → раздел про резюме и LinkedIn, если он есть в меню (≈20 мин). Берём правило «результат + цифра» — оно же пригодится в главе [13.1 · Резюме](AIL-53.md).
5. Проверяем в справке LinkedIn (Help Center, поиск по «Open to work» и «profile in another language») текущие настройки видимости (≈10 мин): интерфейс меняется, поэтому сверяемся со справкой, а не с чужими гайдами.
6. Открываем https://api-docs.deepseek.com/quick_start/pricing и https://docs.ollama.com/api/openai-compatibility (≈10 мин). Не учить, а свериться: имена моделей, которые упоминаются в профиле и README, ещё актуальны, а формулировка «OpenAI-compatible» верна для обоих.

## На что обратить внимание

- **Секреты в истории.** Перед тем как сделать учебные репозитории публичными, проходим историю: `git log -p | grep -iE "api[_-]?key|sk-|secret"` — грубо, но ловит очевидное. Есть специализированные сканеры секретов (gitleaks, trufflehog), но это сторонний код: перед установкой проверяем источник, версию и подпись.
- **Данные снимка в демо.** Скриншоты Telegram-бота с выручкой из снимка, именами и телефонами покупателей — утечка. Перегенерируем на демо-базе.
- **Рабочий код и данные.** Ничего от работодателя или клиентов — ни файлом, ни скриншотом, ни «обезличенной» выгрузкой.
- **Профиль «в процессе».** Пустой README профиля хуже, чем его отсутствие. Делаем всё за один заход.
- **Overclaiming.** Не пишем «Senior AI Engineer» и «production LLM systems serving millions», если это учебные проекты. На собеседовании это раскрывается за пять минут. Честная формулировка «built and evaluated» сильнее.
- **Английский.** Одна грамматическая ошибка в заголовке заметнее, чем десять в коде. Стоит прогнать тексты через LLM с просьбой исправить только ошибки, не стиль.
- **Активность коммитов.** Зелёный график сам по себе ничего не значит, но 13 недель учёбы дают честную активность — историю ради красоты не переписываем.

## Практика

- [ ] **Инвентаризация.** Выписать в `notes/portfolio.md` четыре проекта: название репозитория (проекты 2 и 3 — в `support-kb-rag`), одна фраза «что делает», одна главная цифра (из evals или стоимости), ссылка.
- [ ] **Аудит секретов и данных.** Для каждого публичного репозитория: проверить `.gitignore` (там `.env`, `*.db`, `outputs/`, `runs/`), историю коммитов на ключи, отсутствие снимка базы, `../shop-live/` и настоящих сообщений клиентов (только демо-база и выдуманная `kb/`). Результат — галочка напротив каждого репозитория в `notes/portfolio.md`.
- [ ] **Провайдеры.** Для каждого проекта дописать в `notes/portfolio.md`, на каких моделях он реально работал (DeepSeek, какая модель в Ollama, Claude/OpenAI для сравнения) и на каких данных (в облако — только демо-база и база знаний, снимок и сообщения клиентов — только локально). Если Claude или OpenAI ни разу не вызывали, сделать хотя бы один eval-прогон на каждом, прежде чем упоминать их в профиле.
- [ ] **Позиционирование.** Написать три варианта фразы-позиционирования на английском (до 25 слов) с опорой на свою предметную область. Попросить LLM сыграть рекрутера, который за 10 секунд решает «звать или нет», и объяснить выбор. Выбрать одну.
- [ ] **README профиля.** Создать репозиторий `<username>/<username>`, написать README по скелету из «Теории» (на английском, один экран). Проверить в браузере в светлой и тёмной теме.
- [ ] **Закрепления.** Закрепить три репозитория проектов в порядке силы. Каждому — description с результатом и 3–5 topics.
- [ ] **LinkedIn.** Заполнить фото, headline, About (3 абзаца), Experience (работа в своей области: что делает система, стек, масштаб — без закрытых данных работодателя и клиентов), Featured (4 проекта + позже статья), Skills (10–15, три закреплены), Open to work с ролями AI Engineer / LLM Engineer / Backend Engineer.
- [ ] **Единая идентичность.** Один ник, одно фото, одна транслитерация имени. Ссылки: GitHub ↔ LinkedIn. Место для ссылки на статью оставить — добавим в главе [12.3 · Статья на Хабр / LinkedIn](AIL-51.md).
- [ ] **Внешний взгляд.** Открыть оба профиля в режиме инкогнито (LinkedIn — через «View as public»), засечь 30 секунд и записать, что понял бы незнакомый человек.

## Готово, когда

- README профиля GitHub опубликован: кто, стек, своя предметная область, закреплённые проекты с одной цифрой каждый.
- LinkedIn заполнен: фото, headline AI / Backend Engineer, About, опыт, проекты, навыки, Open to work.
- Ник, фото и имя совпадают везде; профили ссылаются друг на друга.
- В публичных репозиториях нет секретов, данных снимка базы магазина и ничего от работодателя.

## Ответы

1. **b.** Публичный репозиторий `<username>/<username>` с `README.md` в корне — особый случай, который GitHub показывает вверху профиля.
2. Рекрутеры ищут через поиск LinkedIn/ATS по полям профиля; до кода они доходят только если профиль нашёлся. Текст репозиториев читает уже инженер, а не поиск.
3. **b.** До шести репозиториев или gist'ов.
4. Ни одного слова о роли, стеке или результате — только прилагательные. Поиск по «LLM», «Python», «RAG» его не найдёт; лучше «Backend / AI Engineer · Python · RAG, agents, evals».
5. Нет: ключ остаётся в истории git и, возможно, уже скопирован ботами, сканирующими GitHub. Нужно отозвать ключ у провайдера и выпустить новый; чистка истории — второй шаг, не замена.
6. **c.** Первым — то, что лучше всего доказывает нужные для роли навыки и что хочется обсуждать на собеседовании.
7. На нём данные снимка: имена и телефоны покупателей, номера заказов, суммы, выручка магазина. Данные выдуманы, но обращаемся с ними как с настоящими; правило портфолио — только демо-база.
8. Рекрутер ищет кандидата по имени на разных площадках; разные написания разрывают связь между профилями, статьёй и резюме.
9. Счётчики и карточки статистики — шум, 42 значка — стена без смысла, эмодзи-заголовок отвлекают. Нет главного: кто автор, что построил, цифры.
10. Писать: что делает система и для кого (в общих словах), масштаб (нагрузка, число интеграций, размер команды), свои технические решения и результат с цифрой, которую можно раскрывать. Не писать: данные пользователей и клиентов, внутренние цифры компании (выручку, объёмы, если они не публичны), ключи, адреса внутренних систем и детали, которые являются преимуществом компании или закрыты договором.
11. **b.** Ключевые слова становятся честными, а сравнение провайдеров на одном eval-наборе — сильный материал для профиля и интервью. Вариант a — overclaiming, который раскроется на первом вопросе.
12. Список имён без контекста: непонятно, что с ними делали, и, скорее всего, часть не вызывали. Лучше: какой провайдер для чего (облако / локально) и чем закончилось сравнение.
13. Например: «Provider-agnostic LLM apps: DeepSeek for cloud runs, local models via Ollama for private data, benchmarked against Claude/OpenAI on the same evals». Главное — подать как выбор (стоимость, приватность, сравнение), а не как вынужденную замену.
