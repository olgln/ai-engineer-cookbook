# 12.1 · Профиль GitHub и LinkedIn  (AIL-67)

> **Неделя 12** · Портфолио · ⏱ ~4 ч · Проект

## Зачем это AI-инженеру

Рекрутер и нанимающий менеджер сначала открывают профиль, а не код: за 20–60 секунд они решают, стоит ли кликать дальше. На рынке AI Engineer много кандидатов «прошёл курс по LangChain», и профиль — первое место, где ты показываешь, что у тебя другое: бэкенд с real-time и деньгами плюс четыре LLM-проекта с измеренным качеством. На собеседовании профиль тоже всплывает: интервьюер часто открывает GitHub прямо во время звонка.

## Теория

### Как на самом деле смотрят профиль

Наём обычно идёт в три фильтра, и у каждого свой читатель:

```
Рекрутер / sourcer        Нанимающий инженер          Интервьюер
(20–60 сек, не пишет код) (2–5 мин, пишет код)        (перед звонком, 10 мин)
 ─ заголовок               ─ закреплённые репо          ─ конкретный проект
 ─ ключевые слова          ─ README: что, как, цифры    ─ код, коммиты, тесты
 ─ последняя роль/опыт     ─ схема архитектуры          ─ вопросы «почему так»
 ─ локация/формат          ─ есть ли evals/тесты
```

Отсюда главное правило: **каждый уровень должен работать без следующего**. Рекрутер, который не откроет ни одного репозитория, должен из заголовка и первых строк понять «AI / Backend Engineer, Python + TypeScript, RAG, агенты, evals». Инженер, который откроет один репозиторий, должен за минуту увидеть цифры качества. Это тот же принцип, что у API: публичный контракт понятен без чтения реализации.

### Рекрутеры ищут по ключевым словам

LinkedIn Recruiter и внутренние ATS — это, по сути, полнотекстовый поиск с фильтрами. Если в профиле нет слов «LLM», «RAG», «Python», ты не попадёшь в выдачу, как бы хорош ни был код. Поэтому ключевые слова должны стоять в трёх местах: заголовок (headline), раздел About и навыки (Skills). При этом список из 40 технологий выглядит как спам; лучше 10–15 честных, сгруппированных.

Типичный набор ключевых слов для твоего профиля:

| Группа | Слова |
|---|---|
| LLM | LLM, RAG, embeddings, tool calling, agents, MCP, evals, prompt engineering |
| Стек | Python, TypeScript, Node.js, Pydantic, FastAPI (если использовал), SQLite/PostgreSQL |
| LLM API | OpenAI-compatible API (DeepSeek, Ollama), Anthropic/OpenAI API — только те, что реально вызывал |
| Инфра | Docker, Langfuse/promptfoo, Ollama (local LLMs), vector DB (какую реально использовал) |
| Домен | real-time, WebSocket, fintech, trading systems |

### Позиционирование: одна фраза

Позиционирование — это ответ на вопрос «почему тебя, а не другого джуна в AI». У тебя редкая и сильная комбинация: ты построил боевую систему, которая сама торгует деньгами в real-time (socket.io, ccxt, восемь бирж, SQLite с миграциями, Telegram-бот, защита от «голой ноги»), и на её домене сделал LLM-проекты с evals. Формула:

> **Backend / AI Engineer.** Строю LLM-продукты с измеримым качеством: RAG, агенты, evals. До этого — real-time торговая система на TypeScript/Node (8 бирж, WebSocket, автоторговля).

Обрати внимание, чего здесь нет: «увлечённый», «быстро обучаюсь», «passionate about AI». Это слова, которые не несут информации. Вместо прилагательных — существительные и цифры.

### Что такое README профиля GitHub

Если создать публичный репозиторий с именем, совпадающим с твоим логином (`<username>/<username>`), его `README.md` показывается вверху страницы профиля. Это твоя «главная страница». Под ним — до шести закреплённых (pinned) репозиториев или gist'ов.

Хороший README профиля короткий — помещается на один экран:

```markdown
# Имя Фамилия — Backend / AI Engineer

Строю LLM-приложения с измеримым качеством (RAG, агенты, evals) на Python.
Бэкграунд: real-time торговая система на TypeScript/Node — WebSocket-стримы
цен с 8 бирж, автоторговля, Telegram-бот.

**Проекты**
- **exchange-docs-rag** — RAG по документации API бирж с цитатами;
  recall@5 0.62 → 0.87 после гибридного поиска и реранкера.
- **rag-evals-lab** — эксперименты с chunking, моделями и реранкером, таблица результатов.
- **trade-review-agent** — агент разбирает сделки (на синтетических данных), evals на 20 кейсах.
- **trading-assistant-bot** — Telegram-бот с tool calling поверх read-only копии базы.

**Стек:** Python, TypeScript, Node.js, Pydantic, DeepSeek + Ollama (OpenAI-compatible),
Claude/OpenAI для сравнения, Docker, SQLite.
**Пишу:** [статья на Хабре](...)  ·  **LinkedIn:** [...](...)
```

Цифры в примере — плейсхолдеры: ставь свои реальные, из evals глав недель 6–10. Чего избегать: анимированных баннеров, счётчиков посетителей, «GitHub stats» карточек, «трофеев» и стены значков технологий. Для инженера-ревьюера это шум, а иногда и минус: видно, что на оформление ушло больше времени, чем на содержание.

### Закреплённые репозитории

Закрепляй ровно то, что хочешь обсуждать на собеседовании. Порядок — по силе, а не по хронологии: самый впечатляющий первым (скорее всего, RAG с evals или агент). У каждого закреплённого репозитория должны быть:

- **description** (строка под названием) — одно предложение с глаголом и результатом;
- **topics** (теги репозитория): `llm`, `rag`, `evals`, `python` — по ним тоже ищут;
- README по шаблону из главы [12.2 · README, схемы и демо для всех проектов](AIL-50.md);
- никаких «Initial commit» и пустых веток как единственного содержимого.

Учебный репозиторий с `notes/` можно оставить публичным, но не закреплять: он показывает процесс, а не результат.

### Что можно публиковать про торговое приложение

Твоё арбитражное приложение — сильный аргумент, но его код и данные публиковать нельзя и не нужно: там ключи в `.env`, история сделок, балансы, логика, которая является твоим преимуществом. В профиле его описывают словами: что делает, масштаб, технические решения. Если хочешь показать код — сделай отдельный маленький публичный пример (например, MCP-сервер к **синтетической** базе той же схемы). Правило из всей книги действует и здесь: в публичном портфолио только фейковые данные, никаких реальных сделок, балансов, названий аккаунтов и скриншотов с цифрами счёта.

### LinkedIn: анатомия профиля

| Поле | Что писать | Ошибка |
|---|---|---|
| Фото | Лицо крупно, нейтральный фон, то же фото, что на GitHub | Фото с отдыха, логотип, пусто |
| Headline (заголовок) | «Backend / AI Engineer · Python, TypeScript · RAG, agents, evals» | «Ищу работу», «Open to work» вместо роли |
| About | 3 коротких абзаца: кто ты, что построил (с цифрами), что ищешь | Автобиография с детства |
| Experience | Торговая система как проект/самозанятость: что, стек, масштаб | Пустой период без объяснения |
| Projects / Featured | 4 проекта со ссылками на GitHub, статья | Ссылки на курсы как на «проекты» |
| Skills | 10–15 навыков, верхние 3 закреплены: LLM, Python, RAG | 50 навыков, включая Excel |
| Open to work | Включить с указанием ролей и формата (remote/релокация) | Публичная зелёная рамка без ролей |

В About у тебя первая строка видна без клика «ещё» — в неё ставь позиционирование. Пиши на английском: LinkedIn — международная площадка, а русскоязычный рекрутер английский тоже прочтёт. Русская версия профиля возможна (LinkedIn поддерживает профиль на втором языке), но это необязательно.

### Единая идентичность

Одинаковые ник, фото, имя (в латинской транслитерации, одинаковой везде) и заголовок на GitHub, LinkedIn, Хабре, в Telegram для работы и в резюме. Это не косметика: рекрутер ищет тебя по имени, и разные транслитерации («Ivan Petrov» / «Ivan Petroff») превращают одного кандидата в трёх неизвестных. Профили должны ссылаться друг на друга по кругу: GitHub → LinkedIn, LinkedIn → GitHub и статья, статья → GitHub.

### Безопасность профиля

- Включи двухфакторную аутентификацию на GitHub и LinkedIn.
- В публичных репозиториях проверь историю коммитов на секреты (`.env`, ключи API): удалённый в последнем коммите ключ остаётся в истории. Если ключ когда-либо попадал в коммит — отзови его у провайдера, переписывать историю недостаточно.
- Включи в GitHub настройку скрытия личного email в коммитах (Settings → Emails → «Keep my email addresses private») и используй выданный `noreply`-адрес.

## DeepSeek и Ollama: как это сделать у нас

Кода в этой главе нет, меняется подача. Твои проекты собраны в основном на DeepSeek (облако, дёшево) и Ollama (локально, бесплатно, для твоих собственных данных). Прятать это не нужно и извиняться тоже: подавай как осознанный выбор.

- **Мультипровайдерность — это сила.** Строка вроде «Provider-agnostic: one OpenAI-compatible client; DeepSeek for cloud runs, local models via Ollama for private data; compared with Claude/OpenAI on the same eval set» показывает то, что ценят в AI Engineer: абстракцию над провайдером, контроль стоимости, приватность данных и сравнение моделей на evals, а не на ощущениях.
- **В вакансиях чаще всего Claude и OpenAI.** Проверь на 5–10 вакансиях, на которые реально будешь откликаться (подробный словарь вакансий соберёшь в главе [13.1 · Резюме](AIL-53.md)): если там «Anthropic/OpenAI API», а ты их ни разу не вызывал, не пиши их в профиль. Лучше прогони хотя бы один eval каждого проекта через Claude и через OpenAI (на синтетических данных, обычно это единицы долларов — посчитай по текущему прайсу) и положи результат в таблицу сравнения. Тогда ключевые слова честные, а у тебя есть что рассказать.
- **Приватность как аргумент.** «Real trading data never leaves my machine: local models via Ollama» — сильная строка, но только если это правда. DeepSeek по своей политике конфиденциальности хранит и обрабатывает данные в Китае (проверено в ноябре 2026), поэтому реальные данные шли только в Ollama, а в облако — синтетика.

| | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| Как часто в вакансиях | часто | часто | реже | реже; ищут как «local / self-hosted LLM» |
| Как писать в профиле | «Anthropic API», если вызывал | «OpenAI API», если вызывал | «DeepSeek (OpenAI-compatible API)» | «Ollama, local LLMs» |
| Что доказывает | знание основного стека рынка | то же | контроль стоимости, абстракция над провайдером | приватность, работа офлайн, self-hosted |
| К какому вопросу готовиться | «чем отличается от других API» | то же | «китайский провайдер — а данные?» | «насколько хуже качество и почему» |

1. Открой https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/managing-your-profile-readme → прочитай целиком (≈10 мин). Обрати внимание: репозиторий должен быть публичным, с именем ровно как логин, и с `README.md` в корне.
2. Открой https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/pinning-items-to-your-profile → (≈5 мин). Возьми: максимум шесть закреплений, порядок меняется перетаскиванием.
3. Открой 5–7 профилей AI-инженеров, которые тебе нравятся (найди через авторов статей из глав про evals и RAG, например Eugene Yan, Hamel Husain, Jason Liu — по их сайтам есть ссылки на GitHub/LinkedIn) (≈30 мин). Для каждого запиши: заголовок, первую строку About, что закреплено. Цель — увидеть, как мало текста у сильных профилей.
4. Открой https://www.techinterviewhandbook.org/ → раздел про резюме и LinkedIn, если найдёшь его в меню (≈20 мин). Возьми правило «результат + цифра» — оно же пригодится в главе [13.1 · Резюме](AIL-53.md).
5. Проверь в справке LinkedIn (Help Center, поиск по «Open to work» и «profile in another language») текущие настройки видимости (≈10 мин): интерфейс меняется, поэтому сверяйся со справкой, а не с чужими гайдами.
6. Открой https://api-docs.deepseek.com/quick_start/pricing и https://docs.ollama.com/api/openai-compatibility (≈10 мин). Не учить, а свериться: имена моделей, которые ты упоминаешь в профиле и README, ещё актуальны, а формулировка «OpenAI-compatible» верна для обоих.

## На что обратить внимание

- **Секреты в истории.** Перед тем как сделать учебные репозитории публичными, пройди историю: `git log -p | grep -iE "api[_-]?key|sk-|secret"` — грубо, но ловит очевидное. Есть специализированные сканеры секретов (gitleaks, trufflehog), но это сторонний код: по твоему правилу — карантин и проверка перед установкой.
- **Реальные данные в демо.** Скриншоты Telegram-бота с настоящими PnL, названиями форм и балансами — утечка. Перегенерируй на синтетической базе.
- **Профиль «в процессе».** Пустой README профиля хуже, чем его отсутствие. Делай всё за один заход.
- **Overclaiming.** Не пиши «Senior AI Engineer» и «production LLM systems serving millions», если это учебные проекты. На собеседовании это раскрывается за пять минут. Честная формулировка «built and evaluated» сильнее.
- **Английский.** Одна грамматическая ошибка в заголовке заметнее, чем десять в коде. Прогони тексты через LLM с просьбой исправить только ошибки, не стиль.
- **Активность коммитов.** Зелёный график сам по себе ничего не значит, но 13 недель учёбы дают честную активность — не переписывай историю ради красоты.

## Практика

- [ ] **Инвентаризация.** Выпиши в `notes/portfolio.md` четыре проекта: название репозитория, одна фраза «что делает», одна главная цифра (из evals или стоимости), ссылка.
- [ ] **Аудит секретов и данных.** Для каждого из четырёх репозиториев: проверь `.gitignore` (там `.env`, `*.db`), историю коммитов на ключи, отсутствие реальных данных сделок (только синтетика). Результат — галочка напротив каждого репо в `notes/portfolio.md`.
- [ ] **Провайдеры.** Для каждого проекта допиши в `notes/portfolio.md`, на каких моделях он реально работал (DeepSeek, какая модель в Ollama, Claude/OpenAI для сравнения) и на каких данных (в облако — только синтетика, реальные — только локально). Если Claude или OpenAI ни разу не вызывал, сделай хотя бы один eval-прогон на каждом, прежде чем упоминать их в профиле.
- [ ] **Позиционирование.** Напиши три варианта фразы-позиционирования на английском (до 25 слов). Попроси LLM сыграть рекрутера, который за 10 секунд решает «звать или нет», и объяснить выбор. Выбери одну.
- [ ] **README профиля.** Создай репозиторий `<username>/<username>`, напиши README по скелету из «Теории» (на английском, один экран). Проверь в браузере в светлой и тёмной теме.
- [ ] **Закрепления.** Закрепи 4 проекта в порядке силы. Каждому — description с результатом и 3–5 topics.
- [ ] **LinkedIn.** Заполни фото, headline, About (3 абзаца), Experience (торговая система: что делает, стек, масштаб — без денег и названий аккаунтов), Featured (4 проекта + позже статья), Skills (10–15, три закреплены), Open to work с ролями AI Engineer / LLM Engineer / Backend Engineer.
- [ ] **Единая идентичность.** Один ник, одно фото, одна транслитерация имени. Ссылки: GitHub ↔ LinkedIn. Место для ссылки на статью оставь — добавишь в главе [12.3 · Статья на Хабр / LinkedIn](AIL-51.md).
- [ ] **Внешний взгляд.** Открой оба профиля в режиме инкогнито (LinkedIn — через «View as public»), засеки 30 секунд и запиши, что понял бы незнакомый человек.

## Готово, когда

- README профиля GitHub опубликован: кто ты, стек, 4 закреплённых проекта с одной цифрой каждый.
- LinkedIn заполнен: фото, headline AI / Backend Engineer, About, опыт, проекты, навыки, Open to work.
- Ник, фото и имя совпадают везде; профили ссылаются друг на друга.
- В публичных репозиториях нет секретов и реальных торговых данных.

## Ответы

1. **b.** Публичный репозиторий `<username>/<username>` с `README.md` в корне — особый случай, который GitHub показывает вверху профиля.
2. Рекрутеры ищут через поиск LinkedIn/ATS по полям профиля; до кода они доходят только если профиль нашёлся. Текст репозиториев читает уже инженер, а не поиск.
3. **b.** До шести репозиториев или gist'ов.
4. Ни одного слова о роли, стеке или результате — только прилагательные. Поиск по «LLM», «Python», «RAG» его не найдёт; лучше «Backend / AI Engineer · Python, TypeScript · RAG, agents, evals».
5. Нет: ключ остаётся в истории git и, возможно, уже скопирован ботами, сканирующими GitHub. Отзови ключ у провайдера и выпусти новый; чистка истории — второй шаг, не замена.
6. **c.** Первым — то, что лучше всего доказывает нужные для роли навыки и что ты хочешь обсуждать на собеседовании.
7. Это реальные финансовые данные: объёмы, PnL, используемые биржи и пары, иногда косвенно баланс. Правило портфолио — только синтетика.
8. Рекрутер ищет кандидата по имени на разных площадках; разные написания разрывают связь между профилями, статьёй и резюме.
9. Счётчики и карточки статистики — шум, 42 значка — стена без смысла, эмодзи-заголовок отвлекают. Нет главного: кто ты, что построил, цифры.
10. Писать: что делает система (арбитраж funding/спреда), масштаб (8 бирж, real-time WebSocket, автоторговля, Telegram-отчёты), технические решения (миграции, защита от одноногих позиций). Не писать: суммы и PnL, конкретные аккаунты/ключи/объёмы, детали стратегии, которые являются преимуществом.
11. **b.** Ключевые слова становятся честными, а сравнение провайдеров на одном eval-наборе — сильный материал для профиля и интервью. Вариант a — overclaiming, который раскроется на первом вопросе.
12. Список имён без контекста: непонятно, что ты с ними делал, и, скорее всего, часть ты не вызывал. Лучше: какой провайдер для чего (облако / локально) и чем закончилось сравнение.
13. Например: «Provider-agnostic LLM apps: DeepSeek for cloud runs, local models via Ollama for private data, benchmarked against Claude/OpenAI on the same evals». Главное — подать как выбор (стоимость, приватность, сравнение), а не как вынужденную замену.
