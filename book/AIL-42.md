# 10.3 · Проект 4: evals агента на 20 случаях  (AIL-42)

> **Неделя 10** · Агенты · ⏱ ~4–5 ч · Проект

## Зачем это AI-инженеру

Агентов тоже надо измерять, и это сложнее, чем RAG: у агента есть не только итоговый ответ, но и **траектория** — какие инструменты, сколько шагов, сколько денег и времени. Фраза «у меня 16 из 20 правильных причин при средней стоимости X и 7 шагах, вот разбор 5 провалов» в README и на собеседовании стоит больше, чем любая демонстрация. Основы evals (golden set, метрики, LLM-as-judge) ты разбирал в главах про evals RAG; здесь — что добавляется для агентов.

## Теория

### Что измерять у агента

```
             ┌─ outcome:    is the final answer right?
agent run ───┼─ trajectory: how did it get there? (steps, tools, errors, loops)
             └─ cost:       tokens, money, wall-clock time, limit hits
```

| Группа | Метрика | Как считать |
|---|---|---|
| Результат | **Верная причина** | `report.cause_category == expected` (точное совпадение) |
| Результат | Качество объяснения | LLM-as-judge по рубрике или твоя оценка 0–2 |
| Результат | Валидность доказательств | Доля `evidence`, прошедших проверку кодом |
| Результат | Честность | Если данных нет — ответил ли `unknown`/`gaps`, а не выдумал |
| Траектория | Число шагов | Из JSONL-лога |
| Траектория | Ошибки инструментов | Число `is_error` |
| Траектория | Повторы | Одинаковые вызовы с одинаковыми аргументами |
| Траектория | Упор в лимит | Статус `STOPPED: ...` |
| Стоимость | Токены in/out | Сумма `usage` по шагам |
| Стоимость | Деньги | Токены × текущий прайс модели (бери со страницы цен провайдера, не по памяти) |
| Стоимость | Время | wall-clock от старта до отчёта |

### Golden set: 20 случаев с известной причиной

Тебе повезло: в базе есть `closedBy`, а это готовая разметка «кто закрыл». Но для хорошего набора нужно больше:

1. **Разнообразие.** Не 20 `auto`. Целевой состав, например: 8 `auto`, 4 `manual`, 3 `liquidation`/`hedge`, 2 `naked`, 1 `adl` (если есть), 2 случая, где логов уже нет (ожидаемый ответ — честное «недостаточно данных»). Если каких-то категорий в реальности нет — так и запиши, не выдумывай.
2. **Ожидаемый ответ** — не только категория, но и 1–3 ключевых факта, которые должен найти агент («SHORT нога на bybit ликвидирована в 14:02, LONG закрыта как hedge через 3 с»). Эти факты ты подтверждаешь сам по данным.
3. **Заморозка данных.** Сделай один снимок базы (`VACUUM INTO`) и копию логов специально для evals и больше их не меняй. Иначе результаты разных прогонов несравнимы.

```json
{"id": "case-07", "form_id": "abc123", "position_number": 4,
 "expected_category": "hedge_after_liquidation",
 "key_facts": ["SHORT leg on bybit closedBy=liquidation", "LONG leg closedBy=hedge within seconds"],
 "logs_available": true, "notes": "verified by hand 2027-01-21"}
```

### Проблема утечки ответа

Агент может просто прочитать `closedBy` и угадать категорию — тогда метрика «верная причина» мерит чтение поля, а не расследование. Сделай **два режима** прогона:

- **open** — всё как в продакшене;
- **blind** — инструмент `get_position` маскирует `closedBy` (флаг в MCP-сервере только для evals). Агент должен восстановить причину по логам, спредам и ценам.

Разница между режимами покажет реальную «исследовательскую» способность агента. Это честный и интересный результат для README.

### Недетерминизм: несколько прогонов

Одинаковый вход даёт разные траектории. Прогоняй каждый случай **k раз** (k = 3 — разумный компромисс по деньгам) и считай:

- **средний success rate** по всем прогонам;
- **pass@k** — хотя бы один из k прогонов верен (оптимистично: «может ли агент вообще»);
- **pass^k** — все k прогонов верны (пессимистично: «можно ли на него положиться»). Эта метрика популяризирована бенчмарком τ-bench; для агента, которому ты доверяешь выводы, она важнее.

```python
# metrics.py — illustrative
def pass_at_k(results: list[bool]) -> bool:
    return any(results)

def pass_hat_k(results: list[bool]) -> bool:  # "pass^k"
    return all(results)
```

### LLM-as-judge для объяснений

Категорию сравнивает код. Качество объяснения — судья-LLM по **узкой рубрике** с ключевыми фактами из golden set:

```text
You grade a trade post-mortem report against reference facts.
Reference facts: {key_facts}
Report: {report_json}
Score each, 0 or 1:
- covers_facts: every reference fact is stated or clearly implied
- no_contradiction: nothing in the report contradicts the reference facts
- no_unsupported: no claim of a specific event without evidence
Return JSON: {"covers_facts": 0|1, "no_contradiction": 0|1, "no_unsupported": 0|1, "reason": "..."}
```

Правила из главы про LLM-as-judge остаются: бинарные критерии лучше шкал 1–10; проверь судью на 5 случаях руками; судья — другая или более сильная модель, чем агент, если возможно.

### Разбор траекторий (error analysis)

Числа говорят «сколько», траектории — «почему». Для 5 неудачных прогонов прочитай JSONL целиком и классифицируй провал:

| Категория провала | Признак |
|---|---|
| Не тот инструмент | Искал в логах то, что есть в базе, или наоборот |
| Плохие аргументы | Не то окно времени (часто — путаница UTC/локальное), не тот символ |
| Ранняя остановка | Принял первую гипотезу, не проверил альтернативу |
| Зацикливание | Повтор одного вызова, упор в лимит шагов |
| Потеря контекста | После compaction забыл факт и противоречит себе |
| Выдумка | Утверждение без доказательства или с несуществующей ссылкой |
| Ошибка данных/инструмента | Инструмент вернул неверное (баг в PnL, в фильтре дат) — это баг твоего кода, не агента |

Каждой категории — конкретное исправление: описание инструмента, промпт, новый инструмент, лимит, фикс в сервере. После исправлений — **полный повторный прогон**, чтобы не сломать то, что работало (регрессия).

## DeepSeek и Ollama: как это сделать у нас

Метрики и методика не зависят от провайдера. Зависят три вещи: **какую модель можно пустить на какие данные**, **кто будет судьёй** и **что такое «стоимость»**. Факты о провайдерах проверены 13 ноября 2026.

### Два набора, две политики

| Набор | Агент | Судья | Где данные |
|---|---|---|---|
| **Реальный** (20 случаев из твоей копии базы) | Ollama `qwen3:4b` | Код + ты сам; LLM-судья — только локальный (`qwen3:8b`, запускается при закрытых программах и **невзведённой автоторговле**) | Только твой Mac, `OLLAMA_NO_CLOUD=1` |
| **Фейковый** (20 случаев: расширь фейковую базу из главы 9.5 — по сути это начало генератора из главы 10.4) | `qwen3:4b` и `deepseek-flash` (по желанию — Claude/OpenAI) | `deepseek-v4-pro` | Можно в облако — данных нет |

Правило «судья сильнее судимого» на реальном наборе выполнить трудно: на M2 с 8 ГБ модель сильнее `qwen3:8b` не запустить, а облачный судья увидел бы твои сделки. Поэтому на реальном наборе основная оценка — **код** (категория, проверка доказательств) и **твоя ручная оценка** 0–2; локальный судья — вспомогательный, и его согласие с тобой ты обязан измерить на 5–10 отчётах. На фейковом наборе судья — `deepseek-v4-pro`: сильнее и `qwen3:4b`, и `deepseek-flash` (но судить им же `deepseek-v4-pro`-агента не стоит — модель склонна хвалить своё).

### Судья на DeepSeek: что учесть

- **JSON:** только `response_format={"type": "json_object"}`; слово «json» и пример ответа — в промпте; пустой `content` возможен — повтор.
- **Thinking включён по умолчанию** и полезен судье (лучше обоснование), но `temperature` в этом режиме игнорируется — повторяемость оценок проверяй повторными прогонами, а не `temperature=0`. Если нужна детерминированность — выключи thinking и ставь `temperature=0`.
- **Кэш:** рубрика и инструкции — в начале промпта, отчёт — в конце. Тогда на 120 оценках начало попадает в автоматический кэш (`prompt_cache_hit_tokens`).

### Стоимость: деньги у DeepSeek, время у Ollama

| | Claude / OpenAI | DeepSeek | Ollama |
|---|---|---|---|
| $ / случай | Токены × прайс | Токены × прайс **с учётом кэша и времени суток**: попадание в кэш в десятки раз дешевле промаха, вне пика (вне 01:00–04:00 и 06:00–10:00 UTC по будням) — вдвое дешевле | 0 $ |
| Что мерить вместо денег | — | — | Время на случай (wall-clock), пиковая память (`ollama ps`, «Мониторинг системы») |
| Как считать | `usage` | `prompt_cache_hit_tokens` × цена hit + `prompt_cache_miss_tokens` × цена miss + `completion_tokens` × цена output | `eval_count`, `prompt_eval_count`, `total_duration` в нативном API |

Цены бери со [страницы DeepSeek](https://api-docs.deepseek.com/quick_start/pricing) в день прогона и пиши дату рядом с таблицей. На ноябрь 2026 для `deepseek-flash` в пик: $0.3 / 1M входных (промах), $0.006 / 1M (попадание), $1.2 / 1M выходных.

**Время на Ollama — реальное ограничение.** 20 случаев × 3 прогона × 2 режима = 120 запусков агента на 4B-модели могут занять часы. Запускай ночью или частями — но не тогда, когда взведена автоторговля: прогон грузит память и CPU/GPU Mac. Начни с k=1 на всех 20, k=3 — на отобранных.

### Чего ожидать от сравнения моделей

Таблица из теории получает столбец «Модель» и «Набор». Ожидай, что `qwen3:4b` проиграет облачным моделям прежде всего в **траектории** (больше ошибок аргументов, повторов, упоров в лимит) и в **валидности доказательств**, а не только в итоговой категории. Это ценный результат для README: «локальная 4B-модель находит верную причину в X из 20 при pass^3 = Y; облачная — Z, но её нельзя пускать на реальные данные» — это честный разговор о компромиссе приватности и качества.

## На что обратить внимание

- **20 случаев — это мало.** Разница 15/20 против 16/20 — шум. Не делай громких выводов из ±1 случая; говори о порядках и о типах провалов.
- **Данные должны быть заморожены**, иначе ты сравниваешь разные задачи.
- **Утечка ответа** через `closedBy` — без blind-режима метрика переоценивает агента.
- **Кэш и стоимость.** Prompt caching снижает цену; укажи в таблице, был ли он включён.
- **Ошибка в golden set** встречается чаще, чем кажется. Когда агент «ошибся», сначала проверь разметку.
- **Не подгоняй промпт под 20 случаев.** Если правишь промпт по конкретному провалу, держи 4–5 случаев отложенными и проверяй на них.
- **Evals тоже только читают.** Прогон 20×3×2 = 120 запусков агента — это 120 раз по копии базы; ни одного обращения к живой базе или бирже.

## Ответы

1. Кроме результата, меряются траектория (шаги, ошибки инструментов, повторы, упор в лимиты) и стоимость (токены, деньги, время).
2. Агент может просто прочитать `closedBy`. Нужен blind-режим, где поле замаскировано, и проверка ключевых фактов, а не только категории.
3. pass@k — способен ли агент решить хотя бы иногда; pass^k — решает ли надёжно каждый раз. Для доверия к выводам важнее pass^k.
4. A: pass@3 = да, pass^3 = да. B: pass@3 = да, pass^3 = нет.
5. Распределения с длинным хвостом: один зациклившийся прогон резко сдвигает среднее, медиана устойчива.
6. Шкала 1–10 без критериев и без эталонных фактов: оценки нестабильны и неинтерпретируемы. Нужны бинарные критерии с референсом.
7. Ошибка данных/инструмента — баг в коде сервера (обработка UTC), а не провал рассуждений агента; исправлять сервер и описание формата времени.
8. b.
9. Чтобы все прогоны и сравнения до/после работали на одинаковых данных; иначе изменения метрик могут объясняться изменением данных.
10. Проверяют честность: агент должен сказать «недостаточно данных», а не выдумать события; это ловит LLM09.
11. Судья видит отчёт и ключевые факты — это реальные данные о сделках, а DeepSeek работает на серверах в Китае. На реальном наборе: код + ручная оценка + локальный судья (`qwen3:8b`) с измеренным согласием; сильный облачный судья — только на фейковом наборе.
12. `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens` по своим ценам плюс `completion_tokens` по цене выхода; цена зависит от модели и от времени суток (вне пика вдвое дешевле). Цены — со страницы в день прогона, с датой.
13. На 20 случаях разница 5 — заметная, но с шумом; правильный вывод — облачная модель лучше на фейковых данных, но на реальные данные её пускать нельзя, поэтому для реальных случаев либо улучшать агента под 4B (инструменты, схемы, лимиты), либо принимать меньшую надёжность и проверять выводы руками.
