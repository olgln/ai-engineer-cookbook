# 6.2 · Синтетические данные для evals  (AIL-61)

> **Неделя 6** · Evals · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Вручную придумать 100 хороших вопросов по документации четырёх бирж — день скучной работы, и вопросы получатся однобокими: ты спросишь о том, что сам помнишь. Модель за минуты генерирует черновик, а ты как эксперт его проверяешь и чистишь. Генерация синтетических данных — стандартный приём в индустрии и частая тема на собеседованиях («как вы собрали тестовый набор, когда пользователей ещё нет?»).

## Теория

### Идея: модель пишет черновик, человек принимает решение

Синтетический набор — это вопросы и эталонные ответы, которые сгенерировала модель по твоим же данным. Схема для RAG:

```
 случайный чанк ──► модель-генератор ──► кандидат {вопрос, ответ, цитата}
                                              │
                                              ▼
                                    автоматические фильтры
                               (дубли, копипаст, «неотвечаемые»)
                                              │
                                              ▼
                                    ручная проверка (ты)
                                              │
                                              ▼
                                   evals/dataset.jsonl
```

Ключевое слово — **черновик**. Ни один синтетический вопрос не попадает в набор без твоего «да». Модель не знает, какие вопросы важны для пользователя, и регулярно ошибается в эталоне.

### Почему «случайный чанк» и почему этого мало

Если выбрать чанк случайно, модель гарантированно знает, где лежит ответ: у кандидата сразу есть `source_chunk_id`. Это удобно для метрик поиска (hit rate). Но у подхода три известных перекоса:

1. **Копирование формулировок.** Модель берёт фразу из чанка и превращает её в вопрос: «Какой rate limit у endpoint /v5/order/create для UTA?» Векторный и особенно BM25-поиск находят такой чанк почти всегда, и hit rate завышен. Реальный пользователь спросит: «Сколько ордеров в секунду я могу отправлять на Bybit?»
2. **Один чанк — один вопрос.** Сравнительные («чем отличается X у OKX и Bybit») и многошаговые вопросы так не получаются, а они самые трудные.
3. **Нет вопросов «вне документации».** Хорошая система должна уметь сказать «не нашёл», и это тоже надо проверять.

Поэтому генератор строится вокруг **измерений разнообразия**, а не только вокруг чанка.

### Измерения разнообразия

Hamel Husain в своих статьях предлагает задавать набор измерений и генерировать вопросы по их комбинациям. Для твоего ассистента по докам бирж:

| Измерение | Значения |
|---|---|
| Тип вопроса | factual, comparative, multi_hop, unanswerable |
| Сложность | easy (ответ в одной фразе), medium (надо собрать из абзаца), hard (несколько мест, условия) |
| Персона | новичок в API, опытный бот-разработчик, трейдер без кода |
| Стиль | точный технический, разговорный, с опечаткой, на русском |
| Биржа | bybit, okx, binance, gate |

Ты выбираешь комбинацию (например, `comparative / hard / бот-разработчик / разговорный / okx+bybit`), подбираешь подходящие чанки и просишь модель сгенерировать вопрос под эту комбинацию. Так распределение вопросов задаёшь ты, а не модель.

### Как получить каждый тип

- **factual**: один случайный чанк → вопрос, на который он отвечает.
- **comparative**: тема (например, «funding rate interval») → по чанку с двух бирж (найди их поиском по теме или по заголовкам) → вопрос, требующий обоих.
- **multi_hop**: два чанка одной биржи, где ответ требует связать факты («какой endpoint вернёт позицию и сколько запросов в секунду к нему можно сделать?»).
- **unanswerable**: проще всего руками. Синтетически: дай модели чанк и попроси вопрос о *соседней* теме, которой в чанке нет, затем проверь поиском по всему индексу, что ответа действительно нет нигде. Без этой проверки «неотвечаемый» вопрос окажется отвечаемым.

### Перефразирование против копипаста

Две защиты, и лучше обе:

1. **В промпте генератора**: «Сформулируй вопрос так, как его задал бы пользователь, не видевший документацию. Не используй названия параметров и фразы из текста, если пользователь их не знал бы».
2. **Фильтр на пересечение**: посчитай, какая доля слов вопроса встречается в чанке, или длину самой длинной общей подстроки. Слишком высокое пересечение — на перефразирование (второй вызов модели) или в мусор.

Простой фильтр пересечения:

```python
import re

def tokens(text: str) -> set[str]:
    # lowercase words of 3+ chars, works for English and Russian
    return {t for t in re.findall(r"\w{3,}", text.lower())}

def overlap_ratio(question: str, chunk: str) -> float:
    q = tokens(question)
    if not q:
        return 0.0
    return len(q & tokens(chunk)) / len(q)

# rule of thumb, tune by looking at examples:
# > 0.7 means the question mostly copies the chunk
```

Порог не бери с потолка: посмотри на 20 кандидатов с разным `overlap_ratio` и реши, где начинается копипаст.

### Фильтр дублей

Модель любит повторяться: из 50 кандидатов про rate limits 10 окажутся одним вопросом. Дубли ловятся эмбеддингами, которые у тебя уже есть с недели 4 ([AIL-18](AIL-18.md)): если косинусное сходство двух вопросов выше порога (начни с 0,9 и проверь глазами), оставь один.

```python
import numpy as np

def dedup(questions: list[str], vectors: np.ndarray, threshold: float = 0.9) -> list[int]:
    # vectors are L2-normalized, so dot product == cosine similarity
    kept: list[int] = []
    for i in range(len(questions)):
        if all(float(vectors[i] @ vectors[j]) < threshold for j in kept):
            kept.append(i)
    return kept
```

### Фильтр «слишком простых»

«Слишком простой» значит одно из двух:
- **Тривиальный для поиска**: вопрос почти дословно совпадает с заголовком чанка. Ловится фильтром пересечения.
- **Не требует документации**: модель отвечает верно без контекста («Что такое funding rate?»). Такой вопрос проверяет знания модели, а не твой RAG. Можно оставить пару для покрытия, но не половину набора. Проверка: спроси модель без контекста и дай судье сравнить с эталоном.

### Проверка эталона

Ответ генератора тоже может быть неверным: модель додумала, округлила, перепутала единицы. Защита:
- Генератор обязан вернуть **цитату** (`evidence`): дословный кусок чанка, на котором основан ответ. Код проверяет, что цитата действительно есть в чанке (после нормализации пробелов). Не нашлась — кандидат отбраковывается.
- Ты при ручной проверке сверяешь ответ с цитатой и при сомнении открываешь исходную страницу.

### Структура кандидата

Сразу генерируй в формате, совместимом с набором из [AIL-28](AIL-28.md):

```json
{"id": "syn-0042", "question": "...", "reference_answer": "...",
 "evidence": "exact quote from the chunk", "source_chunk_ids": ["bybit-...#3"],
 "source_urls": ["https://..."], "exchange": ["bybit"], "type": "factual",
 "difficulty": "medium", "origin": "synthetic", "reviewed": false,
 "generator": {"model": "...", "prompt_version": "gen-v1"}}
```

Поле `evidence` важнее, чем кажется: в [AIL-32](AIL-32.md) ты будешь менять чанкинг, ID чанков поменяются, а цитата останется и по ней можно будет найти правильный чанк в новом индексе.

### Промпт генератора

Пример (иллюстративный; вызов SDK см. в главах про structured output недели 2–3 и в текущей документации провайдера):

```python
GEN_PROMPT = """You create test questions for a search assistant over crypto exchange API docs.

Below is a fragment of {exchange} documentation (source: {url}).
<chunk>
{chunk}
</chunk>

Write ONE question of type "{qtype}" and difficulty "{difficulty}",
as it would be asked by: {persona}. Style: {style}.

Rules:
- The question must be answerable from the fragment alone.
- Do not copy phrases or parameter names from the fragment unless this persona would know them.
- The question must make sense without seeing the fragment (no "in this section").
- The answer must be short and contain the key fact (numbers, names, units).
- "evidence" must be an EXACT quote from the fragment that supports the answer.

Return JSON only:
{{"question": "...", "reference_answer": "...", "evidence": "..."}}
"""
```

Для генерации подойдёт сильная модель: ошибка в эталоне стоит дороже, чем лишние центы. Конкретные модели и цены смотри в документации провайдера на момент работы.

### Ручная проверка

Для каждого кандидата ответь на четыре вопроса:
1. Задал бы так реальный пользователь? Если нет — перепиши или выбрось.
2. Эталон верен и полон? Сверь с цитатой и страницей.
3. Вопрос однозначен? «Какой лимит?» без указания биржи — плохой вопрос.
4. Тип и сложность размечены правильно?

Удобно проверять в простом цикле в терминале: показать кандидата, нажать `y` / `n` / `e` (редактировать). Или в таблице: выгрузить в CSV, проверить, загрузить обратно. Запиши, сколько кандидатов прошло: доля брака сама по себе полезна (если отбраковано 60%, промпт генератора плохой).

## DeepSeek и Ollama: как это сделать у нас

Скелет выше написан на Anthropic SDK; оставь его как вариант «для сравнения». Основной генератор у нас — DeepSeek через OpenAI SDK, эмбеддинги для фильтра дублей — Ollama, локально и бесплатно. Документация бирж публичная, поэтому отправлять чанки в DeepSeek можно; свои сделки и логи — нет (см. «На что обратить внимание»). Факты сверены в ноябре 2026 по [api-docs.deepseek.com](https://api-docs.deepseek.com) и [docs.ollama.com](https://docs.ollama.com).

### Генератор на DeepSeek

```python
# evals/generate.py — DeepSeek variant (illustrative; check current model ids in the docs)
import json, os
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],  # from env / dotenv file in .gitignore
                base_url="https://api.deepseek.com")
MODEL = os.environ.get("GEN_MODEL", "deepseek-v4-pro")

def generate(chunk: dict, qtype: str, difficulty: str, persona: str, style: str,
             retries: int = 3) -> dict | None:
    prompt = GEN_PROMPT.format(exchange=chunk["exchange"], url=chunk["url"], chunk=chunk["text"],
                               qtype=qtype, difficulty=difficulty, persona=persona, style=style)
    for _ in range(retries):
        resp = client.chat.completions.create(
            model=MODEL,
            messages=[{"role": "user", "content": prompt}],
            response_format={"type": "json_object"},  # prompt must contain the word "json" and an example
            max_tokens=4000,  # generous: in thinking mode reasoning also spends output tokens
        )
        text = (resp.choices[0].message.content or "").strip()
        if not text:
            continue  # JSON mode may return blank content; retry
        try:
            data = json.loads(text)
        except json.JSONDecodeError:
            continue
        if normalize(data.get("evidence", "")) not in normalize(chunk["text"]):
            return None  # hallucinated evidence
        data["generator"] = {"model": resp.model, "prompt_version": "gen-v1"}  # model actually served
        return data
    return None
```

Что здесь важно именно для DeepSeek:

- **JSON mode — это `json_object`, а не схема.** Модель обязана вернуть валидный JSON, но поля никто не проверяет. Поэтому `GEN_PROMPT` уже содержит пример структуры и слово «JSON» (без них JSON mode DeepSeek не работает как надо), а наличие полей проверяй сам (Pydantic из главы [1.3 · Python: uv, async, Pydantic](AIL-2.md)). Документация предупреждает: иногда `content` приходит пустым, поэтому ретрай.
- **Режим thinking включён по умолчанию.** Для генерации это скорее плюс: модель «думает», прежде чем выбрать цитату, и эталон точнее. Но temperature в этом режиме не действует, так что разнообразие обеспечивают измерения (тип, персона, стиль), а не температура. Хочешь управлять temperature — выключи рассуждения: `extra_body={"thinking": {"type": "disabled"}}`.
- **Какая модель.** Ошибка в эталоне дороже лишних центов, поэтому генератор — `deepseek-v4-pro`, а «дешёвые» шаги (перефразирование, проверка «отвечает без контекста») — `deepseek-flash`. Порядок цен на ноябрь 2026: 60 кандидатов по ~1500 входных и ~1000 выходных токенов (с рассуждением) на Pro — меньше $0,5 в часы пик и вдвое меньше вне пика. Пересчитай по [странице цен](https://api-docs.deepseek.com/quick_start/pricing).
- **Записывай `resp.model`.** DeepSeek переназначает имена: `deepseek-flash` сейчас обслуживает версия V4.1-Flash-1017, старые имена перенаправляются на новые модели. Без записи через месяц не поймёшь, какой моделью сгенерирован вопрос.

### Генератор на Ollama: бесплатно, но проверяй брак

Локальная модель годится как бесплатный генератор, а `format` с JSON-схемой в нативном API Ollama ограничивает ответ схемой надёжнее, чем `json_object` у DeepSeek:

```python
# illustrative; pull the model first: ollama pull <tag> (official library at ollama.com)
import ollama
from pydantic import BaseModel

class Candidate(BaseModel):
    question: str
    reference_answer: str
    evidence: str

resp = ollama.chat(
    model="qwen3:4b",  # 4B class fits 8 GB next to the arbitrage app; 7-8B only with everything else closed
    messages=[{"role": "user", "content": prompt}],
    format=Candidate.model_json_schema(),
    options={"temperature": 0.8, "seed": 42},  # temperature and seed are honored here
)
cand = Candidate.model_validate_json(resp.message.content)
```

Схема гарантирует форму, но не правду. У тебя Apple M2 с 8 ГБ памяти, и на нём же работает арбитражное приложение. Реально это модели класса 4B (например, `qwen3:4b`); 7–8B — только закрыв всё остальное и не держа автоторговлю включённой; 14B и больше не помещаются. Модель 4B заметно чаще ошибается в эталоне и копирует формулировки, поэтому локальный генератор здесь — учебное сравнение, а не основной путь. Сравни долю принятых кандидатов у двух генераторов на 20 штуках — это и будет ответ, стоит ли экономия. Учти контекст: на Mac с памятью меньше 24 ГБ Ollama по умолчанию даёт модели 4k токенов; длинный чанк плюс промпт может молча обрезаться. Проверь `ollama ps` (колонка CONTEXT); поднимать `OLLAMA_CONTEXT_LENGTH` на 8 ГБ можно лишь осторожно, контекст тоже ест память (подробнее в главе [6.4 · Скрипт оценки: retrieval + faithfulness](AIL-29.md)).

### Эмбеддинги для фильтра дублей — только локально

Эндпоинта эмбеддингов в официальной документации DeepSeek я не нашёл (ноябрь 2026); у Anthropic своих эмбеддингов тоже нет. Поэтому эмбеддинги — через Ollama (или sentence-transformers, если ты так строил индекс на неделе 4):

```python
import numpy as np
import ollama

def embed(texts: list[str], model: str = "bge-m3") -> np.ndarray:
    # /api/embed returns L2-normalized vectors, so dot product == cosine similarity
    resp = ollama.embed(model=model, input=texts)
    return np.array(resp["embeddings"])

vectors = embed([c["question"] for c in candidates])
kept = dedup([c["question"] for c in candidates], vectors, threshold=0.9)
```

Вопросы у тебя смешанные (русский и английский), поэтому бери многоязычную модель эмбеддингов, например `bge-m3` из библиотеки Ollama (567M параметров, на 8 ГБ помещается без проблем). Если индекс Проекта 2 построен другой моделью, для поиска дублей это не страшно, но порог подбирай заново по примерам.

### Сравнение провайдеров для этой главы

| Что нужно | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| JSON с гарантией схемы | structured outputs (JSON-схема) / tool use | `response_format` с JSON-схемой | нет: только `json_object`, поля проверяй сам; обходной путь — strict-режим tool calling (beta, `base_url="https://api.deepseek.com/beta"`) | да: `format` с JSON-схемой |
| Разнообразие через temperature | да (с ограничениями у части моделей) | да, кроме reasoning-моделей | только с выключенным thinking | да, плюс `seed` |
| Свой эндпоинт эмбеддингов | нет | да | в документации не найден | да, `/api/embed` |
| Качество эталонов | высокое, дороже | высокое, дороже | высокое у Pro, центы за набор | ниже, больше брака; бесплатно |
| Куда уходят чанки | облако Anthropic | облако OpenAI | серверы в Китае | никуда |

Итог для практики: генератор `deepseek-v4-pro`, перефразирование и closed-book проверка на `deepseek-flash`, дубли на эмбеддингах Ollama. Claude или OpenAI — по желанию, для сравнения доли брака на тех же 20 комбинациях.

6. Открой [DeepSeek: JSON Output](https://api-docs.deepseek.com/guides/json_mode) и [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode) (≈15 мин). Обрати внимание на три требования JSON mode (слово «json», пример, достаточный `max_tokens`) и на пустой `content`.
7. Открой [Ollama: Structured outputs](https://docs.ollama.com/capabilities/structured-outputs) и [Ollama: Embeddings](https://docs.ollama.com/capabilities/embeddings) (≈15 мин): `format` с Pydantic-схемой и `ollama.embed`. Python-библиотеку `ollama` ставь с закреплённой версией в `requirements.txt`.

## На что обратить внимание

- **Копипаст завышает метрики поиска**, особенно BM25. Если hit rate на синтетике заметно выше, чем на ручных вопросах, вероятно, причина в этом. Считай метрики отдельно по `origin`.
- **Генератор путает биржи**: в чанке Gate он может «вспомнить» факт про Binance. Проверка цитаты это ловит.
- **Чанки-мусор** (оглавления, навигация, таблицы без контекста) дают бессмысленные вопросы. Отфильтруй их до генерации: слишком короткие, без предложений, только ссылки.
- **Смещение к началу документации.** Если сэмплировать чанки равномерно, а у Binance их в 3 раза больше, набор перекосится. Сэмплируй по бирже, потом по чанку.
- **Документация меняется.** Биржи переписывают доки. Храни дату скачивания и URL, чтобы потом понять, почему эталон «вдруг стал неверным».
- **Не отправляй в модель ничего приватного.** Здесь только публичная документация бирж. Свои сделки, ключи, данные из `arbitrage.db` в генератор не идут.
- **Синтетика не заменяет реальные вопросы.** Ручные вопросы из [AIL-28](AIL-28.md) остаются основой; синтетика их дополняет.
- **В DeepSeek не идёт ничего, кроме публичной документации.** Серверы DeepSeek в Китае. Если захочешь добавить вопросы «из опыта» арбитражного приложения, формулируй их как общие вопросы к докам, без своих позиций, объёмов, логов и ключей.
- **Пустой ответ в JSON mode DeepSeek** при `finish_reason="stop"` — документированное поведение, а не баг твоего кода. Ретрай, и не считай такие случаи «браком генератора».
- **Обрезанный чанк в Ollama.** При контексте 4k по умолчанию длинный чанк обрежется без ошибки, и модель сгенерирует вопрос по куску куска, а проверка `evidence` отбракует хорошие кандидаты. Смотри `ollama ps`.

## Ответы

1. Поиск (особенно лексический) находит такой чанк почти всегда, поэтому hit rate завышен и не отражает реальных пользователей, которые формулируют иначе.
2. Проверка, что эталон не выдуман (цитата должна реально быть в чанке), и устойчивость к смене чанкинга: по цитате можно найти правильный чанк в новом индексе.
3. Оси разнообразия (тип, сложность, персона, стиль, биржа), по комбинациям которых генерируются вопросы. Они задают распределение набора сознательно, вместо того чтобы модель генерировала однотипное.
4. **b.** Сравнительному вопросу нужны чанки с двух бирж на одну тему.
5. Что ответа действительно нет нигде в индексе (поиском и глазами), иначе вопрос окажется отвечаемым и эталон «не нашёл» будет неверен.
6. Посчитать эмбеддинги вопросов и выкинуть те, у которых косинусное сходство с уже принятым выше порога (порог подобрать по примерам).
7. Синтетические вопросы копируют формулировки чанков, поэтому поиск находит их легко. Считай метрики отдельно по `origin` и перефразируй.
8. 20 вопросов за раз дают повторы и деградацию к концу; нет типа, сложности и персоны; нет требования к формату (JSON) и цитате; нет запрета копировать текст; «diverse» без измерений ничего не гарантирует.
9. Для воспроизводимости и разбора: понять, откуда взялся вопрос, и перегенерировать набор тем же способом или сравнить версии промпта.
10. Иначе биржа с большей документацией займёт большую часть набора, и метрика будет описывать в основном её.
11. Он проверяет знания модели, а не поиск по документации. Пара таких вопросов допустима, но они не говорят о качестве RAG.
12. Документированное поведение JSON mode: если модель не смогла выдать валидный JSON, API может вернуть пустое содержимое. Сделать ретрай (и проверить, что в промпте есть слово «json», пример и хватает `max_tokens`).
13. `json_object` гарантирует только валидный JSON, а не нужные поля; JSON-схема в Ollama ограничивает ответ схемой. Поэтому на DeepSeek наличие и типы полей проверяются в коде (Pydantic), а пример структуры кладётся в промпт.
14. Локальной моделью эмбеддингов в Ollama (или sentence-transformers): эндпоинта эмбеддингов в документации DeepSeek нет, а локально это бесплатно и приватно. Для смеси русского и английского — многоязычная модель.
