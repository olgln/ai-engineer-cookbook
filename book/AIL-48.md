# 11.5 · Файнтюнинг: базовый пример LoRA  (AIL-48)

> **Неделя 11** · Продакшен · ⏱ ~4 ч · Теория, Практика

## Зачем это AI-инженеру

AI-инженер дообучает модели редко, но вопрос «а почему не дообучить?» звучит на каждом втором собеседовании и в каждом втором разговоре с заказчиком. Сильный ответ — не «файнтюнинг крутой», а «вот когда он оправдан, вот почему здесь RAG, а здесь хватит промпта, и вот как я бы его запустил и оценил». Эта глава даёт и аргументы, и один реальный прогон LoRA своими руками.

## Теория

### Где файнтюнинг в жизненном цикле модели

```
pretraining           →  SFT (instruction tuning)  →  preference tuning     →  твой файнтюнинг
триллионы токенов         примеры «вопрос → ответ»      DPO / RLHF:               сотни–тысячи примеров
текста, модель учится     модель учится следовать        «этот ответ лучше того»   твоей задачи
продолжать текст          инструкциям, формату чата                                (обычно SFT + LoRA)
делают лаборатории        делают лаборатории             делают лаборатории         можешь ты
```

Видео Карпатого из AIL-3 описывало первые этапы. **Supervised fine-tuning (SFT)** — то же обучение «предскажи следующий токен», только на твоих примерах «вход → желаемый выход». Модель сдвигает веса так, чтобы на похожих входах выдавать похожие выходы.

Что важно понять: файнтюнинг меняет **поведение** (стиль, формат, решение узкой задачи), а не надёжно добавляет **знания**. Модель, дообученная на 500 примерах про API Bybit, не «запомнит документацию» — она научится отвечать *в стиле* этих примеров и будет уверенно галлюцинировать в этом стиле.

### Промпт vs RAG vs файнтюнинг: когда что

| Задача | Чем решать | Почему |
|---|---|---|
| Модель должна знать факты из документации бирж | **RAG** | Знания меняются; нужны ссылки на источник (AIL-23); обновление = переиндексация, а не переобучение |
| Нужен определённый формат/тон, который промптом держится нестабильно | **Файнтюнинг** (если промпт + few-shot + structured output не помогли) | Поведение «вшивается» в веса, промпт короче |
| Узкая классификация на большом трафике (тип вопроса, тональность, категория тикета) | **Файнтюнинг маленькой модели** | Маленькая дообученная модель часто догоняет большую на узкой задаче — в разы дешевле и быстрее |
| Дорогая большая модель хорошо решает задачу, нужно дешевле | **Дистилляция**: ответы большой модели → обучающий набор → файнтюнинг маленькой | Удешевление при сохранении качества на узкой задаче |
| Новая задача, мало примеров, требования меняются каждую неделю | **Промпт** | Итерация за минуты, а не часы; нечего «переобучать» |
| Модель должна знать твои сделки | **Tool calling / SQL** (Проект 1) | Данные меняются каждую минуту и должны быть точными |

Лестница решений, которую стоит произносить на собеседовании:

```
1. Промпт (+ few-shot, + structured output)   — часы, почти бесплатно
2. RAG / инструменты                           — если не хватает знаний или данных
3. Более сильная модель                        — если не хватает «ума»
4. Файнтюнинг                                  — если нужен стабильный формат/стиль,
                                                 узкая задача в масштабе, или удешевление
   ...и только при наличии evals, чтобы доказать, что стало лучше
```

Цена файнтюнинга — не только GPU. Это сбор и чистка данных (самое дорогое), evals, хранение и сервинг своих весов, и **переобучение при каждой смене базовой модели**. Облачные модели обновляются; твой адаптер к старой базе — нет.

Часть провайдеров предлагает управляемый файнтюнинг через API (загружаешь JSONL, получаешь id дообученной модели). Какие модели и на каких условиях это поддерживают — меняется, смотри актуальную документацию провайдера.

### Full fine-tuning vs PEFT

Полный файнтюнинг обновляет **все** веса. Для модели 8B это означает хранить в памяти веса, градиенты и состояние оптимизатора (у Adam — ещё два числа на параметр) — десятки гигабайт GPU-памяти и отдельная копия модели на каждую задачу.

**PEFT** (parameter-efficient fine-tuning) — семейство методов, которые замораживают исходные веса и обучают небольшое число новых. Самый популярный — **LoRA**.

### LoRA: идея в одной формуле

Возьмём одну матрицу весов `W` размером `d × k` (например, 4096 × 4096 в слое внимания). Полный файнтюнинг ищет поправку `ΔW` того же размера. Гипотеза LoRA: нужная для адаптации поправка имеет **низкий ранг**, то есть её можно представить как произведение двух узких матриц:

```
W' = W + ΔW = W + (alpha / r) · B · A

W:  d × k   (заморожена)
B:  d × r   (обучается, инициализирована нулями → в начале W' = W)
A:  r × k   (обучается)
r:  ранг, обычно 8–64

параметров в ΔW полного файнтюнинга: 4096 × 4096 = 16 777 216
параметров в LoRA при r = 16:        4096 × 16 + 16 × 4096 = 131 072  (≈0.8%)
```

Аналогия: вместо того чтобы хранить новую версию всего `node_modules`, ты хранишь маленький патч, который применяется поверх. Патч (адаптер) весит мегабайты, базовая модель одна, адаптеров под разные задачи — сколько угодно.

Параметры, которые ты встретишь в `LoraConfig`:

| Параметр | Что значит | Типичное начало |
|---|---|---|
| `r` | ранг: «ёмкость» адаптера | 8–16; больше — больше параметров, риск переобучения |
| `lora_alpha` | масштаб поправки (делится на `r`) | часто равен `r` или `2r` |
| `target_modules` | к каким матрицам добавлять адаптер | проекции внимания (`q_proj`, `k_proj`, `v_proj`, `o_proj`), часто и MLP (`gate_proj`, `up_proj`, `down_proj`); имена зависят от архитектуры |
| `lora_dropout` | регуляризация | 0–0.1 |

Иллюстративный пример на Hugging Face PEFT (сверь с актуальной версией docs):

```python
from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model

base = AutoModelForCausalLM.from_pretrained("<org>/<small-instruct-model>")
config = LoraConfig(
    r=16,
    lora_alpha=16,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)
model = get_peft_model(base, config)
model.print_trainable_parameters()  # expect well under 1% trainable
```

После обучения адаптер либо подгружается поверх базы (`PeftModel.from_pretrained`), либо вливается в веса (`merge_and_unload()` — возвращает новую модель, это не in-place операция) — тогда это обычная модель без дополнительной латентности, которую можно сконвертировать, например, в GGUF и запустить в Ollama (AIL-47).

### QLoRA: LoRA на бесплатном GPU

**QLoRA** = базовая модель загружается **квантизованной в 4 бита** (заморожена), а LoRA-адаптер обучается в 16 битах поверх неё. Память под базу падает в ~4 раза, и модель на несколько миллиардов параметров обучается на одной GPU уровня бесплатного Colab. Связь с AIL-47: это та же квантизация, только применённая во время обучения. Unsloth рекомендует начинать именно с QLoRA и обучать/сервить в одной и той же точности.

### Данные: формат и качество

Для чат-модели пример — это диалог в формате сообщений:

```json
{"messages": [
  {"role": "system", "content": "Классифицируй вопрос пользователя по теме."},
  {"role": "user", "content": "Как часто начисляется funding на OKX?"},
  {"role": "assistant", "content": "funding"}
]}
```

Каждый такой диалог перед обучением превращается в строку через **chat template** модели — специальные токены, обозначающие роли. Шаблон при обучении и при инференсе должен совпадать: если обучил с одним, а запускаешь с другим (например, другой шаблон в Ollama), модель ведёт себя странно. Обычно лосс считают **только на ответе ассистента**, а не на промпте.

Качество данных важнее количества: 300 чистых, разнообразных, единообразно размеченных примеров лучше 3000 противоречивых. Для узкого классификатора — сотни примеров на класс; для стиля — сотни–тысячи диалогов. Данные можно сгенерировать сильной моделью (синтетика из AIL-61 — та же техника), но тогда обязательно ручная проверка выборки.

### Как понять, что стало лучше

Как и всё в этой книге — только через evals:

- **Отложенная выборка** (test split, например 20%), которую модель не видела.
- **Три строки сравнения:** базовая модель с хорошим промптом и few-shot; дообученная модель; сильная облачная модель. Если базовая + few-shot ≈ дообученная — файнтюнинг не нужен.
- **Признаки переобучения:** train loss падает, а качество на test не растёт или падает; модель дословно повторяет обучающие ответы.
- **Catastrophic forgetting:** модель стала хорошо классифицировать, но разучилась нормально отвечать на всё остальное. Для узкой задачи это допустимо, для общего ассистента — нет.

Стартовые гиперпараметры из гайда Unsloth: learning rate `2e-4`, для быстрой проверки `max_steps=60`, для полного прогона 1–3 эпохи (больше — риск переобучения).

### Безопасность и данные

- Colab — облако Google. **Никаких реальных данных сделок в обучающем наборе**, только публичные или фейковые.
- Ноутбук Colab — исполняемый код. Бери ноутбуки из официальных источников (репозиторий/документация Unsloth, Hugging Face), просматривай ячейки перед запуском, особенно `pip install` и всё, что скачивает что-то по URL.
- Токен Hugging Face (если нужен для gated-модели или загрузки результата) — через Colab Secrets, не строкой в ячейке; токен с правами только на чтение, если не загружаешь модель.

## DeepSeek и Ollama: как это сделать у нас

Сам файнтюнинг идёт в Colab (Unsloth/PEFT) и от провайдера API не зависит. Провайдеры важны на трёх участках: где взять данные, где запустить результат и с чем сравнить. Проверено по документации DeepSeek и Ollama в ноябре 2026.

| Что | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| Управляемый файнтюнинг через API | проверь актуальные docs Anthropic | есть (загрузка JSONL, задача обучения) — условия и модели в docs | **нет**: в API Reference на ноябрь 2026 только chat/responses/messages, FIM, модели, баланс, файлы и инструменты | не обучает |
| Открытые веса для своего LoRA | нет | см. docs (часть open-weight моделей) | есть в организации `deepseek-ai` на Hugging Face, но флагманские модели слишком велики для Colab T4 и Мака — смотри размеры в карточках | — |
| Запустить свой результат | нет | дообученная модель живёт у OpenAI | нет | **да**: GGUF → `Modelfile` → `ollama create` |
| Роль в этой главе | для сравнения | для сравнения | «учитель» для синтетики по публичным данным; сильная строка сравнения | запуск адаптированной модели, базовая линия |

**Данные.** Синтетику для классификатора вопросов (опциональное задание) дешевле всего генерировать на DeepSeek (`deepseek-flash`; `deepseek-v4-pro` — если качество примеров хуже) — но **только из публичных** документаций бирж, как и требует глава. Перед тем как обучать модель на ответах другой модели, прочитай условия использования провайдера про использование выходов для обучения моделей — это меняется и различается у провайдеров. Данные сделок не идут ни в DeepSeek, ни в Colab.

**Запуск результата в Ollama.** Надёжный путь, который описан в [Importing a Model](https://docs.ollama.com/import): влить адаптер (`merge_and_unload()`), экспортировать в GGUF (у Unsloth есть функция экспорта в ноутбуке) и создать модель:

```
# Modelfile
FROM ./classifier-q4_k_m.gguf
PARAMETER temperature 0
```

`ollama create topic-clf -f Modelfile`. Ollama не квантизует GGUF при импорте — квантизуй заранее (llama.cpp `llama-quantize` или экспорт Unsloth). Шаблон чата должен совпадать с тем, на котором ты обучал (см. «На что обратить внимание»): проверь его в `ollama show --modelfile topic-clf`. Инструкцию `ADAPTER` (подключить LoRA поверх базы без слияния) на текущей странице Modelfile я не нашёл — если найдёшь её в своей версии, это вариант, но путь через слияние проверен.

**Ответ классификатора — строго из списка.** У Ollama `format` с JSON-схемой ([Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)) ограничивает ответ схемой, в том числе `enum`:

```python
# illustrative: classifier output constrained to the label set
from typing import Literal
from pydantic import BaseModel
import ollama

class Topic(BaseModel):
    topic: Literal["funding", "fees", "orders", "api-limits", "margin", "other"]

r = ollama.chat(model="topic-clf", messages=[{"role": "user", "content": question}],
                format=Topic.model_json_schema(), options={"temperature": 0})
label = Topic.model_validate_json(r.message.content).topic
```

**Три строки сравнения** из теории на наших провайдерах: базовая маленькая модель в Ollama с хорошим промптом и few-shot; та же модель после LoRA в Ollama; сильная облачная — `deepseek-v4-pro` на тех же публичных вопросах (Claude/OpenAI — для сравнения, если есть ключ). Если дообученная локальная догоняет DeepSeek на классификации — это и есть аргумент «дешевле и приватно» для собеседования.

## Маршрут изучения

1. Открой [Hugging Face LLM Course](https://huggingface.co/learn/llm-course) → глава 11 (fine-tuning): Chat Templates, Supervised Fine-Tuning, LoRA, Evaluation (≈75 мин). Обрати внимание на chat templates и на то, как SFT-тренер (TRL) принимает датасет.
2. Открой [Hugging Face PEFT](https://huggingface.co/docs/peft) → Quicktour, затем гайд по LoRA (developer guides) (≈30 мин). Найди: `LoraConfig`, `get_peft_model`, `print_trainable_parameters`, `merge_and_unload`, и что такое QLoRA-вариант загрузки.
3. Открой [Unsloth](https://github.com/unslothai/unsloth) → README: список поддерживаемых моделей и таблицу бесплатных ноутбуков (≈15 мин). Затем [Fine-tuning LLMs Guide](https://unsloth.ai/docs/get-started/fine-tuning-llms-guide) в их документации → разделы про выбор модели, LoRA vs QLoRA, датасет, гиперпараметры (≈30 мин). Там же есть страница с гайдом по гиперпараметрам LoRA — прочитай про `r` и `lora_alpha`.
4. (Желательно) Оригинальная статья «LoRA: Low-Rank Adaptation of Large Language Models» (Hu et al., 2021, arXiv) — только аннотация, введение и рисунок 1 (≈20 мин). Этого хватит, чтобы объяснить идею своими словами.
5. Открой [Ollama: Importing a Model](https://docs.ollama.com/import) и [Modelfile Reference](https://docs.ollama.com/modelfile) → импорт GGUF, `FROM`, `PARAMETER`, шаблон (≈15 мин).
6. Открой [DeepSeek: Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing) и посмотри API Reference — убедись сам, что эндпоинта файнтюнинга нет, и прикинь стоимость генерации 300 синтетических примеров (≈10 мин).
7. Запусти ноутбук (см. Практику) (≈60–90 мин вместе с ожиданием обучения).

## На что обратить внимание

- **Файнтюнинг ради знаний** — самая частая ошибка. Новые факты и часто меняющиеся данные — это RAG или инструменты.
- **Нет базовой линии.** Без сравнения с «базовая модель + хороший промпт» любое улучшение не доказано.
- **Утечка test в train:** дубликаты и почти-дубликаты в обеих выборках дают красивые и ложные цифры. Дедуплицируй до разбиения.
- **Несовпадение chat template** между обучением и запуском.
- **Слишком много эпох / большой learning rate** — модель заучивает примеры.
- **Неконсистентная разметка:** если в данных одна и та же ситуация размечена по-разному, модель выучит шум.
- **Colab-сессия обрывается** — сохраняй адаптер (он маленький) на Google Drive или скачивай сразу после обучения.
- **Сторонний код в ноутбуке** — читай ячейки до запуска.
- **«Дообучу DeepSeek»** — через его API нельзя; открытые веса флагманов на Colab не влезут. Дообучаешь маленькую open-weight модель.
- **GGUF без квантизации** в Ollama: импорт не квантизует, модель займёт память как FP16.
- **Синтетика из реальных данных** через облачную модель — утечка; только публичные доки.

## Ответы

1. RAG. Знания меняются, их нужно обновлять переиндексацией и подтверждать ссылками; файнтюнинг ненадёжно добавляет факты и устаревает.
2. b. Исходные веса заморожены, обучается поправка `B·A` низкого ранга.
3. 4096 × 8 + 8 × 4096 = 65 536 параметров (против 16.7 млн у полной матрицы).
4. В QLoRA базовая модель загружена квантизованной в 4 бита (заморожена), а адаптер обучается поверх в 16 битах. Это резко снижает память и позволяет обучать на одной небольшой GPU.
5. Файнтюнинг не даёт надёжного точного знания данных, а сделки меняются постоянно — модель будет галлюцинировать правдоподобные цифры. Плюс реальные данные уезжают в облако Google. Правильно: инструменты/SQL по копии базы только на чтение (Проект 1).
6. Шаблон, превращающий список сообщений с ролями в строку со служебными токенами. Модель обучается на конкретной разметке; при другой разметке на инференсе она видит непривычный формат и ведёт себя непредсказуемо.
7. Train loss падает, а качество на test стоит или падает; модель дословно повторяет обучающие ответы; хуже справляется с перефразированными входами.
8. b. Если базовая модель с хорошим промптом даёт сопоставимое качество, файнтюнинг не нужен.
9. При узкой, стабильной задаче с большим трафиком, где дообученная маленькая модель достигает качества большой (например, классификация вопросов), — тогда экономия на каждом запросе и латентности окупает сбор данных и сопровождение.
10. Вливает веса адаптера в базовую модель и возвращает обычную модель без отдельного адаптера: нет дополнительной латентности, можно конвертировать (например, в GGUF). Операция не in-place — результат надо присвоить.
11. Сбор, разметка и проверка данных; построение evals; хранение и сервинг своих весов; мониторинг; переобучение при смене базовой модели.
12. Иначе почти одинаковые примеры попадут и в train, и в test, и модель будет «угадывать» заученное — метрики на test окажутся завышенными.
13. Нет: в API DeepSeek (на ноябрь 2026) нет эндпоинта файнтюнинга, а открытые веса его флагманов слишком велики для Colab. Дообучают маленькую open-weight модель (LoRA/QLoRA), а DeepSeek используют как «учителя» для синтетики и как сильную строку сравнения.
14. Ollama не квантизует GGUF при импорте: какой файл дал, такой и запустился. Квантизуй заранее (`llama-quantize` или экспорт Unsloth в `q4_k_m`).
15. Только публичные данные (документации бирж) и фейковые примеры. Данные сделок, логи и ключи — нет: серверы DeepSeek в Китае; плюс проверь условия использования выходов модели для обучения.
