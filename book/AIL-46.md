# 11.3 · Трейсинг и стоимость одного ответа  (AIL-46)

> **Неделя 11** · Продакшен · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Пользователь пишет «бот ответил ерунду», и без трейса ты не узнаешь, что пошло не так: поиск не нашёл нужный чанк, модель проигнорировала контекст, инструмент вернул пустоту или сработал фолбэк на слабую модель. С деньгами то же: «почему вчера потратили втрое больше» без трейсов не объяснить. На собеседованиях observability — обязательный пункт system design (AIL-68): «как вы узнаёте, что качество упало?», «сколько стоит один ответ?», «какой у вас p95?».

## Теория

### Логи vs метрики vs трейсы

Ты уже логируешь стоимость в Проекте 1 (AIL-16) и делал Langfuse-трейсы для RAG в AIL-30. Теперь соберём это в систему.

| | Что отвечает | Пример |
|---|---|---|
| **Лог** | что произошло в момент | `12:03:11 tool=get_positions rows=14` |
| **Метрика** | сколько / как часто, агрегат | p95 латентности = 4.2 с, ошибки 1.3% |
| **Трейс** | как прошёл **один** запрос по всем шагам | дерево: поиск 180 мс → реранк 300 мс → LLM 2.1 с ($0.004) |

В обычном бэкенде трейсинг — это «где тормозит». В LLM-приложении трейс ещё и **содержательный**: в нём лежат промпт, найденные документы, аргументы инструментов и ответ. Поэтому трейс — главный инструмент разбора ошибок (AIL-34): открыл плохой ответ, увидел, что в контекст попали чанки про spot вместо futures, — проблема в retrieval, а не в модели.

### Анатомия трейса

```
trace  "rag-answer"  user=demo  session=tg-123  tags=[rag, v3]   total: 3.1 s, $0.0061
├─ span        "rewrite-query"                    0.6 s
│  └─ generation  model=small  in=220 out=40     0.6 s   $0.0002
├─ span        "retrieve"   top_k=8               0.2 s
│     input: "funding rate interval bybit"  output: [8 chunk ids]
├─ span        "rerank"                           0.3 s
└─ generation  "answer"  model=main  in=4100 (cache_read=1800) out=380   2.0 s  $0.0059
      output: "Интервал funding у Bybit ... [1][3]"
```

- **Trace** — один запрос пользователя целиком. Атрибуты: `user_id`, `session_id` (диалог в Telegram), `tags` (версия промпта, проект), `metadata`.
- **Span** — любой шаг с началом и концом (поиск, вызов инструмента, парсинг).
- **Generation** — span, который является вызовом модели: модель, параметры, usage (токены, включая кэш), стоимость.
- **Score** — оценка, прикреплённая к трейсу: от пользователя (👍/👎 в боте), от LLM-судьи, из evals (AIL-29).

Langfuse построен на OpenTelemetry (OTel) — открытом стандарте трейсинга. Для LLM у OTel есть семантические соглашения GenAI (имена атрибутов вроде модели и токенов). Практический смысл: трейсы можно отправлять в любой совместимый бэкенд, а инструментирование библиотек (OpenAI SDK, LangChain, LlamaIndex) часто есть готовое.

### Как инструментировать

Три уровня, от простого к гибкому:

1. **Обёртка клиента.** `from langfuse.openai import openai` — drop-in замена OpenAI SDK, каждый вызов становится generation с токенами и стоимостью. Работает и для Ollama (AIL-47), и для LiteLLM, если они идут через OpenAI-клиент.
2. **Декоратор `@observe`** на своих функциях — span на функцию, вложенность строится автоматически по стеку вызовов (в том числе в async-коде).
3. **Ручные observations** — когда нужно точно контролировать, что записать, например usage с кэшем Anthropic.

Иллюстративный пример (Langfuse Python SDK; у SDK бывают мажорные изменения — сверь сигнатуры с документацией своей версии):

```python
from langfuse import observe, get_client

langfuse = get_client()  # reads LANGFUSE_PUBLIC_KEY / LANGFUSE_SECRET_KEY / LANGFUSE_BASE_URL

@observe(name="retrieve")
def retrieve(query: str) -> list[dict]:
    ...

@observe(name="rag-answer")
def answer(question: str, user_id: str) -> str:
    chunks = retrieve(question)
    with langfuse.start_as_current_observation(
        as_type="generation", name="answer", model=MODEL
    ) as gen:
        resp, usage, cost = call_llm(question, chunks)   # your llm_utils from AIL-11/45
        gen.update(
            output=resp.text,
            usage_details=usage,   # e.g. {"input": ..., "output": ..., "cache_read_input_tokens": ...}
            cost_details=cost,     # your own computed cost, so cache discounts are right
        )
    return resp.text
```

Про стоимость: Langfuse умеет считать её сам по таблице цен моделей, но для новых моделей, кэша и Ollama цены может не быть или она будет неточной. Надёжнее передавать **свою** стоимость, посчитанную формулой из AIL-45, и сверять с инвойсом провайдера. Для локальной модели стоимость токенов — ноль, но в README честно пиши, что это не «бесплатно» (железо, электричество, время).

Короткоживущие скрипты (evals, `bench_cost.py`) должны вызывать `langfuse.flush()` перед выходом — SDK отправляет данные в фоне пачками, и без flush последние трейсы теряются.

### Метрики, которые нужны на дашборде

**Стоимость:** средняя на ответ, сумма за день, **разбивка по моделям** (фолбэк виден сразу) и по шагам (rewrite дешёвый, answer дорогой).

**Латентность — перцентили, а не среднее.** Распределение латентности LLM длиннохвостое: большинство ответов за 2 с, но некоторые 15 с (длинный ответ, ретрай, агент сделал 6 шагов). Среднее прячет хвост.

- **p50** (медиана) — половина ответов быстрее этого значения: «типичный» опыт.
- **p95** — 95% ответов быстрее: то, что видит каждый двадцатый запрос. Обычно именно на p95 ставят цели (SLO).
- Для стриминга отдельно — **TTFT** (time to first token): пользователь видит, что бот «пишет», и ждать готов дольше.

```python
import statistics
lat = [r["latency_s"] for r in rows]
p50 = statistics.median(lat)
p95 = statistics.quantiles(lat, n=100)[94]  # needs enough data points to be meaningful
```

Помни AIL-62: на 20 запросах p95 — это практически максимум, оценка шумная. Пиши, на скольких запросах посчитано.

**Ошибки:** доля запросов, закончившихся исключением, таймаутом, отказом по бюджету, фолбэком. Отдельно — «мягкие» ошибки: ответ без ссылок, невалидный JSON, «в документации не нашёл» (это может быть и правильный отказ, и провал retrieval — смотри по трейсам).

**Для агента (Проект 4):** число шагов на задачу, число вызовов инструментов, доля задач, упёршихся в лимит шагов. Стоимость агента — это сумма всех итераций, и она растёт сверхлинейно, потому что каждая итерация повторяет всю историю.

### Приватность трейсов

Трейс содержит всё, что видела модель. Для Проекта 1 и Проекта 4 это **цифры твоих сделок**. Правила:

- Реальные данные — только в self-hosted Langfuse на твоей машине (AIL-66), не в облаке. Или маскирование: у Langfuse есть механизм маскирования данных перед отправкой; суммы и объёмы можно заменять на `***`.
- Публичная демо-версия и скриншоты дашборда для README — только на **фейковой** базе.
- Ключи и токены никогда не попадают в metadata трейсов. Проверь, что ты не логируешь целиком объект конфигурации или заголовки.

### Сбой трейсинга не должен ронять ответ

Трейсинг — вспомогательная система. SDK Langfuse отправляет данные асинхронно и не должен бросать исключения в твой код, но твои собственные обёртки (подсчёт стоимости, запись в SQLite) — должны быть в `try/except` с логированием. Проверка из AIL-66: остановил контейнер Langfuse — ассистент отвечает.

### LLM CLI: эксперименты из терминала

[LLM](https://llm.datasette.io) Саймона Уиллисона — CLI для разговора с моделями: `llm "вопрос"`, `llm -m <model> -s "system prompt" < file.md`, шаблоны, эмбеддинги. Провайдеры подключаются плагинами (`llm-anthropic`, `llm-ollama` и др.). Чем полезен в контексте этой главы: **каждый запрос автоматически пишется в SQLite** — промпт, ответ, модель, токены (`llm logs -u`, `llm logs --json`, путь к базе — `llm logs path`). Это мини-трейсинг для быстрых экспериментов: сравнил три формулировки промпта из терминала — и у тебя есть журнал с токенами, который можно открыть в Datasette или запросить SQL.

Плагины LLM — сторонний код, который получает твои ключи. Ставь сам `llm` через `uv tool install llm` и только нужные плагины, после проверки по твоему обычному чек-листу (автор, репозиторий, что делает установка). Учти, как он хранит ключи (`llm keys set` пишет их в файл в профиле пользователя) — можно вместо этого передавать через переменные окружения.

## DeepSeek и Ollama: как это сделать у нас

Трейсинг от провайдера почти не зависит: Langfuse всё равно, кто ответил. Зависит от провайдера **usage и стоимость** — у каждого свои поля, и именно на них ломается «стоимость одного ответа». Факты проверены по документации DeepSeek, Ollama и OpenRouter в ноябре 2026.

### Откуда брать цифры для generation

| Что нужно в трейсе | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| Input / output токены | `usage.input_tokens` / `output_tokens` | `usage.prompt_tokens` / `completion_tokens` | как у OpenAI | родной API: `prompt_eval_count` / `eval_count`; OpenAI-совместимый — проверь, что `usage` заполнен (в странице совместимости это явно не описано) |
| Кэш | `cache_creation_input_tokens`, `cache_read_input_tokens` | `prompt_tokens_details.cached_tokens` | `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` (в примере — на верхнем уровне `usage`, в схеме — в `prompt_tokens_details`; читай оба) | `prompt_eval_cached_count` |
| Токены размышления | в `output_tokens` (thinking) | `completion_tokens_details.reasoning_tokens` | `completion_tokens_details.reasoning_tokens`; размышление **включено по умолчанию** | зависит от модели |
| Стоимость в ответе | нет, считаешь сам | нет, считаешь сам | нет, считаешь сам; цена зависит от **пиковых часов UTC** | $0 API |
| Время | считаешь сам | считаешь сам | считаешь сам | `total_duration`, `load_duration`, `prompt_eval_duration`, `eval_duration` в **наносекундах** |
| Usage при стриминге | в финальном `message_delta` | `stream_options={"include_usage": True}` | `stream_options` поддерживается | `include_usage` поддерживается |

Через OpenRouter (глава 2.4 · OpenRouter: один API ко многим моделям, AIL-69) стоимость приходит готовой в `usage.cost` — без дополнительных параметров ([Usage Accounting](https://openrouter.ai/docs/guides/guides/usage-accounting)). Это удобно, но сверяй с собственным расчётом хотя бы выборочно.

### Стоимость DeepSeek в Langfuse

Встроенной таблице цен Langfuse не стоит доверять для DeepSeek: у него цена промаха и попадания в кэш различаются в десятки раз, а вне пиковых часов (01:00–04:00 и 06:00–10:00 UTC по будням — пик) всё стоит вдвое дешевле. Ни того, ни другого автоматический расчёт может не знать — проверь на своей версии, а надёжнее передавай свою стоимость функцией `deepseek_cost` из главы 11.2 (AIL-45):

```python
# illustrative: one DeepSeek call as a Langfuse generation with your own cost
from datetime import datetime, timezone
from llm_utils import deepseek, deepseek_cost, ds_cache_tokens, is_peak

with langfuse.start_as_current_observation(as_type="generation", name="answer",
                                           model="deepseek-flash") as gen:
    ts = datetime.now(timezone.utc)
    resp = deepseek.chat.completions.create(model="deepseek-flash", messages=messages,
                                            extra_body={"thinking": {"type": "disabled"}})
    hit, miss = ds_cache_tokens(resp.usage)
    details = resp.usage.completion_tokens_details
    gen.update(
        output=resp.choices[0].message.content,
        usage_details={"input_cache_hit": hit, "input_cache_miss": miss,
                       "output": resp.usage.completion_tokens,
                       "reasoning": getattr(details, "reasoning_tokens", 0) or 0},
        cost_details={"total": deepseek_cost("deepseek-flash", resp.usage, ts)},
        metadata={"provider": "deepseek", "peak": is_peak(ts)},
    )
```

Две вещи, которые надо проверить на своих ответах, а не принять на веру: входят ли `reasoning_tokens` в `completion_tokens` (в OpenAI-конвенции входят; DeepSeek в документации пишет, что биллинг — по сумме input и output токенов) — иначе ты посчитаешь рассуждение дважды или не посчитаешь вовсе; и совпадает ли сумма твоих `cost` за день с расходом в личном кабинете DeepSeek.

### Ollama: стоимость ноль, время — главная метрика

Для локальной модели стоимость токенов — $0, а интересное — время. Родной API Ollama ([Usage](https://docs.ollama.com/api/usage)) отдаёт его по фазам, и из этого получаются метрики главы 11.4 (AIL-47):

```python
# illustrative: Ollama native /api/chat metrics -> trace metadata
import ollama  # official Python library; pin the version

r = ollama.chat(model=MODEL, messages=messages, options={"num_ctx": 16384})
ns = 1e9
meta = {
    "load_s": r.load_duration / ns,                       # >0 = cold start, exclude from latency stats
    "prefill_s": r.prompt_eval_duration / ns,             # ~ TTFT without network
    "decode_tok_per_s": r.eval_count / (r.eval_duration / ns),
    "prompt_tokens": r.prompt_eval_count,                 # compare with num_ctx: truncation?
    "cached_prompt_tokens": getattr(r, "prompt_eval_cached_count", None),
}
```

`load_duration` заметно больше нуля — значит, модель загружалась (холодный старт после `keep_alive`); такие запросы помечай тегом и не смешивай с остальными в p95.

## Маршрут изучения

1. Открой [Langfuse docs](https://langfuse.com/docs) → раздел Observability: обзор, data model (traces, observations, generations, sessions, scores) и Python SDK (≈45 мин). Обрати внимание на `@observe`, вложенность, `flush()` и на то, как задаются `user_id`/`session_id`/tags.
2. В тех же docs → раздел про model usage and cost: как Langfuse считает стоимость, как задать свою цену модели и как передать готовую стоимость (≈20 мин). Запомни, что делать с кэш-токенами.
3. В docs → интеграция с OpenAI SDK (`from langfuse.openai import openai`) — если твои проекты (или Ollama/LiteLLM) идут через OpenAI-клиент (≈10 мин).
4. В docs → раздел про дашборды/metrics и про маскирование данных (≈20 мин). Посмотри, какие графики есть из коробки (cost, latency, по моделям) и как строится свой.
5. Открой [LLM CLI](https://llm.datasette.io) → установка, «Usage», «Logging to SQLite», плагины (≈25 мин). Поставь и сделай 5 запросов, затем `llm logs -n 5 -u`.
6. Открой [DeepSeek: Create Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion) → схему объекта `usage` в ответе (≈10 мин). Выпиши все поля, включая кэш и `reasoning_tokens`, и найди, где они лежат в реальном ответе (`print(resp.usage.model_dump())`).
7. Открой [Ollama: Usage](https://docs.ollama.com/api/usage) → метрики времени и токенов родного API (≈10 мин). Запомни: длительности в наносекундах.
8. (Если пользуешься OpenRouter) [Usage Accounting](https://openrouter.ai/docs/guides/guides/usage-accounting) → `usage.cost`, `cached_tokens`, `reasoning_tokens` (≈10 мин).
9. В docs LLM CLI найди, как подключить OpenAI-совместимую модель (DeepSeek) и плагин `llm-ollama` для локальной (≈10 мин); перед установкой плагина — твоя обычная проверка стороннего кода.
10. (Справочно) Найди в документации OpenTelemetry страницу про семантические соглашения GenAI — только просмотреть, какие атрибуты стандартизованы (≈10 мин).

## На что обратить внимание

- **Плоские трейсы.** Если всё записано одним generation без spans, ты не поймёшь, поиск виноват или модель. Минимум: retrieve и answer — отдельно.
- **Нет `flush()` в скриптах** — evals «прошли», а в Langfuse пусто или половина.
- **Двойной учёт стоимости:** обёртка клиента посчитала и ты вручную записал ещё одну generation на тот же вызов. Сумма в дашборде удвоится.
- **Стоимость без кэша.** Если Langfuse считает по прайсу без учёта `cache_read`, экономия из AIL-45 на дашборде не видна, а стоимость завышена.
- **Среднее вместо перцентилей** и перцентили на 15 точках.
- **Трейсы с реальными сделками в облаке** или на скриншотах в README.
- **Высокая кардинальность тегов:** не клади в tags уникальные значения (id запроса, текст вопроса) — это для metadata.
- **В async-коде** контекст трейса передаётся через contextvars; если ты запускаешь задачу в отдельном потоке или пуле, вложенность может потеряться — проверь дерево в UI.
- **Сэмплирование:** при большом трафике трейсят не всё. На твоём масштабе — трейсить 100%.
- **DeepSeek по прайсу Langfuse** — без hit/miss и пиковых часов стоимость окажется неверной в обе стороны. Передавай свою.
- **Ollama: наносекунды** в длительностях родного API и холодный старт (`load_duration`) внутри p95.
- **Трейс с `provider=deepseek` в проекте с реальными сделками** — утечка, а не просто запись.

## Ответы

1. Span — любой шаг с длительностью; generation — span, представляющий вызов модели, с моделью, параметрами, usage и стоимостью. Стоимость и токены агрегируются по generations.
2. Распределение длиннохвостое: среднее прячет медленные ответы, которые видит заметная доля пользователей. p95 показывает опыт «каждого двадцатого».
3. В Проекте 1 и Проекте 4 — цифры реальных сделок. Только self-hosted Langfuse локально или маскирование; демо и скриншоты — на фейковой базе.
4. Нет `langfuse.flush()` в конце: SDK отправляет данные в фоне, скрипт завершается, и последние трейсы теряются.
5. В tags — значения с малой кардинальностью для фильтрации: `chunking-B`, `v3`. Id запроса и текст вопроса — в metadata/input.
6. Двойная запись generation (обёртка + ручная); автоматическая стоимость без учёта кэш-скидки; неверная цена модели в таблице Langfuse; фолбэк на более дорогую модель.
7. Time to first token — время до первого токена ответа. При стриминге пользователь видит, что ответ пошёл, и общая длительность воспринимается терпимее; TTFT — главный показатель «отзывчивости».
8. b. Модель ответила по тому, что ей дали; надо разбирать запрос к поиску, переформулировку, фильтры по метаданным (AIL-60) и чанкинг.
9. Почти никак: на 12 точках p95 практически равен максимуму и сильно зависит от одного выброса. Нужно больше запросов и указание размера выборки.
10. Для быстрых экспериментов из терминала без кода: промпт против нескольких моделей, всё автоматически логируется в SQLite с токенами. Langfuse — для приложения.
11. Автоматический расчёт может не знать цену новой модели, кэш-множителей или локальной модели. Своя формула (AIL-45) согласована с инвойсом и учитывает кэш.
12. 4000 токенов — попадание в кэш, у DeepSeek оно в десятки раз дешевле промаха; считать надо hit и miss отдельно. Ещё на цену влияет время запроса: вне пиковых часов UTC всё вдвое дешевле.
13. 300 / 6 с = 50 tokens/s (длительности в наносекундах). `load_duration` в 4 с — холодный старт: модель загружалась в память; такой запрос помечают и исключают из p95 или считают отдельно.
14. Реальные данные сделок ушли в облако DeepSeek — инцидент приватности: где-то фолбэк или конфиг пустил приватный путь в облако. Остановить, найти причину (цепочка фолбэка, переменная окружения), добавить тест, что приватный путь только локальный.
