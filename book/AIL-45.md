## Зачем это AI-инженеру

В главе 11.1 ассистент поддержки стал подниматься одной командой; теперь он должен ещё и не разорять владельца и не падать вместе с провайдером. Счёт за LLM растёт линейно с трафиком, а провайдеры регулярно отвечают 429 и 529 (перегрузка у Anthropic). Сервис, который в эти минуты просто падает или за ночь сжигает месячный бюджет из-за зациклившегося агента, в продакшен не пускают. На собеседованиях спрашивают именно так: «как вы снизили стоимость?», «что будет, если Anthropic недоступен?», «как не допустить счёта на $5000?» — и ждут цифр и механизмов, а не «ну, мы следили».

## Теория

### Откуда берётся стоимость запроса

В главе 1.7 · Токены, temperature и стоимость запроса к LLM (AIL-5) мы считали стоимость как `input_tokens × цена_input + output_tokens × цена_output` (функция `estimate_cost`). Для ассистента поддержки магазина Shelf из проекта 2 разложение одного ответа обычно такое:

```
запрос к модели ≈ 8k токенов input
 ├─ system prompt + правила цитирования    ~1.5k  одинаковый всегда
 ├─ few-shot примеры                       ~1k    одинаковый всегда
 ├─ постоянные разделы kb/ (по желанию)    ~2.5k  одинаковый, пока не поменяли kb/
 ├─ найденные куски (top-5)                ~3k    свой у каждого вопроса
 └─ вопрос клиента                         ~50    свой
ответ ≈ 300 токенов output (дороже за токен в несколько раз)
```

Отсюда три рычага: **не платить заново за одинаковое** (prompt caching), **не делать запрос вообще** (кэш ответов), **платить меньше за токен** (модель дешевле там, где хватает, — это решается evals, как в главе 8.3). Плюс два механизма защиты: **фолбэки** — переключение на запасного провайдера, когда основной лежит, — и **бюджет** — лимит расходов на случай, когда что-то пошло не так. Глава идёт в этом порядке: сначала два вида кэша, потом фолбэки, потом бюджет.

### Prompt caching: повторение из главы 2.7 и применение к RAG

Первый рычаг — prompt caching: провайдер запоминает обработанное начало промпта и при повторе берёт за него меньше. Механику мы разобрали в главе 2.7 · Стриминг, ретраи, rate limits, prompt caching (AIL-11); коротко главное:

- Кэшируется **префикс** запроса. У Anthropic порядок префикса: `tools` → `system` → `messages`. Изменение на любом уровне инвалидирует его и всё после.
- У Anthropic кэш включается явно: `cache_control: {"type": "ephemeral"}` на блоке (до 4 точек разметки) или автоматический режим с одним полем верхнего уровня. Запись в кэш стоит дороже обычного input (для 5-минутного TTL — 1.25×, для часового — 2×), чтение — в разы дешевле (стандартно 0.1×, у части новых моделей ещё меньше). Есть **минимальная длина** кэшируемого префикса, разная для разных моделей — от сотен до нескольких тысяч токенов. Короче — кэш молча не включится, без ошибки. Точные множители и пороги стоит сверить с документацией на день работы.
- У OpenAI кэширование префиксов автоматическое для достаточно длинных промптов; сколько попало в кэш — в `usage.prompt_tokens_details.cached_tokens`.
- Проверять факт попадания — только по `usage`: `cache_creation_input_tokens` и `cache_read_input_tokens` у Anthropic. Если оба нуля — кэша не было.

**Главная мысль для RAG:** кэш работает только на одинаковом префиксе, а куски у каждого вопроса свои. Значит, промпт надо **упорядочить** так, чтобы всё неизменное шло первым, а изменяемое — последним:

```
[tools]                          ─┐
[system: роль, правила]           │  стабильный префикс → cache_control здесь
[few-shot примеры]                │
[постоянные разделы kb/]         ─┘
[найденные куски <documents>]    ─┐  меняется каждый раз
[вопрос клиента]                 ─┘
```

Типичная ошибка, которая обнуляет кэш: в system prompt подставлена текущая дата-время («Сейчас 2026-11-26 14:03:17»), id запроса или имя клиента. Префикс меняется каждую секунду — кэш никогда не читается, зато каждый раз пишется по повышенной цене. Динамику — в конец.

Если стабильный префикс короче минимального порога, кэш в RAG ничего не даст. Это нормальный результат эксперимента, его надо так и записать. Где кэш даёт много: длинные инструкции, большая «шпаргалка», которая нужна почти в каждом ответе, многоходовые диалоги в Telegram-боте поддержки (вся история — префикс следующего хода), агентский цикл из главы 9.3 (каждая итерация повторяет всю историю инструментов).

У ассистента поддержки такая «шпаргалка» естественна: про доставку и возвраты спрашивают чаще всего, поэтому актуальные `kb/delivery.md` и `kb/returns.md` можно класть в префикс целиком. Условия: только текущие страницы (архивная `kb/returns-2025.md` — никогда); префикс пересобирается при переиндексации (иначе ассистент цитирует старые правила); постоянные разделы оформлены такими же `<document>` с `kb/<file>.md#<anchor>` и всегда получают номера `[1]`…`[m]`, найденные куски нумеруются дальше, дубли из выдачи убираем.

Иллюстративный пример (Anthropic SDK; модель и детали параметров сверяем с актуальной документацией):

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from env

STABLE_KB = ["kb/delivery.md", "kb/returns.md"]  # current pages only, never archived
# rules + few-shot + stable kb sections as numbered <document> blocks; rebuilt on re-ingest
STATIC_SYSTEM = build_static_system("prompts/answer_v2.txt", STABLE_KB)

def answer(question: str, docs_xml: str, model: str):
    resp = client.messages.create(
        model=model,
        max_tokens=600,
        system=[
            {"type": "text", "text": STATIC_SYSTEM,
             "cache_control": {"type": "ephemeral"}},  # breakpoint after stable prefix
        ],
        messages=[{"role": "user",
                   "content": f"<documents>\n{docs_xml}\n</documents>\n\nQuestion: {question}"}],
    )
    u = resp.usage
    # cache_creation_input_tokens: written now; cache_read_input_tokens: served from cache
    return resp, u.input_tokens, u.cache_creation_input_tokens, u.cache_read_input_tokens
```

Формула стоимости с кэшем (множители — из документации для выбранной модели):

```
cost = (input × P_in
      + cache_write × P_in × k_write
      + cache_read  × P_in × k_read
      + output × P_out) / 1_000_000
```

Именно её надо зашить в `common/llm_utils.py` (параметры `cache_read_tokens` и `cache_write_tokens` у `estimate_cost`), иначе кэшированные токены посчитаются по полной цене и экономии не будет видно.

### Кэш ответов и семантический кэш

Второй рычаг — другой уровень: не «дешевле обработать промпт», а «не звонить модели вообще».

**Точный кэш** — ключ = хэш от (модель, промпт, параметры). Безопасен, но в чате почти не попадает: люди формулируют по-разному. Полезен в evals и при разработке — повторный прогон того же набора стоит ноль (так, кстати, работают кэши в promptfoo).

**Семантический кэш** — ключ = эмбеддинг вопроса. Если новый вопрос близок к сохранённому (косинусная близость выше порога, глава 4.1), возвращаем сохранённый ответ.

```
вопрос → embed → поиск ближайшего в кэше
             ├─ sim ≥ 0.95 → вернуть сохранённый ответ  (0 токенов LLM)
             └─ иначе      → полный RAG → сохранить (вопрос, ответ, ts)
```

Когда уместен: FAQ-подобный трафик, где много одинаковых вопросов, ответы не зависят от времени и от клиента (например, «сколько дней на возврат?»).

Когда опасен — и это любимая тема на собеседованиях:

| Риск | Пример из ассистента магазина Shelf |
|---|---|
| Близкие по эмбеддингу, разные по смыслу | «можно ли вернуть вскрытый чай?» vs «можно ли вернуть невскрытый чай?»; «гарантия на лампу Light» (12 месяцев) vs «гарантия на Light Mini» (6 месяцев) — косинус высокий, ответы разные |
| Устаревание | «действует ли TEA15 вместе со скидкой?», «сколько стоит доставка» — после правки `kb/promo.md` или тарифов ответ из кэша верен только вчера |
| Утечка между клиентами | ответ локальной модели на вопрос с личными данными («где мой заказ 1042, телефон …») выдан другому клиенту с похожей формулировкой |
| Отравление кэша | prompt injection (глава 9.4) через отравленную страницу `kb/` заставил модель выдать мусор или «промокод на 100%», и это теперь отдаётся всем похожим вопросам |
| Потеря трассируемости | ответ без свежих ссылок на источники ломает контракт «каждое утверждение — со ссылкой» из главы 5.3 |

Отсюда правила: высокий порог, TTL, ключ включает версию индекса (хэши страниц `kb/`); вопросы, на которых сработал `contains_personal_data`, не кэшируются вообще; отказы и ошибки тоже не кэшируются; и **кэш проверяется evals-набором**: перефразы должны попадать, а «ловушки» с противоположным смыслом — нет.

### Фолбэки: что, когда, на что

Кэши снижают цену, но не помогают, когда провайдер не отвечает. Для этого нужен фолбэк — переход на запасную модель. Фолбэк — не «поймать любое исключение и позвать другую модель». Правила:

- **Какие ошибки:** 429 (после ретраев), 5xx, 529 overloaded, таймаут, сетевые ошибки. **Не** 400/401/403/404 — это ошибка в нашем запросе или ключе, на другом провайдере она либо повторится, либо замаскирует баг.
- **Порядок:** сначала ретраи с экспоненциальной паузой и джиттером (глава 2.7), потом фолбэк. Иначе каждый случайный 529 переключает провайдера.
- **Circuit breaker** («автомат-предохранитель»): если основной провайдер упал 5 раз за минуту, не пытаться ещё N секунд, идти сразу в запасной. Иначе каждый запрос сначала ждёт таймаут.
- **Куда переключаться, решают данные.** Вопрос о правилах без личных данных может уйти в другую облачную модель; сообщение, где сработал `contains_personal_data`, — только в локальную модель или оператору (`handoff`).
- **Совместимость:** у запасной модели другой токенизатор, другое поведение в tool calling, другой стиль цитирования. Промпт может потребовать версию под каждую модель. **Evals на запасной модели обязательны** — фолбэк, который отвечает плохо, хуже честной ошибки.
- **Кэш теряется:** prompt cache привязан к провайдеру и модели; после переключения первые запросы идут по полной цене.
- **Наблюдаемость:** в лог/трейс пишем, какая модель фактически ответила. Иначе в главе 11.3 не понять, почему подскочила стоимость.
- **Запасной может быть локальным** — Ollama (подробно — глава 11.4); тогда стоимость ноль, но качество надо измерить.

### LiteLLM: один интерфейс ко всем провайдерам

Ретраи, фолбэки, circuit breaker, учёт стоимости — всё это можно написать самим, а можно взять готовым. [LiteLLM](https://docs.litellm.ai) — библиотека (и отдельный прокси-сервер), которая даёт OpenAI-подобный интерфейс `completion(model="anthropic/...", messages=...)` к десяткам провайдеров, плюс подсчёт стоимости, ретраи, фолбэки, кэширование и бюджеты. По смыслу это наш `call_llm()` из главы 2.7 (или Vercel AI SDK в мире JavaScript), доведённый до промышленного вида.

Два режима:

- **SDK** (`from litellm import completion, Router`) — внутри нашего Python-кода.
- **Proxy** — отдельный сервис с OpenAI-совместимым API: приложение ходит в него, а он — к провайдерам. Там удобны виртуальные ключи, бюджеты на ключ, общая статистика. Для одного учебного проекта избыточно, но на собеседовании полезно знать, что «LLM-гейтвей» — стандартный элемент архитектуры.

Иллюстративный пример Router с фолбэком «облако → другое облако» (точные имена моделей и формат стоит проверить в docs):

```python
import os
from litellm import Router

router = Router(
    model_list=[
        {"model_name": "primary",
         "litellm_params": {"model": "anthropic/<claude-model-id>",
                            "api_key": os.environ["ANTHROPIC_API_KEY"]}},
        {"model_name": "backup",
         "litellm_params": {"model": "openai/<gpt-model-id>",
                            "api_key": os.environ["OPENAI_API_KEY"]}},
    ],
    fallbacks=[{"primary": ["backup"]}],
    num_retries=2,
    timeout=30,
)

resp = router.completion(model="primary", messages=[{"role": "user", "content": "ping"}])
```

**Безопасность зависимости.** LiteLLM — пакет, который видит все ключи провайдеров. Такие пакеты — привлекательная цель для атак на цепочку поставок (подменённые релизы на PyPI), поэтому обращаемся с ним как с кодом с доступом к деньгам. Перед установкой: GitHub Security Advisories проекта, версия не первого дня, закреплённая в `uv.lock`, список того, что пакет тянет. Альтернатива, вполне достойная для учебного проекта: свой фолбэк на 40 строк поверх `common/llm_utils.py` из главы 2.7 (такой каркас — в разделе про DeepSeek ниже). Решение и его причину записываем в README.

### Бюджет: на ответ и на день

Последний механизм ловит то, что пропустили все предыдущие. Бюджет — это **предохранитель**, а не отчёт. У ассистента поддержки два естественных масштаба: **стоимость одного ответа** и **расход за день**. Посчитаем на примере разложения выше: `deepseek-flash` в пиковые часы (цены — в разделе про DeepSeek ниже), 8 050 токенов input (1 500 + 1 000 + 2 500 + 3 000 + 50 из схемы; первые три части, 5 000 токенов, — стабильный префикс), 300 output.

| | input, $ | output, $ | ответ, $ | 100 ответов в день, $ |
|---|---|---|---|---|
| без кэша (всё — промах) | 8 050 × 0.30 / 1M = 0.002415 | 300 × 1.20 / 1M = 0.00036 | 0.002775 | 0.28 |
| префикс 5 000 токенов в кэше | 5 000 × 0.006 / 1M + 3 050 × 0.30 / 1M = 0.000945 | 0.00036 | 0.001305 | 0.13 |

Экономия — около 53%. Суммы маленькие: лимиты защищают не от обычного трафика, а от аварии — цикла ретраев, бота-спамера, бага, из-за которого в промпт уходит вся `kb/`. Дневной лимит ставят в несколько раз выше нормы (например, $1), лимит на ответ — выше худшего нормального случая: всё промах и полный `max_tokens=600` дают 8 050 × 0.30 / 1M + 600 × 1.20 / 1M ≈ $0.0031, так что $0.01 ловит раздутый контекст или рассуждение, включённое по ошибке.

Проверяется **до** запроса:

```
перед вызовом:
  estimated   = стоимость ответа по известному input и max_tokens
  if estimated > ANSWER_LIMIT:
      не вызывать модель → записать в лог, разобраться (это баг, а не трафик)
  spent_today = SUM(cost) WHERE day = today       (из своей таблицы логов)
  if spent_today + estimated > DAILY_LIMIT:
      уведомить владельца (один раз в день) → вежливый ответ клиенту и handoff
после вызова:
  записать фактическую стоимость
  if spent_today пересёк 80% → предупреждение
```

Детали, которые отличают рабочий предохранитель от декоративного:

- Хранить расход в **персистентном** месте (SQLite, как журнал стоимости в главе 3.4), а не в переменной процесса — рестарт контейнера не должен обнулять счётчик.
- Оценивать стоимость запроса **заранее** (input известен, output ограничен `max_tokens`), иначе последний запрос может сильно превысить лимит. Для агентов — ещё и лимит на число шагов.
- Клиент при остановке видит не стектрейс, а «сейчас ответит оператор»: `handoff(question, "unavailable")`.
- Уведомление — владельцу в Telegram (chat id — в `.env`, как `OWNER_TELEGRAM_ID` в проекте 1), **один раз** на событие, иначе при остановке придёт 500 одинаковых сообщений.
- **Второй рубеж — у провайдера**: лимиты расходов в консоли Anthropic/OpenAI, лимит трат на ключ OpenRouter. В нашем коде может быть баг; лимит у провайдера от него не зависит.
- Часовой пояс «дня» — явный (UTC), иначе ограничение «скачет».

## DeepSeek и Ollama: как это сделать у нас

Всё, что выше, делаем на **DeepSeek** (облако, OpenAI-совместимый API) и **Ollama** (локально); облачный запасной — модель другого вендора через **OpenRouter** (глава 2.4, AIL-69). Факты ниже проверены по официальной документации в ноябре 2026 — цены и имена моделей у DeepSeek меняются, перед работой стоит открыть [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing).

### Кэш у DeepSeek: включать нечего, можно только не мешать

У Anthropic кэш — явная операция: ставим `cache_control`, платим за запись и получаем дешёвое чтение. У DeepSeek [context caching](https://api-docs.deepseek.com/guides/kv_cache) **включён по умолчанию у всех**: каждый запрос сам строит кэш на диске, и следующий запрос с тем же префиксом получает «cache hit». Отличия, которые меняют работу:

- **Нечего включать и нечего настраивать** — нет `cache_control`, нет TTL, нет точек разметки. Единственный рычаг тот же, что в теории выше: **порядок промпта**. Правила, few-shot и постоянные разделы `kb/` — в начало, найденные куски и вопрос — в конец, никаких timestamp в system. Это работает у всех провайдеров одинаково.
- **Нет доплаты за запись.** Промах стоит обычную цену input (cache miss), попадание — в десятки раз дешевле. Поэтому «первый запрос с кэшем дороже» (вопрос 5 теста) у DeepSeek неверно.
- **Best-effort**: документация прямо говорит, что 100% попаданий не гарантируется. Кэш строится «за секунды» и удаляется, когда не используется, — «обычно в пределах от нескольких часов до нескольких дней». Фиксированного TTL и минимальной длины в документации нет; кэш совпадает по «единицам префикса» (границы — конец каждого сообщения пользователя и ответа модели, общий префикс нескольких запросов, плюс фиксированные интервалы на длинных текстах).
- **Как проверить попадание:** в `usage` поля `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens`. В примере ответа они лежат на верхнем уровне `usage`, а в схеме API — внутри `prompt_tokens_details`; читаем оба места.
- **Anthropic-совместимый эндпоинт** `https://api.deepseek.com/anthropic`: код на `anthropic` SDK из теории запустится против DeepSeek, но `cache_control` там **игнорируется**, попадания придут в `cache_read_input_tokens`, а `cache_creation_input_tokens` — нулём ([Anthropic API](https://api-docs.deepseek.com/guides/anthropic_api)). Одинаковый интерфейс — не одинаковая семантика.

Цены (за 1M токенов, USD, на ноябрь 2026, пиковые / непиковые):

| Модель | input, cache hit | input, cache miss | output |
|---|---|---|---|
| `deepseek-flash` | $0.006 / $0.003 | $0.30 / $0.15 | $1.20 / $0.60 |
| `deepseek-v4-pro` | $0.044 / $0.022 | $1.32 / $0.66 | $3.96 / $1.98 |

У DeepSeek есть то, чего нет у Anthropic: **время суток в цене**. Пиковые часы — 01:00–04:00 и 06:00–10:00 UTC с понедельника по пятницу; в остальное время, в выходные и в китайские праздники — половина цены. Значит, формула стоимости зависит от **момента запроса**, а прогон 100 вопросов в 07:00 UTC стоит вдвое дороже того же прогона в 12:00 UTC. Сравнивая «до/после», сравниваем прогоны из одного ценового окна (или считаем обе стоимости по одному тарифу). Дневной расход ассистента тоже зависит от того, когда пишут клиенты.

```python
# common/llm_utils.py (illustrative) - DeepSeek cost with cache hit/miss and peak hours
from datetime import datetime, timezone

# USD per 1M tokens at PEAK; off-peak is half. Checked Nov 2026 - re-check the pricing page.
DEEPSEEK_PEAK = {
    "deepseek-flash":  {"hit": 0.006, "miss": 0.30, "out": 1.20},
    "deepseek-v4-pro": {"hit": 0.044, "miss": 1.32, "out": 3.96},
}

def is_peak(ts: datetime) -> bool:
    # Chinese public holidays are off-peak too; ignoring them overestimates cost slightly
    ts = ts.astimezone(timezone.utc)
    return ts.weekday() < 5 and (1 <= ts.hour < 4 or 6 <= ts.hour < 10)

def ds_cache_tokens(usage) -> tuple[int, int]:
    # the docs show these fields both at the top level and under prompt_tokens_details
    u = usage.model_dump()
    det = u.get("prompt_tokens_details") or {}
    hit = u.get("prompt_cache_hit_tokens", det.get("prompt_cache_hit_tokens")) or 0
    miss = u.get("prompt_cache_miss_tokens", det.get("prompt_cache_miss_tokens")) or 0
    return hit, miss

def deepseek_cost(model: str, usage, ts: datetime) -> float:
    p = DEEPSEEK_PEAK[model]
    k = 1.0 if is_peak(ts) else 0.5
    hit, miss = ds_cache_tokens(usage)
    return k * (hit * p["hit"] + miss * p["miss"] + usage.completion_tokens * p["out"]) / 1_000_000
```

Ещё один рычаг стоимости, специфичный для DeepSeek: **режим размышления включён по умолчанию** (effort `high`, [Thinking mode](https://api-docs.deepseek.com/guides/thinking_mode)). Рассуждение — это output-токены (видны в `completion_tokens_details.reasoning_tokens`), то есть самая дорогая часть. Для ответа поддержки по найденным кускам размышление обычно не нужно — выключаем его (как в 5.3) и проверяем evals:

```python
resp = deepseek.chat.completions.create(
    model="deepseek-flash",
    messages=messages,
    max_tokens=600,
    extra_body={"thinking": {"type": "disabled"}},  # OpenAI SDK: thinking goes in extra_body
)
```

В режиме размышления `temperature` молча **игнорируется** (без ошибки) — `temperature=0` из наших прогонов там ничего не делает.

### Фолбэк: DeepSeek → другое облако → Ollama, а для личных данных — только локально

Проще всего — своя обёртка: все три провайдера говорят на одном протоколе, отличаются только `base_url`, ключом и именем модели. Ретраи с паузой делает сам OpenAI SDK (`max_retries`), а цикл ниже — это фолбэк и circuit breaker.

```python
import os, openai
from openai import OpenAI

deepseek = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"], base_url="https://api.deepseek.com",
                  timeout=60, max_retries=2)   # explicit timeout: see the keep-alive note below
openrouter = OpenAI(api_key=os.environ["OPENROUTER_API_KEY"], base_url="https://openrouter.ai/api/v1",
                    timeout=60, max_retries=2)
ollama = OpenAI(api_key="ollama", base_url=os.environ.get("OLLAMA_BASE_URL", "http://localhost:11434/v1"),
                timeout=120, max_retries=0)    # key is ignored by Ollama

CLOUD = [("deepseek",   deepseek,   os.environ.get("ANSWER_MODEL", "deepseek-flash")),
         ("openrouter", openrouter, os.environ["ANSWER_MODEL_FALLBACK"])]  # another vendor's model
LOCAL = [("ollama",     ollama,     os.environ.get("ANSWER_MODEL_LOCAL", "qwen3:4b"))]

FALLBACK_ON = (openai.RateLimitError, openai.APITimeoutError,
               openai.APIConnectionError, openai.InternalServerError)  # 429, timeouts, network, 5xx

class NoProviderError(RuntimeError):
    pass

def chat(messages, *, private: bool, **kw):
    # private=True: the message has personal data -> local model only, never any cloud
    chain = LOCAL if private else CLOUD + LOCAL
    last_err = None
    for name, client, model in chain:
        if breaker.is_open(name):      # our circuit breaker: skip a provider that keeps failing
            continue
        try:
            resp = client.chat.completions.create(model=model, messages=messages, **kw)
            breaker.success(name)
            return name, model, resp   # log which provider actually answered
        except FALLBACK_ON as e:
            breaker.failure(name)
            last_err = e
    raise NoProviderError("no provider available") from last_err
```

В `ask()` флаг даёт проверка из 5.3, а последнее звено цепочки — человек:

```python
private = contains_personal_data(question)    # runs before any cloud call
try:
    provider, model, resp = chat(messages, private=private, max_tokens=600)
except NoProviderError:
    handoff(question, "personal_data" if private else "unavailable")
    return Answer(text=OPERATOR_MESSAGE, sources=[], refused=True, latency_ms=...)
```

Что здесь специфично для наших провайдеров:

- **Направление фолбэка — вопрос безопасности, а не только надёжности.** Цепочка «DeepSeek → другая облачная модель → Ollama» годится для вопросов о правилах: в промпт идут публичная `kb/` и вопрос без личных данных. Для сообщения, где `contains_personal_data` нашёл телефон, e-mail или номер заказа, цепочка **только локальная**: Ollama, а если она недоступна — оператор через `handoff`. Фолбэк «Ollama упала → отправим в облако» — это утечка данных клиента на чужие серверы (у DeepSeek — в Китае), которую мы сами и написали. Поэтому флаг `private` обязательный, без значения по умолчанию.
- **Облачный запасной — от другого вендора** (тот же DeepSeek через OpenRouter упадёт вместе с основным), с `data_collection: "deny"` (см. ниже). `extra_body` с `thinking` передаём только DeepSeek.
- **Ошибки DeepSeek** ([Error Codes](https://api-docs.deepseek.com/quick_start/error_codes)): 429 — превышен лимит **одновременных запросов** (лимиты на аккаунт, а не на ключ), 500 — ошибка сервера, **503 Server Overloaded** — аналог 529 у Anthropic. Это поводы для фолбэка. 400/401/422 — нет. **402 Insufficient Balance** — особый случай: это не сбой, а кончились деньги на предоплаченном балансе; фолбэк на запасного допустим, но обязательно с уведомлением владельцу, иначе ассистент неделю будет работать на запасной модели и никто не заметит.
- **Keep-alive вместо отказа.** Под нагрузкой DeepSeek не отвечает ошибкой сразу: держит соединение, отправляя пустые строки (без стриминга) или `: keep-alive` (SSE), и закрывает его, только если инференс не начался за **10 минут** ([Rate Limit](https://api-docs.deepseek.com/quick_start/rate_limit)). Без явного `timeout` в клиенте фолбэк сработает через 10 минут — клиент в Telegram-боте поддержки столько ждать не будет.
- **У Ollama нет 429 и 5xx от перегрузки провайдера** — у неё очередь: по умолчанию одна модель обрабатывает один запрос за раз (`OLLAMA_NUM_PARALLEL`, по умолчанию 1, [FAQ](https://docs.ollama.com/faq)). При переключении всего трафика на Ollama латентность растёт, поэтому у неё таймаут больше.
- **Кэш теряется при переключении** и здесь: у Ollama свой KV-кэш префикса в памяти (поле `prompt_eval_cached_count` в родном API), живёт, пока модель загружена (`keep_alive`, по умолчанию 5 минут).
- **Промпт и формат.** Локальная модель на 4B (или 7–8B на машине с 16 GB) хуже держит правила цитирования, отказ и tool calling (глава 11.4). Прогон evals на запасных моделях обязателен — это тот же пункт теории, только теперь разница качества будет большой.

**Вариант через OpenRouter** (глава 2.4 · OpenRouter: один API ко многим моделям, AIL-69): массив `models` в запросе — если первая модель вернула ошибку, OpenRouter пробует следующую ([Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks)). Платим по цене модели, которая фактически ответила (видно в поле `model` ответа), а стоимость приходит в `usage.cost` автоматически ([Usage Accounting](https://openrouter.ai/docs/guides/guides/usage-accounting)). По умолчанию фолбэк срабатывает на **любую** ошибку, включая превышение контекста и модерацию — это шире, чем правило «только 429/5xx/таймаут» выше. Из важного для приватности: в объекте `provider` есть `data_collection: "deny"` (не маршрутизировать к провайдерам, которые хранят данные и могут на них обучаться) и `zdr: true` (только endpoints с нулевым хранением) — [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection). Но OpenRouter — облако: локальную Ollama он в цепочку не поставит, а сообщения с личными данными клиентов туда тоже нельзя. И кэш DeepSeek через OpenRouter зависит от того, к какому хосту модели ушёл запрос.

**Вариант через LiteLLM:** префиксы `deepseek/<model>` (ключ из `DEEPSEEK_API_KEY`), `openrouter/<model>` и `ollama_chat/<model>` с `api_base="http://localhost:11434"` (LiteLLM рекомендует `ollama_chat/`, он ходит в `/api/chat`). Страница провайдера DeepSeek в docs LiteLLM на момент проверки показывала примеры со старыми именами моделей — стоит проверить, что встроенная таблица цен LiteLLM знает `deepseek-flash`/`deepseek-v4-pro` и учитывает пиковые часы; если нет — считаем стоимость своей функцией выше.

### Бюджет: у DeepSeek предоплата

У Anthropic и OpenAI второй рубеж — лимиты расходов в консоли, у OpenRouter — лимит трат на ключ. У DeepSeek модель другая: **предоплаченный баланс**. Когда он кончается, API отвечает 402 — это и есть жёсткий потолок, который не зависит от багов нашего кода. Практический вывод: учебный аккаунт пополняем маленькими суммами. Баланс можно читать через `GET https://api.deepseek.com/user/balance` (поля `is_available`, `balance_infos[].total_balance`, `granted_balance`, `topped_up_balance`, [Get User Balance](https://api-docs.deepseek.com/api/get-user-balance)) — удобно для ежедневной сводки владельцу в Telegram. Свой `check_budget` при этом всё равно нужен: баланс — потолок на всё, лимиты на ответ и на день — защита от того, чтобы один баг или зациклившийся агент не съел его за ночь. Отдельной настройки лимита расходов в консоли DeepSeek в документации API на момент проверки нет — стоит посмотреть в личном кабинете.

У Ollama денежного бюджета нет, но предохранитель всё равно нужен: лимит шагов агента и `max_tokens`, иначе зациклившийся агент займёт машину, на которой работают остальные сервисы магазина.

### Что брать для практики

- **Бенчмарк стоимости и кэша — на DeepSeek** (`deepseek-flash`): дешёво, и кэш работает «сам», так что измеряется эффект порядка промпта, а не правильность разметки. Вопросы — из `eval/golden.jsonl` по публичной `kb/`.
- **Запасные модели.** Для вопросов о правилах: DeepSeek → модель другого вендора через OpenRouter → Ollama. Для сообщений с личными данными: только Ollama, дальше — `handoff`.
- **Эмбеддинги для семантического кэша — Ollama** (у DeepSeek их нет), той же моделью, что индекс (`bge-m3`).
- **Судья для evals запасных моделей** — модель сильнее проверяемой: `deepseek-v4-pro` (на публичных данных) против локальной 4B; Claude — если хочется сравнить судей.
- Эксперимент с явным `cache_control` на Anthropic — опционально, «для сравнения».

## На что обратить внимание

- **Кэш «включён», но не работает.** Префикс короче минимума, в system есть timestamp, порядок tools меняется от запроса к запросу (например, их собирают из `set`), или паузы между запросами больше TTL. Диагноз — только по `usage`.
- **Экономия считается неправильно,** если формула стоимости не знает про `cache_read`/`cache_creation`. У Anthropic первый запрос с кэшем дороже, чем без (запись стоит 1.25–2× input).
- **Сравнение «до/после» на разных вопросах** ничего не значит. Один и тот же набор, одинаковый порядок, одинаковые параметры.
- **Последовательный прогон vs параллельный.** Если 100 запросов отправлены одновременно, кэш ещё не записан — все платят за запись. Сначала один «прогревающий» запрос.
- **Постоянные разделы `kb/` в префиксе устарели.** `kb/` переиндексировали, а префикс собран при старте процесса — ассистент цитирует старые тарифы. Префикс пересобирается вместе с индексом, архивные страницы в него не попадают.
- **Постоянный раздел скрывает конфликт.** `kb/delivery.md` всегда в префиксе, а `kb/promo.md` — только если его нашёл retrieval: про порог бесплатной доставки ответ может назвать одно число вместо двух. Проверяем вопросы с тегом `conflict`.
- **Фолбэк маскирует инцидент.** Если 30% запросов идёт на запасную модель, а об этом никто не знает — качество упало молча. Метрика «доля фолбэков» должна быть на дашборде из главы 11.3.
- **Ретрай не-идемпотентного.** Для чистого вопроса-ответа повтор безопасен; для агента с инструментами повтор шага может выполнить инструмент дважды. У ассистента и агента инструменты только на чтение — и это одна из причин, почему так и должно оставаться.
- **Семантический кэш без evals** — бомба: проблема всплывёт, когда клиент получит ответ про Light вместо Light Mini.
- **Бюджет в памяти процесса** обнуляется при рестарте.
- **DeepSeek: сравнение прогонов из разных ценовых окон.** Прогон в пиковые часы UTC стоит вдвое дороже — «экономия» может оказаться сменой времени суток.
- **DeepSeek: нет таймаута в клиенте.** Сервер держит соединение keep-alive до 10 минут; фолбэк без `timeout` срабатывает слишком поздно.
- **DeepSeek: размышление включено по умолчанию.** Output-токены рассуждения дорогие и не нужны для ответа по готовым кускам; `temperature` в этом режиме игнорируется молча.
- **Фолбэк в облако для личных данных.** Ollama → DeepSeek или Ollama → «другое облако» на сообщении с телефоном или номером заказа — утечка. Для них цепочка только локальная, дальше оператор.

## Ответы

1. Кэшируется префикс, а любое изменение инвалидирует всё после себя. Куски меняются от вопроса к вопросу, поэтому всё стабильное должно идти до них.
2. Стабильный префикс короче минимальной длины для модели; в префиксе есть меняющиеся данные (timestamp, id); порядок tools меняется; запросы реже TTL; неправильное место `cache_control`.
3. Текущее время в начале system делает префикс уникальным для каждого запроса — кэш всегда пишется (дороже) и никогда не читается. Дату, если нужна, — в конец, в сообщение пользователя.
4. **b.** 4xx (кроме 429) — ошибка запроса или ключа; на другом провайдере она повторится или спрячет баг.
5. Запись в кэш стоит дороже обычного input (1.25× для 5-минутного TTL у Anthropic). Экономия появляется с повторными чтениями. У DeepSeek доплаты за запись нет: промах стоит обычную цену, поэтому первый запрос не дороже.
6. «Можно ли вернуть вскрытый чай?» и «можно ли вернуть невскрытый чай?», или гарантия на Light (12 месяцев) и на Light Mini (6 месяцев) — эмбеддинги близки, ответы разные. Ещё «действует ли TEA15 со скидкой» после правки `kb/promo.md` — ответ устаревает; и ответ на вопрос с личными данными, выданный другому клиенту.
7. Рестарт или пересоздание контейнера обнулит счётчик, и лимит перестанет действовать. Расход хранится персистентно (SQLite).
8. После серии сбоев основного провайдера он временно «выключается», и запросы сразу идут в запасной, не тратя время на таймауты. Без него каждый запрос во время инцидента ждёт таймаут перед фолбэком.
9. Запасная модель может отвечать хуже или ломать формат (цитаты, отказ, tool calling). Фолбэк, качество которого неизвестно, может быть хуже честной ошибки.
10. Все запросы ушли до того, как первый записал кэш, поэтому каждый заплатил за запись. Нужен один прогревающий запрос, затем параллельные.
11. Единая точка для ключей, бюджетов на ключ/команду, логов, фолбэков и смены провайдера без правок приложения. Для одного проекта это лишний сервис в compose и ещё одна зависимость, которой доверены все ключи.
12. Через Anthropic-совместимый эндпоинт DeepSeek `cache_control` игнорируется, но кэш работает автоматически: попадания видны в `cache_read_input_tokens`, `cache_creation_input_tokens` равен нулю. Через OpenAI-совместимый — смотрим `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`.
13. Один прогон был в пиковые часы (01–04 и 06–10 UTC по будням), другой — вне их: вне пика цены у DeepSeek вдвое ниже. Сравнивать нужно прогоны из одного окна или пересчитывать по одному тарифу.
14. При сбое Ollama телефон, e-mail или номер заказа уйдут на чужие серверы (у DeepSeek — в Китае); другой провайдер — всё равно облако. Для личных данных цепочка только локальная: Ollama, затем оператор через `handoff(question, "personal_data")`. Вопрос о правилах без личных данных отвечается по публичной `kb/`, его можно отдать любой облачной модели — с evals на запасной.
15. При ожидании DeepSeek держит соединение keep-alive (пустые строки или `: keep-alive` в SSE) и закрывает его, только если инференс не начался за 10 минут. Нужен явный `timeout` в клиенте, чтобы фолбэк сработал вовремя.
