# 11.2 · Prompt caching, бюджеты, фолбэки  (AIL-45)

> **Неделя 11** · Продакшен · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Счёт за LLM растёт линейно с трафиком, а провайдеры регулярно отвечают 429 и 529. Сервис, который в эти минуты просто падает или за ночь сжигает месячный бюджет из-за зациклившегося агента, в продакшен не пускают. На собеседованиях спрашивают именно так: «как вы снизили стоимость?», «что будет, если Anthropic недоступен?», «как не допустить счёта на $5000?» — и ждут цифр и механизмов, а не «ну, мы следили».

## Теория

### Откуда берётся стоимость запроса

В AIL-5 ты считал стоимость как `input_tokens × цена_input + output_tokens × цена_output`. Для RAG-ассистента разложение обычно такое:

```
запрос к модели ≈ 4–8k токенов input
 ├─ system prompt + правила цитирования   ~1–2k   одинаковый всегда
 ├─ few-shot примеры                     ~0.5–1k  одинаковый всегда
 ├─ найденные чанки                      ~2–5k    свой у каждого вопроса
 └─ вопрос пользователя                  ~50      свой
ответ ≈ 200–500 токенов output (дороже за токен в несколько раз)
```

Отсюда три рычага: **не платить заново за одинаковое** (prompt caching), **не делать запрос вообще** (кэш ответов), **платить меньше за токен** (модель дешевле там, где хватает, — это решается evals, AIL-33). Плюс два механизма защиты: **фолбэки** (когда провайдер лежит) и **бюджет** (когда что-то пошло не так).

### Prompt caching: повторение из AIL-11 и применение к RAG

Механику ты разобрал в AIL-11; коротко напомню главное:

- Кэшируется **префикс** запроса. У Anthropic порядок префикса: `tools` → `system` → `messages`. Изменение на любом уровне инвалидирует его и всё после.
- У Anthropic кэш включается явно: `cache_control: {"type": "ephemeral"}` на блоке (до 4 точек разметки) или автоматический режим с одним полем верхнего уровня. Запись в кэш стоит дороже обычного input (для 5-минутного TTL — 1.25×, для часового — 2×), чтение — в разы дешевле (стандартно 0.1×, у части новых моделей ещё меньше). Есть **минимальная длина** кэшируемого префикса, разная для разных моделей — от сотен до нескольких тысяч токенов. Короче — кэш молча не включится, без ошибки. Точные множители и пороги смотри в документации на день работы.
- У OpenAI кэширование префиксов автоматическое для достаточно длинных промптов; сколько попало в кэш — в `usage.prompt_tokens_details.cached_tokens`.
- Проверять факт попадания — только по `usage`: `cache_creation_input_tokens` и `cache_read_input_tokens` у Anthropic. Если оба нуля — кэша не было.

**Главная мысль для RAG:** кэш работает только на одинаковом префиксе, а чанки у каждого вопроса свои. Значит, промпт надо **упорядочить** так, чтобы всё неизменное шло первым, а изменяемое — последним:

```
[tools]                      ─┐
[system: роль, правила]       │  стабильный префикс → cache_control здесь
[few-shot примеры]           ─┘
[найденные чанки]            ─┐  меняется каждый раз
[вопрос]                     ─┘
```

Типичная ошибка, которая обнуляет кэш: в system prompt подставлена текущая дата-время («Сейчас 2027-01-26 14:03:17»), id запроса или имя пользователя. Префикс меняется каждую секунду — кэш никогда не читается, зато каждый раз пишется по повышенной цене. Динамику — в конец.

Если стабильный префикс короче минимального порога, кэш в RAG ничего не даст. Это нормальный результат эксперимента, его надо так и записать. Где кэш даёт много: длинные инструкции, большая «шпаргалка» (например, справочник терминов бирж, который ты всегда подкладываешь), многоходовые диалоги в Telegram-боте (вся история — префикс следующего хода), агентский цикл из AIL-38 (каждая итерация повторяет всю историю инструментов).

Иллюстративный пример (Anthropic SDK; модель и детали параметров сверь с актуальной документацией):

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from env

STATIC_SYSTEM = open("prompts/system_rag.md").read()  # rules + few-shot, never changes

def answer(question: str, chunks: list[str], model: str):
    context = "\n\n".join(f"[{i+1}] {c}" for i, c in enumerate(chunks))
    resp = client.messages.create(
        model=model,
        max_tokens=600,
        system=[
            {"type": "text", "text": STATIC_SYSTEM,
             "cache_control": {"type": "ephemeral"}},  # breakpoint after stable prefix
        ],
        messages=[{"role": "user",
                   "content": f"Документы:\n{context}\n\nВопрос: {question}"}],
    )
    u = resp.usage
    # cache_creation_input_tokens: written now; cache_read_input_tokens: served from cache
    return resp, u.input_tokens, u.cache_creation_input_tokens, u.cache_read_input_tokens
```

Формула стоимости с кэшем (множители — из документации для выбранной модели):

```
cost = (input × P_in
      + cache_write × P_in × k_write
      + cache_read  × P_in × k_read
      + output × P_out) / 1_000_000
```

Именно её надо зашить в `llm_utils.py`, иначе ты будешь считать кэшированные токены по полной цене и не увидишь экономии.

### Кэш ответов и семантический кэш

Это другой уровень: не «дешевле обработать промпт», а «не звонить модели вообще».

**Точный кэш** — ключ = хэш от (модель, промпт, параметры). Безопасен, но в чате почти не попадает: люди формулируют по-разному. Полезен в evals и при разработке — повторный прогон того же набора стоит ноль (так, кстати, работают кэши в promptfoo).

**Семантический кэш** — ключ = эмбеддинг вопроса. Если новый вопрос близок к сохранённому (косинусная близость выше порога, AIL-18), возвращаешь сохранённый ответ.

```
вопрос → embed → поиск ближайшего в кэше
             ├─ sim ≥ 0.95 → вернуть сохранённый ответ  (0 токенов LLM)
             └─ иначе      → полный RAG → сохранить (вопрос, ответ, ts)
```

Когда уместен: FAQ-подобный трафик, где много одинаковых вопросов, ответы не зависят от времени и от пользователя (например, «какой лимит запросов у публичного API Bybit»).

Когда опасен — и это любимая тема на собеседованиях:

| Риск | Пример из твоего домена |
|---|---|
| Близкие по эмбеддингу, разные по смыслу | «комиссия maker на OKX» vs «комиссия taker на OKX»; «как открыть шорт» vs «как закрыть шорт» — косинус высокий, ответ противоположный |
| Устаревание | «текущий funding rate», «что изменилось в API» — ответ из кэша верен вчера |
| Утечка между пользователями | ответ, содержащий данные одного пользователя (его сделки из Проекта 1), выдан другому |
| Отравление кэша | prompt injection (AIL-64) заставил модель выдать мусор, и мусор теперь отдаётся всем похожим вопросам |
| Потеря трассируемости | ответ без свежих ссылок на источники ломает контракт из AIL-23 |

Отсюда правила: высокий порог, TTL, ключ включает версию индекса и id пользователя (или кэш только для обезличенных вопросов), не кэшировать отказы и ошибки, и **проверить кэш evals-набором**: перефразы должны попадать, а «ловушки» с противоположным смыслом — нет.

### LiteLLM: один интерфейс ко всем провайдерам

[LiteLLM](https://docs.litellm.ai) — библиотека (и отдельный прокси-сервер), которая даёт OpenAI-подобный интерфейс `completion(model="anthropic/...", messages=...)` к десяткам провайдеров, плюс подсчёт стоимости, ретраи, фолбэки, кэширование и бюджеты. Аналогия из Node — то, что делает Vercel AI SDK (AIL-11) или твой `ExchangeHelper` поверх ccxt: один интерфейс, разные «биржи» под ним.

Два режима:

- **SDK** (`from litellm import completion, Router`) — внутри твоего Python-кода.
- **Proxy** — отдельный сервис с OpenAI-совместимым API: приложение ходит в него, а он — к провайдерам. Там удобны виртуальные ключи, бюджеты на ключ, общая статистика. Для одного учебного проекта избыточно, но на собеседовании полезно знать, что «LLM-гейтвей» — стандартный элемент архитектуры.

Иллюстративный пример Router с фолбэком (точные имена моделей и формат проверь в docs):

```python
import os
from litellm import Router

router = Router(
    model_list=[
        {"model_name": "primary",
         "litellm_params": {"model": "anthropic/<claude-model-id>",
                            "api_key": os.environ["ANTHROPIC_API_KEY"]}},
        {"model_name": "backup",
         "litellm_params": {"model": "openai/<gpt-model-id>",
                            "api_key": os.environ["OPENAI_API_KEY"]}},
    ],
    fallbacks=[{"primary": ["backup"]}],
    num_retries=2,
    timeout=30,
)

resp = router.completion(model="primary", messages=[{"role": "user", "content": "ping"}])
```

**Безопасность зависимости.** LiteLLM — пакет, который видит все твои ключи провайдеров. Такие пакеты — привлекательная цель для атак на цепочку поставок (подменённые релизы на PyPI), поэтому относись к нему как к коду с доступом к деньгам. Перед установкой: посмотри GitHub Security Advisories проекта, выбери версию не первого дня, закрепи её в `uv.lock`, прочитай, что пакет тянет. Альтернатива, вполне достойная для учебного проекта: свой фолбэк на 40 строк поверх `llm_utils.py` из AIL-11. Решение и его причину запиши в README.

### Фолбэки: что, когда, на что

Фолбэк — не «поймать любое исключение и позвать другую модель». Правила:

- **Какие ошибки:** 429 (после ретраев), 5xx, 529 overloaded, таймаут, сетевые ошибки. **Не** 400/401/403/404 — это ошибка в твоём запросе или ключе, на другом провайдере она либо повторится, либо замаскирует баг.
- **Порядок:** сначала ретраи с экспоненциальной паузой и джиттером (AIL-11), потом фолбэк. Иначе каждый случайный 529 переключает провайдера.
- **Circuit breaker:** если основной провайдер упал 5 раз за минуту, не пытаться ещё N секунд, идти сразу в запасной. Иначе каждый запрос сначала ждёт таймаут.
- **Совместимость:** у запасной модели другой токенизатор, другое поведение в tool calling, другой стиль цитирования. Промпт может потребовать версию под каждую модель. **Прогони evals на запасной модели** — фолбэк, который отвечает плохо, хуже честной ошибки.
- **Кэш теряется:** prompt cache привязан к провайдеру и модели; после переключения первые запросы идут по полной цене.
- **Наблюдаемость:** в лог/трейс пиши, какая модель фактически ответила. Иначе в AIL-46 не поймёшь, почему подскочила стоимость.
- **Запасной может быть локальным** — Ollama из AIL-47; тогда стоимость ноль, но качество надо измерить.

### Дневной бюджет: остановка и уведомление

Бюджет — это **предохранитель**, а не отчёт. Проверяется **до** запроса:

```
перед вызовом:
  spent_today = SUM(cost) WHERE day = today       (из своей таблицы логов)
  if spent_today + estimated_cost > DAILY_LIMIT:
      уведомить (один раз в день) → отказать вежливым сообщением
после вызова:
  записать фактическую стоимость
  if spent_today пересёк 80% → предупреждение
```

Детали, которые отличают рабочий предохранитель от декоративного:

- Хранить расход в **персистентном** месте (SQLite из AIL-16), а не в переменной процесса — рестарт контейнера не должен обнулять счётчик.
- Оценивать стоимость запроса **заранее** (input известен, output ограничен `max_tokens`), иначе последний запрос может сильно превысить лимит. Для агентов — ещё и лимит на число шагов.
- Уведомление — в Telegram (у тебя уже есть бот), **один раз** на событие, иначе при остановке ты получишь 500 одинаковых сообщений. Это тот же принцип, что ты применял в арбитражном приложении для повторяющихся предупреждений.
- **Второй рубеж — у провайдера**: лимиты расходов в консоли Anthropic/OpenAI. Твой код может иметь баг; лимит в консоли — нет.
- Часовой пояс «дня» — явный (UTC), иначе ограничение «скачет».

## DeepSeek и Ollama: как это сделать у нас

Всё, что выше, ты делаешь на **DeepSeek** (облако, OpenAI-совместимый API) и **Ollama** (локально). Факты ниже проверены по официальной документации в ноябре 2026 — цены и имена моделей у DeepSeek меняются, перед работой открой [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing).

### Кэш у DeepSeek: включать нечего, можно только не мешать

У Anthropic кэш — явная операция: ты ставишь `cache_control`, платишь за запись и получаешь дешёвое чтение. У DeepSeek [context caching](https://api-docs.deepseek.com/guides/kv_cache) **включён по умолчанию у всех**: каждый запрос сам строит кэш на диске, и следующий запрос с тем же префиксом получает «cache hit». Отличия, которые меняют твою работу:

- **Нечего включать и нечего настраивать** — нет `cache_control`, нет TTL, нет точек разметки. Единственный рычаг тот же, что в теории выше: **порядок промпта**. Стабильное — в начало, чанки и вопрос — в конец, никаких timestamp в system. Это работает у всех провайдеров одинаково.
- **Нет доплаты за запись.** Промах стоит обычную цену input (cache miss), попадание — в десятки раз дешевле. Поэтому «первый запрос с кэшем дороже» (вопрос 5 теста) у DeepSeek неверно.
- **Best-effort**: документация прямо говорит, что 100% попаданий не гарантируется. Кэш строится «за секунды» и удаляется, когда не используется, — «обычно в пределах от нескольких часов до нескольких дней». Фиксированного TTL и минимальной длины в документации нет; кэш совпадает по «единицам префикса» (границы — конец каждого сообщения пользователя и ответа модели, общий префикс нескольких запросов, плюс фиксированные интервалы на длинных текстах).
- **Как проверить попадание:** в `usage` поля `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens`. В примере ответа они лежат на верхнем уровне `usage`, а в схеме API — внутри `prompt_tokens_details`; читай оба места.
- **Anthropic-совместимый эндпоинт** `https://api.deepseek.com/anthropic`: твой код на `anthropic` SDK из теории запустится против DeepSeek, но `cache_control` там **игнорируется**, попадания придут в `cache_read_input_tokens`, а `cache_creation_input_tokens` — нулём ([Anthropic API](https://api-docs.deepseek.com/guides/anthropic_api)). Хороший урок: одинаковый интерфейс не значит одинаковую семантику.

Цены (за 1M токенов, USD, на ноябрь 2026, пиковые / непиковые):

| Модель | input, cache hit | input, cache miss | output |
|---|---|---|---|
| `deepseek-flash` | $0.006 / $0.003 | $0.30 / $0.15 | $1.20 / $0.60 |
| `deepseek-v4-pro` | $0.044 / $0.022 | $1.32 / $0.66 | $3.96 / $1.98 |

У DeepSeek есть то, чего нет у Anthropic: **время суток в цене**. Пиковые часы — 01:00–04:00 и 06:00–10:00 UTC с понедельника по пятницу; в остальное время, в выходные и в китайские праздники — половина цены. Значит, формула стоимости зависит от **момента запроса**, а прогон 100 вопросов в 07:00 UTC стоит вдвое дороже того же прогона в 12:00 UTC. Сравнивая «до/после», сравнивай прогоны из одного ценового окна (или считай обе стоимости по одному тарифу).

```python
# llm_utils.py (illustrative) - DeepSeek cost with cache hit/miss and peak hours
from datetime import datetime, timezone

# USD per 1M tokens at PEAK; off-peak is half. Checked Nov 2026 - re-check the pricing page.
DEEPSEEK_PEAK = {
    "deepseek-flash":  {"hit": 0.006, "miss": 0.30, "out": 1.20},
    "deepseek-v4-pro": {"hit": 0.044, "miss": 1.32, "out": 3.96},
}

def is_peak(ts: datetime) -> bool:
    # Chinese public holidays are off-peak too; ignoring them overestimates cost slightly
    ts = ts.astimezone(timezone.utc)
    return ts.weekday() < 5 and (1 <= ts.hour < 4 or 6 <= ts.hour < 10)

def ds_cache_tokens(usage) -> tuple[int, int]:
    # the docs show these fields both at the top level and under prompt_tokens_details
    u = usage.model_dump()
    det = u.get("prompt_tokens_details") or {}
    hit = u.get("prompt_cache_hit_tokens", det.get("prompt_cache_hit_tokens")) or 0
    miss = u.get("prompt_cache_miss_tokens", det.get("prompt_cache_miss_tokens")) or 0
    return hit, miss

def deepseek_cost(model: str, usage, ts: datetime) -> float:
    p = DEEPSEEK_PEAK[model]
    k = 1.0 if is_peak(ts) else 0.5
    hit, miss = ds_cache_tokens(usage)
    return k * (hit * p["hit"] + miss * p["miss"] + usage.completion_tokens * p["out"]) / 1_000_000
```

Ещё один рычаг стоимости, специфичный для DeepSeek: **режим размышления включён по умолчанию** (effort `high`, [Thinking mode](https://api-docs.deepseek.com/guides/thinking_mode)). Рассуждение — это output-токены (видны в `completion_tokens_details.reasoning_tokens`), то есть самая дорогая часть. Для RAG-ответа по найденным чанкам размышление обычно не нужно — выключи его и проверь evals:

```python
resp = deepseek.chat.completions.create(
    model="deepseek-flash",
    messages=messages,
    max_tokens=600,
    extra_body={"thinking": {"type": "disabled"}},  # OpenAI SDK: thinking goes in extra_body
)
```

В режиме размышления `temperature` молча **игнорируется** (без ошибки) — `temperature=0` из твоих прогонов там ничего не делает.

### Фолбэк DeepSeek → Ollama

Проще всего — своя обёртка: оба провайдера говорят на одном протоколе, отличаются только `base_url` и именем модели. Ретраи с паузой делает сам OpenAI SDK (`max_retries`), а цикл ниже — это фолбэк и circuit breaker.

```python
import os, openai
from openai import OpenAI

deepseek = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"], base_url="https://api.deepseek.com",
                  timeout=60, max_retries=2)   # explicit timeout: see the keep-alive note below
ollama = OpenAI(api_key="ollama", base_url=os.environ.get("OLLAMA_BASE_URL", "http://localhost:11434/v1"),
                timeout=120, max_retries=0)    # key is ignored by Ollama

CHAIN = [("deepseek", deepseek, os.environ.get("DEEPSEEK_MODEL", "deepseek-flash")),
         ("ollama",   ollama,   os.environ["OLLAMA_MODEL"])]   # a tag from `ollama list`

FALLBACK_ON = (openai.RateLimitError, openai.APITimeoutError,
               openai.APIConnectionError, openai.InternalServerError)  # 429, timeouts, network, 5xx

def chat(messages, *, private: bool, **kw):
    # private=True: real trading data -> local model only, never a cloud fallback
    chain = [c for c in CHAIN if c[0] == "ollama"] if private else CHAIN
    last_err = None
    for name, client, model in chain:
        if breaker.is_open(name):      # your circuit breaker: skip a provider that keeps failing
            continue
        try:
            resp = client.chat.completions.create(model=model, messages=messages, **kw)
            breaker.success(name)
            return name, model, resp   # log which provider actually answered
        except FALLBACK_ON as e:
            breaker.failure(name)
            last_err = e
    raise last_err or RuntimeError("no provider available")
```

Что здесь специфично для наших провайдеров:

- **Направление фолбэка — вопрос безопасности, а не только надёжности.** Цепочка «DeepSeek → Ollama» годится для публичных доков бирж. Для всего, что видит твои сделки (бот из Проекта 1, агент из Проекта 4), цепочка **только локальная**: Ollama или честная ошибка. Фолбэк «Ollama упала → отправим в облако» — это утечка данных на серверы в Китае, которую ты сам и написал. Поэтому флаг `private` обязательный, без значения по умолчанию.
- **Ошибки DeepSeek** ([Error Codes](https://api-docs.deepseek.com/quick_start/error_codes)): 429 — превышен лимит **одновременных запросов** (лимиты на аккаунт, а не на ключ), 500 — ошибка сервера, **503 Server Overloaded** — аналог 529 у Anthropic. Это поводы для фолбэка. 400/401/422 — нет. **402 Insufficient Balance** — особый случай: это не сбой, а кончились деньги на предоплаченном балансе; фолбэк на Ollama допустим, но обязательно с уведомлением, иначе ты неделю будешь работать на локальной модели и не заметишь.
- **Keep-alive вместо отказа.** Под нагрузкой DeepSeek не отвечает ошибкой сразу: держит соединение, отправляя пустые строки (без стриминга) или `: keep-alive` (SSE), и закрывает его, только если инференс не начался за **10 минут** ([Rate Limit](https://api-docs.deepseek.com/quick_start/rate_limit)). Без явного `timeout` в клиенте твой фолбэк сработает через 10 минут — пользователь Telegram-бота столько ждать не будет.
- **У Ollama нет 429 и 5xx от перегрузки провайдера** — у неё очередь: по умолчанию одна модель обрабатывает один запрос за раз (`OLLAMA_NUM_PARALLEL`, по умолчанию 1, [FAQ](https://docs.ollama.com/faq)). При переключении всего трафика на Ollama латентность растёт, поэтому у неё таймаут больше.
- **Кэш теряется при переключении** и здесь: у Ollama свой KV-кэш префикса в памяти (поле `prompt_eval_cached_count` в родном API), живёт, пока модель загружена (`keep_alive`, по умолчанию 5 минут).
- **Промпт и формат.** Локальная 7–8B модель хуже держит правила цитирования и tool calling (глава 11.4). Прогон evals на запасной модели обязателен — это тот же пункт теории, только теперь разница качества будет большой.

**Вариант через OpenRouter** (глава 2.4 · OpenRouter: один API ко многим моделям, AIL-69): массив `models` в запросе — если первая модель вернула ошибку, OpenRouter пробует следующую ([Model Fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks)). Платишь по цене модели, которая фактически ответила (видно в поле `model` ответа), а стоимость приходит в `usage.cost` автоматически ([Usage Accounting](https://openrouter.ai/docs/guides/guides/usage-accounting)). По умолчанию фолбэк срабатывает на **любую** ошибку, включая превышение контекста и модерацию — это шире, чем правило «только 429/5xx/таймаут» выше. Из важного для приватности: в объекте `provider` есть `data_collection: "deny"` (не маршрутизировать к провайдерам, которые хранят данные и могут на них обучаться) и `zdr: true` (только endpoints с нулевым хранением) — [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection). Но OpenRouter — облако: локальную Ollama он в цепочку не поставит, а реальные данные туда тоже нельзя. И кэш DeepSeek через OpenRouter зависит от того, к какому хосту модели ушёл запрос.

**Вариант через LiteLLM:** префиксы `deepseek/<model>` (ключ из `DEEPSEEK_API_KEY`) и `ollama_chat/<model>` с `api_base="http://localhost:11434"` (LiteLLM рекомендует `ollama_chat/`, он ходит в `/api/chat`). Страница провайдера DeepSeek в docs LiteLLM на момент проверки показывала примеры со старыми именами моделей — проверь, что встроенная таблица цен LiteLLM знает `deepseek-flash`/`deepseek-v4-pro` и учитывает пиковые часы; если нет — считай стоимость своей функцией выше.

### Бюджет: у DeepSeek предоплата

У Anthropic и OpenAI второй рубеж — лимиты расходов в консоли. У DeepSeek модель другая: **предоплаченный баланс**. Когда он кончается, API отвечает 402 — это и есть жёсткий потолок, который не зависит от багов твоего кода. Практический вывод: пополняй учебный аккаунт маленькими суммами. Баланс можно читать через `GET https://api.deepseek.com/user/balance` (поля `is_available`, `balance_infos[].total_balance`, `granted_balance`, `topped_up_balance`, [Get User Balance](https://api-docs.deepseek.com/api/get-user-balance)) — удобно для ежедневной сводки в Telegram. Свой `check_budget` при этом всё равно нужен: баланс — потолок на всё, дневной лимит — защита от того, чтобы один зациклившийся агент не съел его за ночь. Отдельной настройки лимита расходов в консоли DeepSeek я в документации API не нашёл — проверь в личном кабинете.

У Ollama денежного бюджета нет, но предохранитель всё равно нужен: лимит шагов агента и `max_tokens`, иначе зациклившийся агент займёт Мак, на котором работает торговое приложение.

### Что брать для практики

- **Бенчмарк стоимости и кэша — на DeepSeek** (`deepseek-flash`): дешёво, и кэш у него работает «сам», так что ты измеряешь эффект порядка промпта, а не правильность разметки. Вопросы — из eval-набора по **публичным** докам бирж; ничего из твоей базы, логов и ключей в DeepSeek не уходит.

## На что обратить внимание

- **Кэш «включён», но не работает.** Префикс короче минимума, в system есть timestamp, порядок tools меняется от запроса к запросу (например, собираешь их из `set`), или паузы между запросами больше TTL. Диагноз — только по `usage`.
- **Экономия считается неправильно,** если формула стоимости не знает про `cache_read`/`cache_creation`. Первый запрос с кэшем дороже, чем без.
- **Сравнение «до/после» на разных вопросах** ничего не значит. Один и тот же набор, одинаковый порядок, одинаковые параметры.
- **Последовательный прогон vs параллельный.** Если 100 запросов отправлены одновременно, кэш ещё не записан — все платят за запись. Сначала один «прогревающий» запрос.
- **Фолбэк маскирует инцидент.** Если 30% запросов идёт на запасную модель, а ты не знаешь — качество упало молча. Метрика «доля фолбэков» должна быть на дашборде AIL-46.
- **Ретрай не-идемпотентного.** Для чистого вопроса-ответа повтор безопасен; для агента с инструментами повтор шага может выполнить инструмент дважды. У тебя инструменты только на чтение — и это одна из причин, почему так и должно оставаться.
- **Семантический кэш без evals** — бомба: проблема всплывёт, когда пользователь получит ответ на чужой вопрос.
- **Бюджет в памяти процесса** обнуляется при рестарте.
- **DeepSeek: сравнение прогонов из разных ценовых окон.** Прогон в пиковые часы UTC стоит вдвое дороже — «экономия» может оказаться сменой времени суток.
- **DeepSeek: нет таймаута в клиенте.** Сервер держит соединение keep-alive до 10 минут; фолбэк без `timeout` срабатывает слишком поздно.
- **DeepSeek: размышление включено по умолчанию.** Output-токены рассуждения дорогие и не нужны для ответа по готовым чанкам; `temperature` в этом режиме игнорируется молча.
- **Фолбэк в облако для приватных данных.** Ollama → DeepSeek на данных сделок — утечка. Для них цепочка только локальная.
- **«Кэш DeepSeek — значит, порядок промпта не важен».** Важен: кэш совпадает только по префиксу, timestamp в system обнуляет его так же, как у Anthropic.

## Практика

## Ответы

1. Кэшируется префикс, а любое изменение инвалидирует всё после себя. Чанки меняются от вопроса к вопросу, поэтому всё стабильное должно идти до них.
2. Стабильный префикс короче минимальной длины для модели; в префиксе есть меняющиеся данные (timestamp, id); порядок tools меняется; запросы реже TTL; неправильное место `cache_control`.
3. Текущее время в начале system делает префикс уникальным для каждого запроса — кэш всегда пишется (дороже) и никогда не читается. Дату, если нужна, — в конец, в сообщение пользователя.
4. b. 4xx (кроме 429) — ошибка запроса или ключа; на другом провайдере она повторится или спрячет баг.
5. Запись в кэш стоит дороже обычного input (1.25× для 5-минутного TTL у Anthropic). Экономия появляется с повторными чтениями. У DeepSeek доплаты за запись нет: промах стоит обычную цену, поэтому первый запрос не дороже.
6. «Комиссия maker на OKX» и «комиссия taker на OKX», или «как открыть шорт» и «как закрыть шорт» — эмбеддинги близки, ответы разные. Ещё «текущий funding rate» — ответ устаревает.
7. Рестарт или пересоздание контейнера обнулит счётчик, и лимит перестанет действовать. Расход хранится персистентно (SQLite).
8. После серии сбоев основного провайдера он временно «выключается», и запросы сразу идут в запасной, не тратя время на таймауты. Без него каждый запрос во время инцидента ждёт таймаут перед фолбэком.
9. Запасная модель может отвечать хуже или ломать формат (цитаты, tool calling). Фолбэк, качество которого неизвестно, может быть хуже честной ошибки.
10. Все запросы ушли до того, как первый записал кэш, поэтому каждый заплатил за запись. Нужен один прогревающий запрос, затем параллельные.
11. Единая точка для ключей, бюджетов на ключ/команду, логов, фолбэков и смены провайдера без правок приложения. Для одного проекта это лишний сервис в compose и ещё одна зависимость, которой доверены все ключи.
12. Через Anthropic-совместимый эндпоинт DeepSeek `cache_control` игнорируется, но кэш работает автоматически: попадания видны в `cache_read_input_tokens`, `cache_creation_input_tokens` равен нулю. Через OpenAI-совместимый — смотри `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`.
13. Один прогон был в пиковые часы (01–04 и 06–10 UTC по будням), другой — вне их: вне пика цены у DeepSeek вдвое ниже. Сравнивать нужно прогоны из одного окна или пересчитывать по одному тарифу.
14. Фолбэк в облако отправит реальные данные сделок на серверы DeepSeek в Китае. Для приватных данных цепочка только локальная: Ollama или честная ошибка пользователю.
15. При ожидании DeepSeek держит соединение keep-alive (пустые строки или `: keep-alive` в SSE) и закрывает его, только если инференс не начался за 10 минут. Нужен явный `timeout` в клиенте, чтобы фолбэк сработал вовремя.
