## Зачем это AI-инженеру

Довести проект до состояния «не стыдно показать». Работодатель открывает репозиторий на две минуты: README, схема, как запустить, сколько стоит ответ. Строка «средняя стоимость ответа $0.004, 2.1 инструмента на вопрос» говорит о тебе больше, чем любой красивый промпт: значит, ты думаешь о продакшене. А логи каждого запроса — фундамент для evals и мониторинга, к которым ты вернёшься в этапах 3 и 5.

⚠️ Публичный репозиторий — **только фейковые данные**. Реальные цифры сделок не должны попасть в него ни файлом, ни скриншотом, ни строчкой README, ни логом.

## Теория

### 1. Что логировать и зачем

Один запрос пользователя — это не один вызов API, а цикл из 1–5 шагов (AIL-15). Логировать нужно **на двух уровнях**:

| Уровень | Поля | Зачем |
|---|---|---|
| Шаг (вызов LLM) | модель, input/output токены, cache-токены, `stop_reason`, длительность | понять, какой шаг дорогой |
| Запрос (вопрос → ответ) | время, `request_id`, вопрос, вызванные инструменты с аргументами, сумма токенов, стоимость, полное время ответа, число шагов, статус (ok / error / max_steps), длина ответа | `/stats`, README, отладка, будущие evals |

Пример записи запроса (JSON Lines — один JSON на строку):

```json
{"ts": "2026-12-04T10:15:02+00:00", "request_id": "a1b2c3", "question": "какой PnL за неделю?",
 "tools": [{"name": "get_pnl", "args": {"period": "week"}, "ms": 4, "chars": 312}],
 "steps": 2, "input_tokens": 2841, "output_tokens": 96, "cache_read_tokens": 0,
 "cost_usd": 0.0099, "latency_ms": 3120, "status": "ok", "model": "<model-id>"}
```

Почему JSONL: дописывается одной строкой, не ломается при падении процесса посреди записи (испортится максимум последняя строка), читается и `jq`, и `pandas.read_json(..., lines=True)`, и десятью строками Python. Альтернатива — отдельная SQLite-база `logs/requests.db` с таблицей `requests`: удобнее для `/stats` через SQL. Обе нормальны; **главное — это отдельный файл, а не таблица в копии торговой базы**: копия открыта только на чтение и должна такой остаться.

### 2. Стоимость

Ты уже написал `estimate_cost(model, input_tokens, output_tokens)` в AIL-5 и подсчёт usage в `call_llm()` в AIL-11. Здесь две тонкости:

1. **Стоимость запроса = сумма по всем шагам.** На каждом шаге модель заново читает системный промпт, схемы инструментов, историю и все предыдущие результаты. Поэтому второй шаг почти всегда дороже первого по input-токенам.
2. **Кэш оплачивается иначе.** Если ты включил prompt caching (AIL-11), в `usage` будут отдельные поля для записи в кэш и чтения из кэша (`cache_creation_input_tokens`, `cache_read_input_tokens` у Anthropic), и у них свои цены. Учитывай их в `estimate_cost`, иначе стоимость будет завышена или занижена.

Цены меняются — не зашивай их «по памяти». Держи словарь цен в `bot/pricing.py` с комментарием «checked on YYYY-MM-DD, source: pricing page» и ссылкой на актуальную страницу цен провайдера. В README пиши «≈ $X за ответ на модели Y по ценам на дату Z».

Пример расчёта (цены условные, для арифметики): шаг 1 — 2000 input + 60 output, шаг 2 — 2400 input + 120 output. При $3 / 1M input и $15 / 1M output: `(4400 × 3 + 180 × 15) / 1 000 000 = $0.0159`. Видно, что output-токенов мало, а платишь в основном за повторное чтение контекста — вот почему компактные результаты инструментов из AIL-14 экономят деньги.

### 3. Время ответа

Мерь `time.perf_counter()` — монотонные часы, не `time.time()`. Три числа:

- полное время запроса (от получения сообщения до отправки ответа) — то, что чувствует пользователь;
- время каждого вызова LLM — обычно 90% общего;
- время каждого инструмента — должно быть миллисекунды; если сотни мс — нет индекса или функция тянет лишнее.

Для статистики полезны не только среднее, но и медиана и p95: один запрос с ретраем на 40 секунд испортит среднее, а p95 покажет, как часто так бывает.

### 4. Как встроить логирование, не замусорив код

Собирай метаданные в объекте, который проходит через цикл, и пиши запись **один раз в конце**, в `finally`, — тогда упавшие запросы тоже попадут в лог:

```python
# bot/agent.py (illustrative)
async def answer(question: str, history: list[dict]) -> AgentResult:
    trace = RequestTrace(question=question)           # dataclass with counters
    started = time.perf_counter()
    try:
        ...                                           # loop from AIL-15
        # after each call_llm: trace.add_step(resp.usage, step_ms, resp.model)
        # after each tool:     trace.add_tool(name, args, tool_ms, len(content))
        trace.status = "ok"
        return result
    except Exception:
        trace.status = "error"
        raise
    finally:
        trace.latency_ms = int((time.perf_counter() - started) * 1000)
        trace.cost_usd = trace.total_cost()           # uses estimate_cost per step
        write_jsonl(LOG_PATH, trace.to_dict())
```

Ошибка записи лога не должна ронять ответ пользователю: оберни `write_jsonl` в `try/except` с `log.exception`.

### 5. `/stats`

Команда для владельца, читает лог и отвечает текстом:

```
Запросов: 47 (сегодня 6)
Потрачено: $0.41 (сегодня $0.05)
Средняя стоимость ответа: $0.0087, медиана $0.0071
Время ответа: медиана 2.8 с, p95 7.9 с
Инструментов на вопрос: 1.6; чаще всего get_pnl (21)
Ошибок: 2
```

Логика — чистая функция `compute_stats(records, now, tz) -> Stats` с тестом pytest на 5 ручных записях; хендлер только читает файл и форматирует. «Сегодня» — в твоём часовом поясе, как и в AIL-15.

### 6. Демо-режим

Одна кодовая база, два источника данных — переключение через переменные окружения, без `if demo:` по коду:

```
TRADES_DB_PATH=data/demo_trades.db
CHARTS_DB_PATH=data/demo_charts.db
LOG_PATH=logs/demo-requests.jsonl
```

Демо-база создаётся `scripts/make_fake_db.py` (AIL-14). Всё, что попадает в README — скриншот диалога, пример ответа, цифры стоимости — снимается **в демо-режиме**. Стоимость на демо-базе будет близка к реальной: размер контекста зависит от схем и промпта, а не от цифр в сделках.

Удобно добавить в `/start` строку «режим: DEMO» — как DEMO/PROD в шапке твоего приложения, чтобы на скриншоте было видно, что данные фейковые.

Структура:

### 8. Чистота публичного репозитория

Перед тем как сделать репозиторий публичным:

- `git ls-files` — нет `*.db`, `.env`, `logs/`, `data/`;
- `git log --all --stat -- '*.db' '*.jsonl' '.env'` — этих файлов не было и в истории. Если были — проще создать новый репозиторий с чистой историей, чем вычищать старую;
- поиск по коду на ключи и токены: `git grep -nE "sk-|ANTHROPIC_API_KEY=.+|[0-9]{8,10}:[A-Za-z0-9_-]{30,}"` (последнее — формат токена Telegram);
- в `.env.example` только имена переменных;
- скриншоты: демо-режим, нет твоего ID, имени, реальных цифр;
- `questions.md` и примеры ответов — на демо-базе.

В настройках GitHub есть secret scanning и push protection — включи их для репозитория, но относись как ко второй сетке, не первой.

## DeepSeek и Ollama: как это сделать у нас

### Одна запись лога — четыре формата usage

Каждый провайдер отдаёт токены по-своему, и самая частая ошибка — сложить поля, которые уже включают друг друга. Приводи всё к одному виду сразу после вызова: `Usage(input_total, input_cached, output)`.

| Провайдер | Все входные токены | Из них из кэша | Выходные | Особенность |
|---|---|---|---|---|
| Claude | `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` | `cache_read_input_tokens` | `output_tokens` | `input_tokens` **не включает** кэш; запись в кэш дороже обычного input |
| OpenAI | `prompt_tokens` | `prompt_tokens_details.cached_tokens` | `completion_tokens` | кэш **включён** в `prompt_tokens` |
| DeepSeek | `prompt_tokens` (= `prompt_cache_hit_tokens + prompt_cache_miss_tokens`) | `prompt_cache_hit_tokens` | `completion_tokens` | кэш автоматический, без параметров; размышления — в `completion_tokens_details.reasoning_tokens` (у бота thinking выключен) |
| Ollama, нативный `/api/chat` | `prompt_eval_count` | — | `eval_count` | плюс длительности в **наносекундах**: `total_duration`, `load_duration`, `prompt_eval_duration`, `eval_duration` |
| Ollama, `/v1` | `usage` в формате OpenAI | — | | в доке совместимости явно описан только `stream_options.include_usage` для стриминга; проверь на первом запросе, что в обычном ответе `resp.usage` заполнен, иначе бери числа из нативного API |

```python
# bot/usage.py (illustrative)
from dataclasses import dataclass

@dataclass
class Usage:
    input_total: int
    input_cached: int
    output: int

def from_deepseek(u) -> Usage:
    return Usage(u.prompt_tokens, getattr(u, "prompt_cache_hit_tokens", 0) or 0,
                 u.completion_tokens)

def from_ollama_native(r: dict) -> Usage:
    return Usage(r.get("prompt_eval_count", 0), 0, r.get("eval_count", 0))
```

Тест на каждый адаптер — на записанном вручную фейковом объекте usage (без сети).

### Стоимость: у DeepSeek три цены и время суток

Цены DeepSeek на ноябрь 2026 ([Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing)), USD за 1M токенов:

| `deepseek-flash` | Ночные (off-peak) | Пиковые |
|---|---|---|
| Input, попадание в кэш | 0.003 | 0.006 |
| Input, промах кэша | 0.15 | 0.30 |
| Output | 0.60 | 1.20 |

Пик — 01:00–04:00 и 06:00–10:00 UTC по будням, кроме китайских праздников; в остальное время цены вдвое ниже. У `deepseek-v4-pro` цены в несколько раз выше — смотри ту же страницу. DeepSeek прямо пишет, что цены может менять, поэтому дата проверки в `pricing.py` обязательна.

```python
# bot/pricing.py (illustrative)
# checked on 2026-11-13, source: https://api-docs.deepseek.com/quick_start/pricing
DEEPSEEK_PRICES = {  # USD per 1M tokens
    "deepseek-flash": {
        "off_peak": {"hit": 0.003, "miss": 0.15, "out": 0.60},
        "peak":     {"hit": 0.006, "miss": 0.30, "out": 1.20},
    },
}

def deepseek_is_peak(ts_utc) -> bool:
    # Mon-Fri 01:00-04:00 and 06:00-10:00 UTC; Chinese public holidays not modelled
    return ts_utc.weekday() < 5 and (1 <= ts_utc.hour < 4 or 6 <= ts_utc.hour < 10)

def deepseek_cost(model: str, u: Usage, ts_utc) -> float:
    p = DEEPSEEK_PRICES[model]["peak" if deepseek_is_peak(ts_utc) else "off_peak"]
    miss = u.input_total - u.input_cached
    return (u.input_cached * p["hit"] + miss * p["miss"] + u.output * p["out"]) / 1_000_000
```

По какому моменту запроса (начало или конец) DeepSeek относит его к пику, в документации не указано (проверено в ноябре 2026) — для оценки в README это неважно, но не жди совпадения с биллингом до цента.

Тот же пример, что в теории (шаг 1: 2000 input + 60 output, шаг 2: 2400 input + 120 output), на `deepseek-flash` ночью, если на втором шаге 2000 токенов префикса попали в кэш: `(2400 × 0.15 + 2000 × 0.003 + 180 × 0.60) / 1 000 000 ≈ $0.00047` — примерно в 30 раз дешевле условных $3/$15. Попадание в кэш не гарантировано: DeepSeek описывает кэш как best effort, поэтому логируй `input_cached` и смотри реальную долю в `/stats`.

**Ollama:** `cost_usd = 0`, но запись в логе всё равно нужна — у локальной модели «стоимость» это время и память. Логируй `latency_ms`, токены и скорость генерации `eval_count / eval_duration × 1e9` (токенов в секунду), а в `/stats` показывай медиану и p95 времени ответа по модели. Первый запрос после простоя включает `load_duration` — загрузку модели в память; отделяй его, иначе медиана будет врать.

### README: раздел «Модели и приватность»

Для работодателя это сильный пункт — ты подумал, куда уходят данные. Пример:

> Реальные данные обрабатываются только локальной моделью через Ollama (`qwen3:4b-instruct-2507-q4_K_M`), запрос не покидает машину. Облачные модели (DeepSeek) подключаются только к сгенерированной демо-базе; бот отказывается стартовать с облачным провайдером и реальной базой (`assert_data_policy`). Провайдер переключается переменными окружения, код один — OpenAI-совместимый клиент.

Плюс в «Стоимость и качество» — две строки: DeepSeek на демо (`$X` за ответ, цены на дату), Ollama (медиана N с на M2 8 ГБ), и «N из 15» для обеих. Цифры «12 из 15 на реальной копии» можно указать числом, без самих вопросов и ответов.

## На что обратить внимание

- **Лог содержит реальные вопросы и ответы с твоими цифрами** → `logs/` в `.gitignore`; демо пишет в отдельный файл.
- **Не логируй секреты**: заголовки запросов, ключи, полные объекты клиента. Логируй usage и метаданные, а не «весь `resp`».
- **Стоимость только последнего шага** вместо суммы — классическая ошибка: цифра в README окажется в 2–3 раза ниже реальной.
- **`time.time()` для длительностей** может прыгать при синхронизации часов; `perf_counter()` — нет.
- **Падение записи лога роняет ответ** — `try/except` вокруг записи.
- **`/stats` доступен только владельцу** — он стоит под тем же фильтром роутера из AIL-15. Проверь, что ты не повесил его на отдельный роутер без фильтра.
- **Устаревшие цены.** Через полгода README будет врать, если не указать дату и модель.
- **README, который работает только у тебя**: абсолютные пути, забытая зависимость, неявная версия Python, шаг «скопируй базу из моего приложения». В публичном README базы приложения нет вообще — только `make_fake_db.py`.
- **История git помнит всё.** Удалить файл последним коммитом недостаточно.
- **Двойной счёт кэша.** У OpenAI и DeepSeek кэш уже внутри `prompt_tokens`, у Anthropic — нет. Прибавишь `prompt_cache_hit_tokens` к `prompt_tokens` — стоимость завысится.
- **Ночная цена DeepSeek в README.** Если замерил ночью — так и напиши, днём (в пик) та же нагрузка стоит вдвое дороже.
- **Медиана Ollama с холодным стартом.** Первый запрос после простоя включает загрузку модели; без пометки `cold_start` в логе статистика времени смешает два разных режима.

## Ответы

1. **c.** Каждый шаг заново оплачивает весь контекст; cache-токены тарифицируются отдельно.
2. Дописывается по строке, падение процесса портит максимум последнюю строку, легко читается построчно Python, `jq`, pandas.
3. `time.time()` вместо `perf_counter()`; нет перевода строки — записи слипнутся в одну строку; `json.dumps` без `ensure_ascii=False`; не записываются инструменты, токены, статус; при исключении в `answer` запись не происходит (нет `finally`).
4. Тогда запросы, упавшие с исключением, тоже попадают в лог — а именно они нужнее всего для отладки и статистики ошибок.
5. **b.** Копия торговой базы открыта только на чтение и должна такой остаться; журнал — отдельный файл.
6. Стоимость определяется размером контекста (системный промпт, схемы, история, компактные результаты) и числом шагов, а не конкретными цифрами в сделках; структура данных та же.
7. Нет: файл остаётся в истории git. Нужно переписать историю или проще — создать новый репозиторий с чистой историей.
8. Цены и модели меняются; без даты и модели цифра через несколько месяцев вводит в заблуждение.
9. Редкие долгие запросы (ретраи, таймауты) сильно сдвигают среднее; медиана показывает типичный опыт, p95 — насколько часто бывает плохо.
10. Включён демо-режим и цифры фейковые; нет твоего имени, ID и личных данных; нет токенов, путей и прочих технических секретов в кадре.
11. Клонировать в чистую папку, новое окружение, выполнить README дословно до работающего бота и зелёного `pytest`; всё, что потребовало знаний вне README, — исправить.
12. `prompt_tokens` уже включает попадания в кэш — их посчитали дважды; токены из кэша надо брать по цене hit, а по цене miss — только `prompt_tokens − prompt_cache_hit_tokens`; цены зашиты числами без даты и без учёта пика (днём вдвое дороже).
13. У локальной модели «стоимость» — время и память: журнал даёт медиану и p95 времени ответа, скорость генерации, холодные старты, ошибки и вызванные инструменты — и это всё ещё основа для evals.
14. С реальной копией работает только Ollama — её результат «N из 15» на копии можно указать числом (без самих данных). DeepSeek реальную копию не видит никогда, его цифры — только с демо-базы.
