# 3.1 · Проект 1: архитектура бота и копия базы  (AIL-13)

> **Неделя 3** · Основы LLM · ⏱ ~4 ч · Проект

## Зачем это AI-инженеру

Это первый проект в портфолио: Telegram-бот, который отвечает на вопросы о твоих сделках через tool calling. На собеседовании про такой проект спросят не «какой промпт», а «как ты не дал модели сделать что-то опасное» и «откуда она берёт данные». Сегодня ты закладываешь ответы на оба вопроса: модель видит данные только через функции, функции видят только копию базы, а копия открыта только на чтение.

⚠️ **Только чтение.** Никаких функций, которые ставят или отменяют ордера, и никаких запросов к биржам с ключами — только копия базы.

## Теория

### 1. Что мы строим и чего не строим

Бот — это «аналитик», а не «трейдер». Он умеет ровно одно: превратить вопрос на естественном языке («какой PnL за неделю?») в вызов одной или нескольких читающих функций и пересказать результат человеческим языком. Всё, что может изменить состояние мира — ордера, отмены, переключатели авто-торговли, запросы к биржам с ключами, — в проекте отсутствует физически, а не «запрещено промптом». Промпт — это просьба, а не защита: модель можно уговорить, сбить с толку длинной историей, или она просто ошибётся. Защита — это архитектура, в которой опасного действия нет в коде.

Принцип, который стоит запомнить на всю карьеру: **у LLM ровно те права, которые есть у функций, которые ты ей дал**. Хочешь, чтобы модель не могла удалить данные — не давай ей функцию с `DELETE` и не открывай базу на запись.

### 2. Архитектура

```
 Telegram (ты)
     │  сообщение
     ▼
 ┌──────────────┐   не твой user_id → отказ
 │ aiogram bot  │
 └──────┬───────┘
        │ вопрос + история + системный промпт с датой
        ▼
 ┌──────────────┐  tool_use: get_pnl(period="week")
 │  call_llm()  │◄──────────────────────────────┐
 │ (Ollama/DS)  │──────────┐                    │
 └──────────────┘          ▼                    │ tool_result (компактный JSON)
                    ┌─────────────────┐         │
                    │  tools.py       │─────────┘
                    │  4 читающие     │
                    │  функции        │
                    └───────┬─────────┘
                            │ SELECT ... (mode=ro, query_only)
                            ▼
                    ┌─────────────────┐
                    │ data/trades.db  │  ← VACUUM INTO из живой базы
                    │ data/charts.db  │     (вручную, по команде)
                    └─────────────────┘

  Живая база приложения (arbitrage.db) — бот её НЕ открывает никогда.
  Копию реальной базы видит только локальная модель (Ollama);
  DeepSeek и другие облачные модели — только демо-базу (см. ниже).
```

Обрати внимание на три слоя защиты:

1. **Слой данных.** Бот работает со снимком, а не с живой базой. Даже если всё остальное сломается, приложение арбитража ничего не заметит.
2. **Слой соединения.** Снимок открыт с `mode=ro` в URI и с `PRAGMA query_only = ON`. Любой `INSERT/UPDATE/DELETE` упадёт с ошибкой.
3. **Слой инструментов.** Модель не пишет SQL. Она вызывает 4 функции с типизированными параметрами; SQL внутри функций пишешь ты. (Вариант «дать модели text-to-SQL» обсудим ниже — для этого проекта он хуже.)

Аналогия с твоим TS-кодом: это как если бы фронтенд вызывал только `GET`-роуты, а на сервере вообще не было бы `POST /api/orders/open`. Не «роут есть, но кнопка спрятана», а роута нет.

### 3. Что в твоей базе на самом деле

Перед тем как проектировать функции, нужно знать данные. В приложении две SQLite-базы, обе лежат на уровень выше репозитория:

| Файл | Что внутри | Нужно боту |
|---|---|---|
| `arbitrage.db` | `Forms` (пары: шорт-нога + лонг-нога, пороги, объём), `Positions` (одна строка на ногу), `ExcludePositions`, `AppSettings` | `Forms`, `Positions` |
| `arbitrage-charts.db` | `Candles`, `SpreadBuckets` (20-секундные корзины спреда по паре), `Quotes`, `FeedSpreads` | `SpreadBuckets` |
| `*-demo.db` | то же для DEMO | можно для экспериментов |

Ключевые факты, которые повлияют на функции:

- **Одна арбитражная позиция = две строки** в `Positions`: short и long с одинаковыми `formId` + `positionNumber`. PnL позиции — сумма PnL двух ног.
- **PnL в базе не хранится.** Есть `entryPrice`, `closePrice`, `volume`, `contractSize`, `entryFee`, `closeFee`. Считать придётся самому.
- **Объём в монетах считается по-разному**: для okx, gate, mexc `volume` уже в монетах, для остальных монеты = `contractSize * volume` (в приложении это `dbPositionCoins` в `app/utils/contracts.ts`). Классический источник багов — перенеси эту логику в Python один раз, в одну функцию.
- **Funding-платежей в базе нет.** Значит, PnL из базы — это PnL по ценам и комиссиям, без фандинга. Бот должен честно это говорить.
- **Даты** `dateCreated/dateClosed` пишутся `current_timestamp` → это UTC в виде текста `YYYY-MM-DD HH:MM:SS`. «Сегодня» в твоём часовом поясе ≠ «сегодня» в UTC.
- **История спреда** живёт 7 дней (retention в `chartDb.ts`). Вопрос «где был максимальный спред в октябре» бот честно не может ответить.
- В `SpreadBuckets.time` — целое число; проверь, секунды это или миллисекунды, одним `SELECT time FROM SpreadBuckets LIMIT 1`.

### 4. Почему копия, и почему только `VACUUM INTO`

Живая база в режиме **WAL** (write-ahead log). В этом режиме свежие изменения сначала пишутся в файл `arbitrage.db-wal`, и только при checkpoint переезжают в основной файл. Если сделать `cp arbitrage.db`, ты получишь основной файл без последних транзакций из `-wal`, а если в момент копирования шёл checkpoint — ещё и рваные страницы. Копия выглядит нормально и может даже открыться, но данные в ней неконсистентны. Скопировать три файла (`.db`, `-wal`, `-shm`) тоже не вариант: между копированием первого и последнего приложение успеет записать.

`VACUUM INTO 'путь'` делает другое: открывает читающую транзакцию и записывает **консистентный снимок** базы в новый файл — со всеми закоммиченными изменениями из WAL, без мусора, компактно. Исходную базу он не меняет. Это официальный способ «бэкапа живой SQLite» наряду с Backup API (`Connection.backup()` в Python).

```bash
# run from the arbitrage-app parent folder, where arbitrage.db lives
sqlite3 arbitrage.db "VACUUM INTO '/Users/<you>/code/trading-assistant-bot/data/trades.db'"
sqlite3 arbitrage-charts.db "VACUUM INTO '/Users/<you>/code/trading-assistant-bot/data/charts.db'"
```

Важно: `VACUUM INTO` не перезаписывает существующий файл — если копия уже есть, удали её перед новой. И ещё одна деталь: у копии может сохраниться журнал WAL; чтобы потом открывать её строго на чтение без вспомогательных файлов, один раз переключи её в обычный режим журнала:

```bash
sqlite3 data/trades.db "PRAGMA journal_mode=DELETE;"
```

Это команда к **копии**, не к живой базе. К живой базе разрешена только одна операция — `VACUUM INTO`.

### 5. Открыть на чтение: URI и `query_only`

В Python `sqlite3.connect()` по умолчанию открывает файл на чтение и запись и **создаёт пустую базу**, если файла нет (опечатка в пути → бот молча работает с пустой базой и отвечает «сделок нет»). URI-режим решает обе проблемы:

```python
import sqlite3
from pathlib import Path

def open_readonly(path: Path) -> sqlite3.Connection:
    # mode=ro: read-only, and the file must already exist
    uri = f"file:{path.resolve()}?mode=ro"
    conn = sqlite3.connect(uri, uri=True)
    conn.row_factory = sqlite3.Row          # rows behave like dicts
    conn.execute("PRAGMA query_only = ON")  # second layer: reject any write
    return conn
```

- `mode=ro` — SQLite откроет файл только на чтение; если файла нет — ошибка `unable to open database file`, а не новая пустая база.
- `PRAGMA query_only = ON` — второй замок на уровне соединения.
- `row_factory = sqlite3.Row` — строки с доступом по имени колонки (`row["entryPrice"]`), как объекты из `sqlite` в Node.

Есть ещё `immutable=1` в URI: говорит SQLite, что файл вообще никогда не меняется, и отключает блокировки. Для снимка это корректно, но если ты ошибёшься и направишь его на живой файл — получишь неконсистентное чтение. Для обучения хватит `mode=ro`.

### 6. Почему не text-to-SQL

Соблазн: дать модели одну функцию `run_sql(query)` и схему базы. Минусы для этого проекта:

| | 4 узкие функции | `run_sql` |
|---|---|---|
| Безопасность | SQL пишешь ты | модель пишет любой SQL (даже на ro-базе — тяжёлые запросы, чтение всего) |
| Корректность PnL | логика contractSize/funding в одном месте, покрыта тестами | модель каждый раз заново «вспоминает», как считать PnL |
| Размер ответа | агрегаты, ≤ 20 строк | легко вернуть 5000 строк в контекст |
| Тестируемость | pytest на каждую функцию | почти никакой |

Text-to-SQL — легитимный паттерн для аналитики «на любые вопросы», но он требует evals и песочницы. Вернёшься к нему, когда будут evals (этап 3). Здесь — узкие функции.

### 7. Стек и структура репозитория

- **Python 3.12+**, менеджер окружения — `uv` или `venv` + `pip`.
- **aiogram 3** — асинхронный фреймворк ботов. Аналог: как Express для HTTP, только для Telegram-апдейтов. Ключевые понятия: `Bot` (клиент Bot API), `Dispatcher` (корневой роутер, раздаёт апдейты), `Router` (группы хендлеров), фильтры (`Command`, `F.text`), middleware.
- **openai** SDK как клиент к Ollama и DeepSeek (оба говорят на формате OpenAI Chat Completions, отличается только `base_url`) + твоя обёртка `call_llm()` из главы 2.7 · Стриминг, ретраи, rate limits, prompt caching (AIL-11). **anthropic** SDK — по желанию, для сравнения на демо-базе.
- **pydantic** — модели результатов (AIL-14), **pytest** — тесты.

### 8. Список вопросов — это спецификация

Список из 10–15 вопросов — не формальность. Это твой первый мини-eval: в AIL-15 критерий готовности — «12 из 15 правильно». Хороший список:

- покрывает **каждую** функцию минимум дважды;
- содержит вопросы, требующие **двух функций** («какие пары открыты и сколько они принесли за неделю?»);
- содержит **относительные даты** («вчера», «за прошлую неделю», «с начала месяца»);
- содержит **вопросы вне возможностей** («закрой позицию по BTC», «какой фандинг заплатил», «какой спред был в августе») — правильный ответ на них: вежливый отказ с объяснением;
- для каждого вопроса записан **ожидаемый ответ** или способ его проверить (SQL-запрос, который ты сам выполнишь).

## DeepSeek и Ollama: как это сделать у нас

### Главное решение проекта: какая модель видит реальные данные

Результаты инструментов — это твои PnL, пары, объёмы и даты сделок. Всё, что вернула функция, уходит в контекст модели, то есть **на сервер провайдера**. Поэтому в этом проекте провайдер выбирается не по цене и не по качеству, а по данным:

| Какие данные видит бот | Ollama (локально) | DeepSeek | Claude / OpenAI |
|---|---|---|---|
| Копия реальной базы `data/trades.db` | ✅ основной путь | ❌ никогда: серверы в Китае | ❌ в этом проекте нет |
| Демо-база `data/demo_trades.db` (AIL-14) | ✅ | ✅ основной облачный путь | ✅ только для сравнения |

У Ollama модель крутится на твоём Mac, запрос идёт на `http://localhost:11434` и никуда не уходит. Оговорка: в библиотеке Ollama есть **облачные** модели (с пометкой `cloud` или суффиксом `-cloud` в теге, например `gpt-oss:20b-cloud`) — они выполняются на серверах Ollama. Для реальных данных — только локальные теги.

Это то же правило, что и с ордерами: защита — в коде, а не в дисциплине. Бот при старте сам проверяет, что облачному провайдеру подсунута только демо-база.

### Один клиент на двух провайдеров

И DeepSeek, и Ollama принимают формат OpenAI Chat Completions (проверено по документации, ноябрь 2026): у DeepSeek `base_url="https://api.deepseek.com"`, у Ollama — `http://localhost:11434/v1/` и любой непустой `api_key` (он игнорируется). Значит, весь бот пишется на одном SDK `openai`, а провайдер переключается переменными окружения:

```python
# bot/config.py (illustrative)
import os
from pathlib import Path

PROVIDERS = {
    # name: (base_url, env var holding the key, runs on this Mac?)
    "ollama":   ("http://localhost:11434/v1/", None, True),
    "deepseek": ("https://api.deepseek.com", "DEEPSEEK_API_KEY", False),
}
DEMO_TRADES_DB = Path("data/demo_trades.db").resolve()

def llm_settings() -> tuple[str, str, str]:
    provider = os.environ["LLM_PROVIDER"]            # "ollama" | "deepseek"
    base_url, key_env, _ = PROVIDERS[provider]
    api_key = os.environ[key_env] if key_env else "ollama"   # Ollama ignores the key
    return provider, base_url, api_key

def assert_data_policy(provider: str, model: str, trades_db: Path) -> None:
    # A cloud model may only ever see the fake demo database.
    _, _, local = PROVIDERS[provider]
    if model.endswith("-cloud") or ":cloud" in model:   # Ollama cloud tags run remotely
        local = False
    if not local and trades_db.resolve() != DEMO_TRADES_DB:
        raise SystemExit(f"{provider} is a cloud provider: "
                         f"TRADES_DB_PATH must be {DEMO_TRADES_DB}, got {trades_db}")
```

`assert_data_policy` вызывается в `main.py` до старта polling и в `run_questions.py` до первого вопроса. Если ты по привычке поставишь `LLM_PROVIDER=deepseek` рядом с `TRADES_DB_PATH=data/trades.db`, бот не запустится — а не «запустится и отправит твои сделки в Китай». Добавь на это тест pytest.

Мелочь, на которой легко потерять час: если в окружении задан `HTTP_PROXY`/`HTTPS_PROXY`, `openai`-клиент (он на `httpx`) может отправить даже запрос к `localhost` в прокси. Добавь `NO_PROXY=localhost,127.0.0.1`.

### Ollama на Mac с 8 ГБ памяти

На твоём MacBook (M2) 8 ГБ единой памяти, и на нём же работает приложение арбитража. Это главное ограничение выбора модели:

- Ollama требует macOS Sonoma (14) или новее, на Apple Silicon использует GPU ([docs.ollama.com/macos](https://docs.ollama.com/macos)). Модели лежат в `~/.ollama`.
- Реалистичный размер — модели 4B в квантизации q4 (≈2.5 ГБ на диске) и, впритык, 8B (≈5 ГБ). Модели на 14 ГБ и больше (например, `gpt-oss:20b`, которой по её странице нужно от 16 ГБ памяти) на этой машине не работают.
- **Не грузи модель, пока включена автоторговля.** Большая модель вытеснит память приложения в swap, и сервер арбитража начнёт отвечать с задержкой. Ollama выгружает модель через несколько минут простоя (`keep_alive`, по умолчанию `5m`) — прогоняй вопросы, когда торговля не взведена, или держи модель маленькой.

Какую именно модель взять и как это проверить — подробно в главе 3.3 · Проект 1: tool calling + Telegram. Для старта сегодня: `qwen3:4b-instruct-2507-q4_K_M` (2.5 ГБ, поддерживает tools).

### Установка — только из официального источника

1. Скачай приложение с [ollama.com/download](https://ollama.com/download), не из сторонних зеркал и не через `curl … | sh`.
2. До первого запуска проверь подпись и нотаризацию:
   ```bash
   codesign -dv --verbose=4 /Applications/Ollama.app   # who signed it (Developer ID, Team ID)
   spctl -a -vv /Applications/Ollama.app               # expect: accepted, source=Notarized Developer ID
   ```
3. Модели качай из официальной библиотеки по **полному тегу** (`ollama pull qwen3:4b-instruct-2507-q4_K_M`), а не `latest` — иначе через месяц под тем же именем окажется другая модель и сравнения перестанут сходиться.
4. Python-пакеты пиннингуй: `openai==<версия>`, и, если понадобится нативный API, `ollama==<версия>` (официальный клиент, на ноябрь 2026 — 0.6.3 на PyPI).

## Маршрут изучения

1. Открой [sqlite3 в Python](https://docs.python.org/3/library/sqlite3.html) → прочитай Tutorial, затем в Reference: `sqlite3.connect()` (параметр `uri`), `Connection.execute`, `Row`, `row_factory`, раздел How-to «How to work with SQLite URIs» и «How to use placeholders to bind values» (≈40 мин). Возьми: плейсхолдеры `?`/`:name` вместо f-строк в SQL, `mode=ro`.

## На что обратить внимание

- **Реальные данные в публичном репозитории — главный риск проекта.** `data/`, `*.db`, `*.db-wal`, `*.db-shm`, `logs/`, `.env` — в `.gitignore` ещё до первого коммита. Если реальная база хоть раз попала в коммит, она остаётся в истории git даже после удаления файла. Проверка: `git check-ignore -v data/trades.db` должна показать правило.
- **Скриншоты и примеры в README — только на фейковой базе.** Реальные цифры сделок не должны попасть в публичный репозиторий ни файлом, ни картинкой, ни строчкой в README.
- **`sqlite3.connect("data/trades.db")` без `mode=ro` создаст пустой файл при опечатке** — и бот будет уверенно отвечать «сделок нет».
- **Не открывай живую базу из бота «просто посмотреть»**, даже на чтение: читающая транзакция в WAL мешает checkpoint и может раздувать `-wal` у работающего приложения. Только снимок.
- **`sqlite3 -readonly` на живую WAL-базу не работает** (в проекте арбитража это отмечено). Для снимка открывай обычным `sqlite3` и выполняй только `VACUUM INTO`.
- **Не перепутай пути**: `VACUUM INTO` с путём, указывающим на существующий файл, упадёт — это хорошо. Но `rm` перед снимком направляй только на файлы в `data/` бота.
- **Не тащи в бот ccxt и ключи бирж** «чтобы показывать текущие цены». Это private/signed запросы и другой класс риска; в этом проекте их нет.
- **Время**: SQLite хранит UTC, ты думаешь в местном времени. Зафиксируй это в README сразу, иначе в AIL-15 «за сегодня» будет врать на несколько часов.
- **«Только посмотреть, как отвечает DeepSeek на моих данных»** — нельзя. Сравнение моделей делается на демо-базе; на реальной копии работает только локальная Ollama. Гарантирует это `assert_data_policy`, а не память.
- **`-cloud`-теги Ollama — это облако**, хоть и запускаются той же командой `ollama run`.

## Ответы

1. **b.** Последние транзакции могут лежать в `-wal`, а во время checkpoint основной файл меняется — копия получится неконсистентной. `VACUUM INTO` пишет согласованный снимок.
2. Первый вызов молча создаст пустую базу `trdes.db`, и бот будет отвечать «нет данных». Второй упадёт с `unable to open database file` — ошибка видна сразу.
3. `mode=ro` в URI (SQLite открывает файл только на чтение) и `PRAGMA query_only = ON` (соединение отклоняет любые изменения).
4. Промпт — это просьба, модель может ошибиться или поддаться инъекции. Настоящая защита — отсутствие функции и прав: нечего вызывать и нечем писать.
5. **b.** Шорт-нога и лонг-нога с одинаковыми `formId` + `positionNumber`; PnL позиции — сумма двух ног.
6. okx входит в группу, где `volume` уже в монетах → 3 монеты. bybit → `contractSize × volume = 0.03` монеты.
7. `cp` вместо `VACUUM INTO` (неконсистентная копия) и `git add` реальной базы — реальные сделки уйдут в историю git; `data/` должна быть в `.gitignore`.
8. Что фандинга в базе нет: может назвать PnL по ценам и комиссиям за неделю и явно оговорить, что фандинг не учтён.
9. Модель пишет произвольный SQL (риск тяжёлых запросов и неверной логики PnL/contractSize каждый раз заново), сложно ограничить размер выдачи, почти нечего тестировать.
10. `date('now')` в SQLite — UTC, а твоё «вчера» — в местном часовом поясе; границы суток сдвинуты на разницу часовых поясов.
11. Это проверка поведения на границах: бот должен вежливо отказать (нет функции закрытия, нет данных о фандинге, нет истории спреда старше 7 дней), а не выдумать ответ.
12. Обе — на демо-базе: результаты инструментов уходят провайдеру, а DeepSeek — облако с серверами в Китае. Локальную модель потом дополнительно прогоняешь на реальной копии; DeepSeek её не видит никогда.
13. Оба реализуют формат OpenAI Chat Completions. Меняются только `base_url`, `api_key` (у Ollama любой, игнорируется) и имя модели — то есть переменные окружения, а не код.
14. Тег `-cloud` выполняется на серверах Ollama, а не на Mac, — реальная копия базы уйдёт в облако. Для реальных данных нужен локальный тег; `assert_data_policy` из этой главы такую конфигурацию отклонит.
