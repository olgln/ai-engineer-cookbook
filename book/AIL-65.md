# 10.1 · Память и контекст агента  (AIL-65)

> **Неделя 10** · Агенты · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Любой агент, который работает дольше десятка шагов, упирается в контекстное окно: история растёт, каждый шаг дорожает, а качество падает задолго до формального лимита. Управление контекстом и памятью — то, что отличает игрушечного агента от рабочего; на собеседованиях спрашивают «как твой агент справляется с длинными задачами?» и ждут конкретики: compaction, заметки, подгрузка по запросу, субагенты.

## Теория

### Контекст — ресурс с убывающей отдачей

Из AIL-37: в статье Anthropic о context engineering это называется **context rot** — чем больше токенов в окне, тем хуже модель находит и использует нужное. У модели ограниченный «бюджет внимания». Отсюда цель: на каждом шаге в окне должен быть **минимальный набор токенов с максимальным сигналом**.

Что занимает контекст агента из AIL-38:

```
[system prompt]            ~1k   stable
[tool definitions]         ~1-3k stable
[task]                     small
[step 1: thought + call]   small
[step 1: tool_result]      LARGE  <- log lines, DB rows, docs
[step 2 ...]
...
[step 30: tool_result]     LARGE
```

Большую часть съедают **результаты инструментов**, причём старые результаты обычно уже не нужны — нужен вывод, который агент из них сделал.

### Виды памяти

| Вид | Где живёт | Аналогия | Пример |
|---|---|---|---|
| Рабочая (краткосрочная) | Контекстное окно | Переменные в стеке | Последние 5 шагов |
| Сжатая история | В окне, как summary | Changelog вместо полного diff | «Шаги 1–20: проверены позиции A, B; у B причина — ликвидация» |
| Заметки (scratchpad) | Файл / SQLite, читается по запросу | Записи в блокноте | `NOTES.md`: факты, гипотезы, что осталось сделать |
| Долгосрочная | Внешнее хранилище между сессиями | База данных | «На bingx время в логах в UTC+0, а не UTC+3» |
| Знания по запросу (just-in-time) | Источник данных, в окне только ссылка | Ленивая загрузка | Агент держит `form_id` и подгружает позицию инструментом, когда нужно |

### Техника 1: сжатие истории (compaction)

Когда история превышает порог (по шагам или токенам), старую часть заменяют кратким резюме, а последние K шагов оставляют как есть.

```
before: [task][s1][r1][s2][r2]...[s20][r20][s21][r21][s22][r22]
after:  [task][SUMMARY of s1..s20][s21][r21][s22][r22]
```

```python
# compaction.py — illustrative
KEEP_LAST_STEPS = 4

def compact(messages: list[dict], summarize) -> list[dict]:
    task, history = messages[0], messages[1:]
    # one "step" = assistant message + following user(tool_result) message
    cut = len(history) - 2 * KEEP_LAST_STEPS
    if cut <= 0:
        return messages
    old, recent = history[:cut], history[cut:]
    summary = summarize(old)  # separate LLM call with its own prompt
    return [task,
            {"role": "user", "content": f"<progress_summary>\n{summary}\n</progress_summary>"},
            *recent]
```

Детали, на которых ломаются:

- **Пары `tool_use`/`tool_result` нельзя разрывать.** Если обрезать так, что в окне остался `tool_result` без своего `tool_use`, API вернёт ошибку. Режь по границам шагов.
- **Чередование ролей.** После сжатия проверь, что сообщения идут в допустимом порядке (у Anthropic — user/assistant попеременно); при необходимости склей summary с задачей в одно user-сообщение.
- **Промпт для summary важнее, чем кажется.** Просить «перескажи кратко» — плохо. Проси конкретное: какие факты установлены (с источником: таблица, строка лога), какие гипотезы отвергнуты и почему, какие вопросы открыты, какие ID и временные метки важны. Иначе агент «забудет», что уже проверял, и пойдёт по кругу.
- **Неизменные идентификаторы** (`form_id`, `position_number`, точное время) должны пережить сжатие дословно.

Облегчённый вариант — **очистка старых результатов инструментов**: заменить содержимое старых `tool_result` на `[result cleared; see notes]`, оставив вызовы. Дёшево и часто достаточно. У некоторых провайдеров есть серверные функции управления контекстом и «memory tool» — проверь текущую документацию, прежде чем писать своё; но сначала сделай руками, чтобы понимать механику.

### Техника 2: заметки агента (structured note-taking)

Агент получает инструменты `write_note` / `read_notes` и сам записывает важное по ходу работы. Заметки живут **вне** окна и переживают compaction и даже перезапуск.

```python
# notes in SQLite — illustrative
import sqlite3, json, time

conn = sqlite3.connect("agent_memory.db")
conn.execute("""CREATE TABLE IF NOT EXISTS notes(
  id INTEGER PRIMARY KEY, session TEXT, kind TEXT, key TEXT, body TEXT, ts REAL)""")

def write_note(session: str, kind: str, key: str, body: str) -> str:
    # kind: fact | hypothesis | todo | lesson
    conn.execute("INSERT INTO notes(session, kind, key, body, ts) VALUES (?,?,?,?,?)",
                 (session, kind, key, body, time.time()))
    conn.commit()
    return "saved"
```

Важно:

- Это **отдельная** база агента (`agent_memory.db`), а не торговая. Торговые данные агент по-прежнему только читает из копии.
- Типизируй заметки (`fact`, `hypothesis`, `todo`, `lesson`) — по ним удобно фильтровать при чтении.
- **Межсессионная память** — то, что переносится в следующую сессию: «уроки» (`lesson`): «у bybit поле времени в логе — время получения ответа, а не исполнения». В начале сессии агент читает последние N уроков.
- **Память — это тоже вектор атаки.** Если агент записал в заметки инструкцию из отравленного лога, она будет «вспоминаться» в каждой следующей сессии (persistent injection). Пиши в долгосрочную память только через проверку: человеком или хотя бы правилами (длина, отсутствие URL и императивов).

### Техника 3: подгрузка по запросу (just-in-time)

Не загружай всё заранее. Вместо «вот все 500 позиций за месяц» дай агенту список ID и инструменты, которые возвращают одну позицию, одну пару, кусок лога за интервал. В окне держатся лёгкие ссылки (ID, путь, время), тяжёлые данные приходят, только когда нужны, и после использования могут быть очищены. Именно поэтому в AIL-39 инструменты узкие и с лимитами.

### Техника 4: субагенты

Главный агент делегирует изолированную подзадачу субагенту с **чистым** контекстом («разбери логи за 14:00–14:30 и верни 5 строк выводов»). Субагент может потратить 30k токенов на чтение логов, а главному вернёт 300. Цена — больше вызовов и сложнее отладка; применяй, когда подзадачи независимы и тяжелы по данным.

### Как выбрать порог

Считай токены, а не только шаги: `resp.usage.input_tokens` на каждом шаге — это фактический размер окна. Порог compaction ставь заметно ниже лимита модели (например, на 30–50% окна): качество падает раньше лимита, а summary тоже нужно место. Проверь эмпирически: прогони длинную задачу с разными порогами и сравни правильность ответа и стоимость.

## DeepSeek и Ollama: как это сделать у нас

Техники главы — compaction, очистка результатов, заметки, субагенты — ты пишешь сам, и они одинаковы для любого провайдера. Различаются **размер окна, цена длинной истории и то, как провайдер ведёт себя при переполнении**. Проверено по документации DeepSeek и Ollama 13 ноября 2026.

> ⚠️ Длинная задача из практики идёт по **реальной** копии базы, и `agent_memory.db` будет содержать выводы о твоих сделках. Основной провайдер — **Ollama**; summary-вызов compaction — тоже локальный. DeepSeek — только на фейковой базе для сравнения.

### Сравнение

| | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| Окно | Большое (по модели) | Большое (по модели) | 1M токенов (`deepseek-flash`, `deepseek-v4-pro`) | Сколько задашь: дефолт **4096** (при VRAM < 24 ГБ), больше — больше памяти |
| Что при переполнении | Ошибка API | Ошибка API | Ошибка API (до 1M ты вряд ли дойдёшь — раньше начнётся context rot) | **Тихая обрезка** начала истории: системный промпт и задача пропадают без ошибки |
| Размер окна в ответе | `usage.input_tokens` | `usage.prompt_tokens` / `input_tokens` | `usage.prompt_tokens` + `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | `prompt_eval_count` (нативный API, есть ещё `prompt_eval_cached_count`) или `usage.prompt_tokens` в OpenAI-совместимом |
| Кэш префикса | Явный `cache_control` | Автоматический | Автоматический, «best effort», хранится от часов до дней | KV-кэш в памяти, пока модель загружена (`keep_alive`) |
| Серверное управление контекстом / memory tool | Есть (проверь текущую доку) | Есть свои механизмы (проверь) | Нет | Нет |

### Ollama: сначала проверь, что окно вообще то, которое ты думаешь

1. Подними контекст: `OLLAMA_CONTEXT_LENGTH=16384 ollama serve` (Mac-приложение: `launchctl setenv OLLAMA_CONTEXT_LENGTH 16384` + перезапуск, или ползунок в настройках) — или `options={"num_ctx": 16384}` в нативной библиотеке. В OpenAI-совместимом API параметра нет: либо переменная окружения сервера, либо своя модель через Modelfile с `PARAMETER num_ctx`.
2. Проверь `ollama ps`: колонки `CONTEXT` и `PROCESSOR` (`100% GPU` — хорошо; частичная выгрузка на CPU — медленно).
3. **Детектор тихой обрезки:** если `prompt_eval_count` на шагах растёт, а потом «прилипает» к значению около `num_ctx`, история обрезается. Логируй это рядом с `input_tokens` и стопай агента с понятным статусом.

Для локальной модели compaction нужен **раньше**, чем для облачной: на M2 с 8 ГБ окно 16k, порог в 30–50% — это 5–8k токенов, то есть несколько результатов инструментов. Поэтому очистка старых результатов и заметки здесь не «оптимизация», а условие работы.

### DeepSeek: compaction против кэша

- Кэш автоматический по префиксу. Пока история только **растёт в конец**, каждый шаг попадает в кэш на всю старую часть — у `deepseek-flash` попадание стоит в десятки раз дешевле промаха (на ноябрь 2026 в пик: $0.006 против $0.3 за 1M входных токенов; проверь актуальные цены).
- Compaction **переписывает середину** истории → следующий запрос промахивается мимо кэша на всём, что после изменения. Значит, сжимать стоит редко и крупно, а не на каждом шаге. Сравни `prompt_cache_hit_tokens` в трёх режимах практики — это наглядная цифра для README.
- **Thinking + инструменты:** при работе с инструментами DeepSeek требует возвращать `reasoning_content` прошлых шагов, иначе 400. Как API отнесётся к истории, где старые шаги заменены summary, в документации прямо не описано — я это не проверял. Для длинного агента на DeepSeek проще выключить thinking (`extra_body={"thinking": {"type": "disabled"}}`) или проверить на фейковых данных, что сжатая история принимается.
- Окно 1M не отменяет context rot: модель хуже находит нужное в огромной истории, а каждый шаг всё равно оплачивается.

### Ollama и кэш

У Ollama нет платы за токены, но длинный префикс всё равно надо «прочитать» (prefill). Пока модель загружена, совпадающий префикс берётся из KV-кэша — смотри `prompt_eval_cached_count` в нативном ответе. Если модель выгрузилась (по умолчанию через несколько минут простоя; управляется `keep_alive`), первый шаг после паузы снова медленный. Compaction и здесь сбрасывает кэш после места изменения.

### Что использовать в этой главе

- **Основной прогон трёх режимов** — Ollama (`qwen3:4b`; `qwen3:8b` — только с закрытыми программами и невзведённой автоторговлей), окно 16k, `OLLAMA_NO_CLOUD=1`. Summary для compaction — та же модель (вторую модель параллельно 8 ГБ не удержат).
- **Для сравнения** — тот же агент на `deepseek-flash` на **фейковой** базе (из главы 9.5): сравни, где агент без управления контекстом «сломался» у каждой модели, и сколько стоил кэш.
- Claude с его встроенными инструментами управления контекстом — по желанию, только читать документацию или на фейковых данных.

## На что обратить внимание

- **Разорванная пара `tool_use`/`tool_result`** после обрезки — самая частая ошибка реализации.
- **Summary теряет детали** — агент снова и снова проверяет одно и то же. Лечится структурированным промптом для summary и заметками.
- **Summary выдумывает.** Сжатие — тоже генерация; проверь на нескольких прогонах, что в summary нет фактов, которых не было в истории.
- **Память без очистки** разрастается и сама становится источником шума; ограничивай размер и чисти устаревшее.
- **Persistent injection** через заметки — см. выше.
- **Prompt caching ломается**, если ты меняешь начало истории: кэш работает по префиксу. Держи стабильное (system, tools) в начале, изменяемое — после.
- **Не путай базы.** Агент пишет только в свою `agent_memory.db`; торговая — только копия и только чтение.

4. Compaction заменяет старые шаги резюме (новая генерация, дороже, но сохраняет выводы); очистка оставляет вызовы, но стирает тяжёлое содержимое результатов (дёшево, выводы остаются только в тексте ассистента или заметках).
