# 13.3 · Подготовка к собеседованиям  (AIL-54)

> **Неделя 13** · Портфолио · ⏱ ~6–8 ч (можно растянуть на 2 дня) · Теория

## Зачем это AI-инженеру

Собеседование AI-инженера обычно состоит из четырёх частей: теория LLM, system design LLM-приложения, live coding и разбор твоих проектов, плюс поведенческий разговор. Ты всё это знаешь по отдельности, но на интервью проверяют, можешь ли ты объяснить это коротко, точно и под давлением времени. Эта глава превращает 12 недель знаний в готовые ответы.

## Теория

### Как устроен процесс найма

Типичная воронка (конкретные этапы зависят от компании):

```
Скрининг с рекрутером (20–30 мин)
   └─ мотивация, опыт, зарплата, формат, английский
Технический скрининг (45–60 мин)
   └─ теория LLM + разбор проекта или небольшая задача
Основной цикл (2–4 встречи)
   ├─ Live coding (Python, иногда без AI-ассистента)
   ├─ LLM system design (см. главу [13.2 · System design LLM-приложения и мок-собеседование](AIL-68.md))
   ├─ Глубокий разбор проекта (deep dive)
   └─ Behavioral / culture fit
Иногда: take-home задание (RAG/агент за 3–8 часов)
Финал с руководителем → оффер
```

Что ищут на каждом этапе: **ясность** (можешь объяснить сложное просто), **глубину** (знаешь, почему, а не только как), **суждение** (видишь trade-offs и риски), **честность** (говоришь «не знаю, но рассуждал бы так»).

### Теория LLM: ответы на 60 секунд

Ниже — каркасы ответов. Подробно всё разобрано в главах недель 1–11; здесь цель — формулировка, которая укладывается в минуту и содержит один пример.

- **Токены.** Модель работает не с символами, а с токенами — кусками слов из словаря токенизатора (BPE). Цена, лимиты контекста и скорость считаются в токенах. Русский текст обычно дороже английского по числу токенов. Модели плохо считают буквы, потому что «не видят» символы внутри токена.
- **Контекстное окно.** Максимум токенов вход + выход за один вызов. Модель не помнит прошлые вызовы — «память» чата это история, которую ты сам присылаешь. Длинный контекст дорог, медленнее и хуже используется в середине («lost in the middle»).
- **Temperature / sampling.** Управляет случайностью выбора следующего токена. Низкая — для извлечения и классификации, выше — для генерации вариантов. Даже при 0 полного детерминизма нет.
- **Эмбеддинги.** Вектор, отображающий смысл текста в точку пространства; близкие по смыслу тексты — близкие векторы (косинусная близость). Основа семантического поиска.
- **RAG.** Найти релевантные куски знаний и подставить в промпт, чтобы модель отвечала по ним. Даёт свежесть, приватные данные и цитаты без переобучения. Ломается чаще всего на поиске, а не на генерации.
- **Evals.** Систематическая оценка качества на наборе примеров с метриками; аналог тестов для недетерминированной системы. Метрики по слоям: ретривер, генерация, инструменты. Без evals любое изменение промпта — гадание.
- **Tool calling.** Модель возвращает структурированный запрос на вызов функции (имя + аргументы по JSON Schema); код вызывает функцию и возвращает результат в модель. Модель сама ничего не выполняет.
- **Агент.** LLM в цикле: модель выбирает инструмент, получает результат, решает следующий шаг, пока не закончит. Отличие от workflow: путь выбирает модель, а не код. Цена — непредсказуемость и стоимость.
- **MCP.** Открытый протокол, стандартизирующий, как приложения-клиенты (Claude Desktop, IDE, свой агент) подключаются к серверам инструментов, ресурсов и промптов. Аналогия: как LSP для редакторов — один сервер работает со многими клиентами.
- **Fine-tuning vs RAG.** Fine-tuning меняет поведение (формат, стиль, узкий навык); RAG даёт знания. Знания через fine-tuning — дорого, плохо обновляется и не даёт цитат.
- **Prompt caching.** Провайдер кэширует обработанный общий префикс промпта; повторные запросы с тем же префиксом дешевле и быстрее. Поэтому стабильное — в начало, переменное — в конец.

Тренируй правило: **определение → зачем → пример из твоего проекта → ограничение**. Пример: «RAG — … В моём проекте по докам бирж ретривер ошибался на точных именах параметров, гибридный поиск с BM25 это исправил».

### Prompt injection: как отвечать

Это вопрос почти на каждом интервью. Структура ответа:

1. **Что это.** Недоверенный текст (ввод пользователя, документ в RAG, веб-страница, результат инструмента) содержит инструкции, и модель им следует. Прямая (от пользователя) и непрямая (через данные).
2. **Почему не решается полностью.** Модель не разделяет надёжно инструкции и данные: всё — токены одного контекста. Это не баг, который можно «пропатчить» промптом.
3. **Защита слоями.**
   - минимальные права инструментов (read-only, как в твоих проектах; доступ только к данным текущего пользователя);
   - подтверждение человеком для действий с побочными эффектами;
   - разделение: модель, читающая недоверенные данные, не имеет опасных инструментов;
   - выделение недоверенного содержимого в промпте (теги, пометки) — помогает, но не гарантирует;
   - валидация выхода (схема, белые списки значений), фильтры на эксфильтрацию (ссылки, markdown-картинки);
   - лимиты и мониторинг, red-teaming своими атаками (ты делал в главе [9.4 · Prompt injection: атаковать своего агента](AIL-64.md)).
4. **Пример.** Из главы [9.4 · Prompt injection: атаковать своего агента](AIL-64.md): какая атака на твой агент сработала и что её остановило.

### Trade-offs: стоимость / качество / латентность

Любая оптимизация двигает одну ось за счёт другой. Держи таблицу рычагов:

| Рычаг | Качество | Стоимость | Латентность |
|---|---|---|---|
| Более сильная модель | ↑ | ↑ | ↑ (обычно) |
| Каскад: дешёвая → сильная при необходимости | ≈ | ↓ | ↓ в среднем |
| Больше чанков в контексте | ↑ до предела, потом ↓ | ↑ | ↑ |
| Реранкер | ↑ | ↑ немного | ↑ |
| Prompt caching | = | ↓ | ↓ |
| Кэш ответов | = (если запросы совпадают) | ↓↓ | ↓↓ |
| Стриминг | = | = | ↓ воспринимаемая |
| Reasoning / extended thinking | ↑ на сложном | ↑ | ↑↑ |
| Локальная модель | ↓ обычно | ↓ при большом объёме | зависит от железа |

Хороший ответ звучит так: «Сначала определил бы бюджет и SLA по латентности, потом на eval-наборе сравнил бы 2–3 конфигурации и выбрал самую дешёвую, проходящую порог качества».

### Рассказ о проекте за 2 минуты

Структура (вариант STAR, адаптированный под инженерный проект):

```
1. Контекст (15 сек): какую задачу решает, для кого
2. Архитектура (30 сек): основные компоненты, одна ключевая деталь
3. Мои решения (30 сек): 1–2 нетривиальных выбора и почему
4. Результат (20 сек): цифры с baseline
5. Что не сработало / что сделал бы иначе (25 сек)
```

После двухминутного рассказа интервьюер пойдёт вглубь (deep dive): «почему такой размер чанка?», «как размечал датасет?», «что будет при 100× нагрузке?», «как ловишь регрессии?». Для каждого проекта заготовь 5 таких вопросов с ответами.

Отдельно готовь рассказ про торговую систему: это твой самый сильный бэкенд-опыт. Темы для deep dive: как устроен поток цен по WebSocket, как гарантируется одновременность двух ног и что происходит, когда одна нога не исполнилась; как переживает сон ноутбука и обрыв соединения; миграции SQLite; почему сервер не доверяет вкладке браузера. Рассказывай об инженерии, не о стратегии и не о деньгах.

### Live coding без AI

Многие компании проверяют Python на живом кодинге, часто без Copilot и чат-ассистента. Ты весь курс писал с AI-помощью, поэтому это отдельная тренировка. Задачи для AI Engineer обычно не олимпиадные, а прикладные:

- разобрать данные: JSON/CSV/логи → агрегаты (`dict`, `collections.Counter`, `defaultdict`, `sorted` с `key`);
- реализовать примитив: косинусная близость, top-k, разбиение текста на чанки с перекрытием, простой BM25;
- надёжность: ретрай с экспоненциальной задержкой, rate limiter, LRU-кэш;
- async: параллельные вызовы с ограничением конкурентности (`asyncio.gather`, `asyncio.Semaphore`);
- маленький «LLM-сервис» с моком клиента: вызов, парсинг структурированного ответа, валидация Pydantic.

Пример уровня сложности (решай сам, без подсказок):

```python
def chunk_text(words: list[str], size: int, overlap: int) -> list[list[str]]:
    """Split words into chunks of `size` with `overlap` words shared
    between neighbours. Raise ValueError if overlap >= size."""
    ...

assert chunk_text(list("abcdefg"), 3, 1) == [["a","b","c"], ["c","d","e"], ["e","f","g"]]
```

Правила live coding: проговаривай план до кода; начни с простого рабочего решения; задай граничные случаи (пусто, overlap ≥ size, последний неполный кусок); напиши 2–3 assert'а; назови сложность. Молчаливое идеальное решение оценивают ниже, чем проговорённое хорошее.

### Поведенческие вопросы

Обычные темы: почему уходишь в AI, сложная проблема и как решил, ошибка и что из неё вынес, конфликт или несогласие, как учишься. Готовь 4–5 историй по STAR (Situation, Task, Action, Result), которые покрывают разные вопросы. Хорошие источники историй у тебя есть: инцидент с одноногой позицией и защита от неё, расхождения бирж в размере контракта и патчи ccxt под них (и тесты, которые ловят поломки при обновлении библиотеки), решение не доверять браузеру и перенести проверки на сервер, самостоятельное освоение LLM-стека с измеримыми результатами.

Вопрос «почему ты, если в AI всего 3 месяца?» — заготовь честный ответ: бэкенд и production-опыт переносятся напрямую, LLM-часть доказана проектами с evals и статьёй.

### Вопросы интервьюеру

В конце всегда спрашивают «есть ли вопросы». Хорошие вопросы показывают зрелость: как вы меряете качество LLM-фич; кто размечает данные для evals; какие модели и почему, как часто меняете; какая доля работы — промпты/RAG, а какая — инфраструктура; что было последним инцидентом с LLM-фичей.

## DeepSeek и Ollama: как это сделать у нас

Почти наверняка спросят: «Почему DeepSeek и Ollama, а не Claude/OpenAI, как у нас?». Это не неудобный вопрос, а возможность показать суждение. Каркас ответа на 60 секунд:

1. **Выбор, а не вынужденность.** «Я строил слой провайдера на OpenAI-совместимом API: DeepSeek для облака — дёшево, локальные модели в Ollama — для приватных данных и бесплатных экспериментов».
2. **Приватность.** «Реальные данные моей торговой системы не уходили с машины: DeepSeek хранит данные в Китае, поэтому туда шла только синтетика и публичные доки, а реальное — только в Ollama».
3. **Сравнение на evals.** «Те же eval-наборы я прогонял на Claude/OpenAI: <твой результат, например: разница в faithfulness X п.п. при цене в Y раз выше>».
4. **Переносимость.** «Переход на ваш стек — смена адаптера и перепрогон evals; различия я знаю: кэш, tool_choice, structured output, эмбеддинги».

Пункт 3 работает, только если ты действительно делал такой прогон. Большинство вакансий — на Claude и OpenAI, поэтому если ещё не вызывал их хотя бы раз, сделай это до интервью (на синтетике, это недорого).

Отличия, о которых могут спросить вдогонку (на ноябрь 2026, проверь актуальное):

| Тема | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| Prompt caching | явная разметка `cache_control` | автоматический по префиксу | автоматический, без изменений кода; cache hit во много раз дешевле miss | платы нет; кэш — пока модель загружена в память |
| Tool calling | свой формат `tool_use` / `tool_result` в SDK `anthropic` | `tools` / `tool_calls` | OpenAI-формат | OpenAI-формат у моделей с поддержкой tools; без `tool_choice` |
| Structured output | через tools / схемы — проверь текущие возможности | `response_format` со схемой | JSON output mode | `format` с JSON-схемой (нативный API) или `response_format` |
| Эмбеддинги | своей модели нет | есть | в документации не видно | есть, локально |
| Данные | облако провайдера | облако провайдера | облако, Китай | локально |

Формулировку «prompt caching» из словаря выше дополни этим: механизм один (переиспользуется общий префикс), а включается и оплачивается он по-разному.

**Тренировка.** Мини-мок проводи на DeepSeek: вопросы по теории и твои ответы — не личные данные. Только в рассказе о торговой системе держись уровня инженерии, без сумм, объёмов и стратегии — это правило и для интервьюера-человека, и для модели. Для сравнения проведи тот же мок через Claude или OpenAI. А оценивать свои записанные ответы проси более сильную модель, чем ту, что вела мок.

## На что обратить внимание

- **Определение вместо понимания.** «RAG — это retrieval augmented generation» — не ответ. Нужно «зачем» и «где ломается».
- **Термины без чисел.** Если говоришь «улучшил», дальше должна быть цифра.
- **Переоценка агентов.** Интервьюеры любят спросить «а зачем тут агент?». Подтверди, что умеешь выбирать workflow.
- **Ступор на live coding без AI.** Синтаксис забывается быстро. Пять задач — минимум; вспомни `enumerate`, `zip`, срезы, `dict.get`, `sorted(key=...)`, comprehension, `with open`, `json.loads`.
- **Длинные ответы.** Отвечай на вопрос в 1–2 минуты, потом предложи углубиться: «могу рассказать подробнее про X».
- **Негатив о прошлом.** Не ругай бывших работодателей, биржи, коллег.
- **Раскрытие торговых деталей.** На собеседовании не называй суммы, объёмы, баланс, конкретную стратегию — рассказывай инженерию.
- **«Не знаю» без рассуждения.** Лучше: «точно не знаю, но рассуждал бы так…».

## Ответы

1. Модель видит токены (куски слов), а не символы; буквы внутри токена ей напрямую недоступны.
2. **b.** Модель stateless; контекст — это то, что клиент заново отправляет в каждом вызове.
3. В workflow путь шагов задаёт код, в агенте модель сама в цикле выбирает следующий инструмент и решает, когда остановиться.
4. Инструкция в промпте снижает риск, но не гарантирует защиту: модель не разделяет надёжно инструкции и данные. Нужны слои: минимальные права, подтверждение действий, изоляция инструментов, валидация выхода, мониторинг.
5. **c.** Fine-tuning меняет поведение; знания, свежесть и цитаты — задача RAG.
6. Кэш работает по совпадающему префиксу: любое изменение в начале делает недействительным всё, что после него.
7. Стриминг (воспринимаемая латентность падает бесплатно), более быстрая/маленькая модель или каскад (риск для качества), меньше контекста/чанков (риск для качества), кэш ответов (работает только на повторах), отключить reasoning на простых запросах.
8. Нет проверки `overlap >= size` (шаг 0 → `range` бросит ValueError, отрицательный шаг — пустой результат); последние чанки могут быть короткими и целиком содержаться в предыдущем (например, хвост из одного слова-перекрытия) — нужно остановиться, когда чанк дошёл до конца списка.
9. Контекст, архитектура, твои решения, результат с цифрами, что не сработало / что сделал бы иначе.
10. Открытый протокол подключения клиентов (Claude Desktop, IDE, свои агенты) к серверам с инструментами, ресурсами и промптами. Аналогия — LSP: один сервер языка работает во многих редакторах.
11. Честно сказать, что точно не знаешь, и порассуждать вслух: что знаешь рядом, как бы проверил. Это оценивают выше, чем уверенную выдумку.
12. Инженерия — то, что оценивают на роли; суммы и стратегия неинтересны интервьюеру, могут быть конфиденциальными и создают риск утечки.
13. Звучит как вынужденная экономия, без суждения. Лучше: осознанный выбор (OpenAI-совместимый слой, облако + локально), приватность данных, сравнение с Claude на тех же evals с цифрами и понимание, что меняется при переходе на их стек.
14. **b.** У DeepSeek кэш включён по умолчанию и работает без изменений кода (на ноябрь 2026); у Claude стабильный префикс помечается `cache_control`.
15. Например: «DeepSeek хранит данные в Китае, поэтому в облако шли только синтетика и публичные доки, а реальные данные обрабатывались локально через Ollama». Коротко, по фактам, без политических оценок.
