# 2.5 · Упражнение: JSON из 20 текстов  (AIL-9)

> **Неделя 2** · Основы LLM · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Разница между хобби-проектом и продуктом на LLM — в одной фразе: «правильно в 17 из 20, ошибки в основном в поле даты». Это первая настоящая оценка качества (eval) в твоём плане. Умение собрать эталон, посчитать метрики по полям и найти систематические ошибки — центральный навык AI-инженера; на собеседованиях на вопрос «как вы поняли, что стало лучше?» ждут именно такого ответа.

## Теория

### Что такое eval в самом простом виде

```
датасет (входы)  +  эталон (правильные ответы, gold)
        │
        ▼
   твоя система (промпт + модель + схема)  →  предсказания
        │
        ▼
   сравнение предсказаний с эталоном  →  метрики + список ошибок
```

Это ровно то, что ты делал в AIL-7 для меток, только теперь ответ — структура из нескольких полей, и сравнивать надо по каждому полю. Аналогия из обычной разработки: эталон — это ожидаемые значения в unit-тестах, а eval — тестовый прогон, только вместо «зелёный/красный» ты получаешь процент, потому что LLM-система вероятностная и 100% не бывает.

### Датасет: какие тексты брать

20 текстов — мало для статистики, но достаточно, чтобы увидеть типовые ошибки. Важнее разнообразие, чем количество:

| Тип | Сколько | Зачем |
|---|---|---|
| Обычные объявления о листинге (спот и фьючерсы) | 6–8 | «Счастливый путь» |
| Делистинги | 3–4 | Модель может спутать с листингом |
| Несколько монет в одном объявлении | 2 | Проверка схемы (список или одна запись?) |
| Без даты / с относительной датой («в следующий понедельник») | 2–3 | Проверка выдумок и нормализации |
| Описания монет (не объявления) | 2 | Должны давать «не листинг» |
| Строки из своих логов (обезличенные, см. ниже) | 2–3 | Шумные, не похожие на новости входы |

**Безопасность данных.** Логи твоего приложения — данные о реальных сделках и аккаунтах. Правила:
- работаешь только с **копией** (лог-файл скопирован в учебный репо; если берёшь что-то из базы — только через `VACUUM INTO` в отдельный файл, read-only);
- строки логов отправляешь **только в локальную модель (Ollama)** — в DeepSeek и другие облачные API их нельзя даже обезличенными (см. раздел «DeepSeek и Ollama» ниже); и всё равно **обезличь**, ведь датасет лежит в репозитории: убери ID ордеров, балансы, объёмы, суммы PnL, имена аккаунтов, любые ключи/токены; лучше перепиши строку руками, сохранив структуру;
- никаких запросов к биржам, тем более подписанных: тексты объявлений — только с публичных страниц, скопированные вручную;
- если сомневаешься, что строку можно отдавать наружу, — не отдавай, придумай похожую.

### Эталон: разметка — это решения, а не механика

Ручная разметка заставляет тебя решить вопросы, которые ты иначе оставил бы модели:

- Как писать биржу: `Binance`, `binance`, `Binance Futures`? → **канонический вид** (например, нижний регистр, без «Futures»).
- Какая дата, если в тексте «торги начнутся 2026-11-20 08:00 UTC, депозиты открыты с 19-го»? → **правило**: дата начала торгов.
- Делистинг — это `is_listing=false` или отдельный тип события? → **схема**: возможно, лучше поле `event: Literal["listing", "delisting", "other"]`.
- «Перпетуал USDⓈ-M» — это `futures`.

Записывай эти решения в `annotation_guide.md` — это одновременно спецификация для промпта. Хорошая практика: правила разметки почти дословно переходят в описания полей и в `<rules>` промпта.

Формат эталона — JSONL, по строке на пример:

```json
{"id": "t07", "text": "...", "gold": {"event": "listing", "coin": "XYZ", "exchange": "bybit", "listing_date": "2026-11-20", "market_type": "futures"}}
```

### Сравнение по полям

Наивное `pred == gold` для целого объекта даёт одну цифру и ничего не объясняет. Сравнивай **каждое поле отдельно** и с **нормализацией**:

```python
def norm_exchange(v: str | None) -> str | None:
    if v is None:
        return None
    v = v.strip().lower()
    aliases = {"binance futures": "binance", "okx.com": "okx"}   # from your annotation guide
    return aliases.get(v, v)

NORMALIZERS = {
    "coin": lambda v: v.strip().upper().lstrip("$") if v else None,
    "exchange": norm_exchange,
    "listing_date": lambda v: str(v) if v else None,     # ISO string or None
    "market_type": lambda v: v,
    "event": lambda v: v,
}
```

Четыре исхода для каждого поля (важно для полей, которые могут быть `null`):

| gold | pred | Исход |
|---|---|---|
| значение | то же значение | ✅ верно |
| значение | другое значение | ❌ ошибка |
| значение | `null` | ❌ пропуск (модель «не нашла») |
| `null` | значение | ❌ **выдумка** (галлюцинация) — самая опасная |
| `null` | `null` | ✅ верно |

Пропуск и выдумка — разные болезни с разным лечением: пропуск лечат подсказками, где искать; выдумку — явным правилом «если нет в тексте — null». Считай их отдельно.

### Метрики

- **Точность по полю** = верных / всего примеров (для поля). Главная цифра этого упражнения.
- **Exact match** = доля примеров, где верны *все* поля. Строгая метрика «запись целиком правильная».
- **Число выдумок** по полю — отдельно.
- **Ошибки формата** — сколько раз ответ вообще не распарсился (при structured outputs должно быть 0).

Для одной-двух вещей, вроде «нашли ли все монеты в объявлении с несколькими монетами», понадобятся precision/recall — это тема этапа evals, сейчас достаточно отметить такие примеры вручную.

### Анализ ошибок важнее цифры

После прогона выведи таблицу ошибок: id, поле, gold, pred, кусок текста. Потом группируй глазами: «5 из 7 ошибок — дата в формате `20 Nov`», «биржа берётся из ссылки внизу, а не из заголовка». Каждой группе — одна гипотеза и одно изменение (промпт, описание поля, схема, нормализация). Это тот же цикл, что в AIL-7.

Иногда виновата **разметка**: ты сам ошибся или правило было неоднозначным. Это нормально — исправь эталон и запиши, почему.

### Переобучение на 20 примерах

Если улучшать промпт, глядя на те же 20 текстов, ты рано или поздно начнёшь «подгонять» промпт под конкретные примеры. Минимальная защита даже на таком маленьком наборе: **отложи 5 текстов** (holdout) и не смотри на ошибки на них до финального прогона. Если на 15 «рабочих» точность выросла, а на 5 отложенных — нет, ты подогнал промпт под данные.

### Шум

Повтори каждый прогон 2–3 раза: даже при одинаковом промпте ответы немного различаются. Если «до» = 82% ± 3%, а «после» = 84% ± 3%, ты ничего не доказал. Разница, которую стоит обсуждать на 20 примерах, — несколько текстов, а не один.

## DeepSeek и Ollama: как это сделать у нас

Сам eval от провайдера не зависит: датасет, эталон, сравнение по полям, holdout — всё то же. Меняются две вещи: **какие тексты можно отправлять в какую модель** и **как сделать прогон воспроизводимым**.

### Маршрутизация по приватности — в коде, а не в голове

В датасете будут строки из твоих логов. Даже обезличенные, они описывают твою реальную торговлю — **в DeepSeek (серверы в КНР) их не отправляем**. Публичные объявления бирж — можно. Сделай это правилом, которое проверяет код:

```python
# every dataset item has "private": true/false
CLOUD_PROVIDERS = {"deepseek", "openrouter", "anthropic", "openai"}

def guard(item: dict, provider: str) -> None:
    if item.get("private") and provider in CLOUD_PROVIDERS:
        raise PermissionError(f"{item['id']}: private text must stay local (ollama), got {provider}")
```

Отсюда два прогона:

| Прогон | Провайдер | Какие тексты |
|---|---|---|
| A | DeepSeek `deepseek-flash` | все публичные (`private: false`) — 17–18 штук |
| B | Ollama `qwen3:4b` (дефолт для твоего M2 с 8 ГБ) | все 20, включая строки логов |

Есть и третий вариант — вместо реальных строк лога придумать похожие (фейковые) и пометить их `private: false`. Это нормально и даже правильно для публичного репозитория; но тогда ты меряешь качество на фейках — запиши это в `summary.md`.

### Воспроизводимость

- **DeepSeek:** выключи размышление (`thinking: disabled`) и поставь низкую `temperature` — в режиме размышления она молча игнорируется (глава 1.7). Записывай в `results/` поле `model` из ответа: за именем `deepseek-flash` может смениться версия, и тогда «улучшение» v2 → v3 окажется сменой модели.
- **Ollama:** `options={"temperature": 0, "seed": 42}` и ID модели из `ollama list` в конфиге прогона. Используй строгую схему через `format` (глава 2.2) — ошибок формата должно быть 0.
- **Для всех:** конфиг прогона = провайдер, модель, версия промпта, схема, параметры, дата, время (для DeepSeek — пик/вне пика влияет на стоимость).

### Чем отличаются провайдеры в этом упражнении

| | Claude / OpenAI | DeepSeek | Ollama (4B на M2 8 ГБ) |
|---|---|---|---|
| Строгая схема для `extract()` | `parse` | только strict tool (бета) или JSON mode + повтор | `format` со схемой |
| Можно отправлять строки логов | нет (облако; правило курса) | **нет** | да |
| Воспроизводимость | ручек сэмплинга почти нет (у новых Claude — никаких) | `temperature` без размышления, версия за алиасом может смениться | `temperature=0` + `seed`, версия у тебя |
| Стоимость 20 текстов × 3 прогона | центы | доли цента | $0, но минуты времени |
| Чего ждать по качеству | эталон для сравнения | высоко | ниже, особенно на датах и нескольких монетах |

### Что брать для практики

Основной прогон — DeepSeek на публичных текстах (быстро и дёшево, хорошая «планка»), второй — Ollama на всех 20 текстах. Разница точности на одних и тех же публичных текстах покажет, сколько качества ты теряешь, держа данные локально; это пригодится, когда будешь решать, как строить бота над своей базой (глава 3.1 · Проект 1: архитектура бота и копия базы). ## На что обратить внимание

- **Без руководства по разметке эталон «плывёт»**: пример 3 ты разметил так, пример 15 — иначе. Модель не может быть точнее неоднозначного эталона.
- **Нормализация может скрыть ошибки** или наоборот создать их. Нормализуй только то, что для задачи эквивалентно (регистр, `$`), и логируй исходные значения.
- **Даты.** Относительные даты («в понедельник») без даты публикации в контексте не решаются. Если хочешь их извлекать — передавай дату публикации в промпт.
- **Подгонка под тест.** Few-shot примеры не должны быть из этих 20 текстов, и holdout не трогаем до конца.
- **Одна цифра врёт.** «90% exact match» может означать «всё отлично», а может «всё отлично, кроме выдумок в 2 примерах без листинга», что для продукта критично. Смотри метрики по полям и выдумки отдельно.
- **Утечка чувствительных данных** через строки логов — реальная ошибка новичков. Только обезличенные копии.
- **Код сохрани аккуратно** — `eval_extract.py` станет основой твоих evals на этапе 3. Не пиши его одноразово в ноутбуке.

## Ответы

1. Правильные ответы для каждого входа, с которыми сравнивают предсказания. Вручную — потому что это и есть определение «правильно»; размечая, ты принимаешь решения о пограничных случаях.
2. Выдумка запускает действие на несуществующем событии (ложная тревога или неверная сделка), пропуск — лишь упущенная возможность. Для автоматических реакций ложные срабатывания обычно дороже.
3. Чтобы эквивалентные для задачи значения (`Binance`/`binance`, `$PEPE`/`PEPE`) не считались ошибкой. Вредна, если склеивает разное: например, нормализация `Binance Futures` → `binance` в задаче, где важно различать рынки.
4. Ошибки в разных полях приходятся на разные примеры: в каждом примере ошибается какое-то одно поле, поэтому записей, где всё верно, мало.
5. Отложенная часть данных, на которую не смотрят во время улучшений. Проверяет, что улучшение обобщается, а не подогнано под конкретные примеры.
6. Сравниваются объекты целиком без нормализации: одна-единственная цифра, не видно, какие поля ломаются; регистр и формат дат дадут ложные ошибки; не различаются выдумки, пропуски и ошибки формата.
7. **c.** Разница в 2 п. п. на 15 текстах — меньше одного примера, в пределах шума.
8. Правила разметки — это и есть спецификация задачи; если модели их не сообщить, она будет решать пограничные случаи по-своему и «ошибаться» относительно эталона.

11. Чтобы делать анализ ошибок, сравнивать версии по конкретным примерам и воспроизводить прогон (модель, промпт, схема, дата) — это основа будущих evals.
