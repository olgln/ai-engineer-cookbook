# 5.1 · Переформулировка запроса и метаданные  (AIL-60)

> **Неделя 5** · RAG · ⏱ ~4 ч · Практика

## Зачем это AI-инженеру

Пользователи задают вопросы не так, как написана документация: по-русски, на жаргоне, с опечатками, без названия эндпоинта, иногда с тремя вопросами в одном. Документация же написана по-английски и терминами API. Переформулировка запроса и автоматические фильтры — самые дешёвые способы поднять качество поиска, не трогая индекс. На собеседованиях это стандартная тема «query understanding»: multi-query, HyDE, self-query (извлечение фильтров из вопроса).

## Теория

### Разрыв между вопросом и документом

Сравни:

- Вопрос: «бинанс шлёт -2019 когда пытаюсь закрыть шорт, чё делать»
- Документ: «-2019 MARGIN_NOT_SUFFICIENT: Margin is insufficient.»

Эмбеддинг вопроса несёт «шум»: эмоции, жаргон, русский язык, лишние слова. Эмбеддинг документа — сухой английский. Они близки, но не так близки, как могли бы. Задача этапа query understanding — **превратить вопрос человека в запрос, похожий на документ**, и **извлечь из вопроса структурные условия** (биржа, тип API), чтобы сузить поиск.

```
вопрос ─► LLM: {exchange: "binance",
                queries: ["Binance futures error code -2019 margin insufficient",
                          "reduce only close position margin requirement"]}
       ─► поиск по каждому запросу с фильтром exchange=binance
       ─► объединение результатов ─► top-k
```

### Техника 1: Query rewriting

LLM переписывает вопрос в один чистый поисковый запрос: на языке документации, с терминами API, без шума. Самый простой вариант, часто уже даёт заметный прирост на кросс-языковых данных (русский вопрос → английские доки).

Плюсы: дёшево (короткий промпт, маленькая модель). Минусы: один запрос — одна интерпретация; если модель поняла вопрос неправильно, поиск уйдёт не туда.

### Техника 2: Multi-query

LLM генерирует 2–3 **разных** запроса: перефразировки, разные аспекты, подвопросы. По каждому делается поиск, результаты объединяются. Это страховка от неудачной формулировки и способ покрыть составной вопрос («как поставить TP/SL и какой лимит запросов на это?» → два подзапроса).

Объединение результатов:

- **Простое:** собрать все найденные чанки, дедуплицировать по id, для каждого взять лучший скор, отсортировать. Работает, когда скоры сравнимы (одна модель эмбеддингов, одна метрика).
- **Reciprocal Rank Fusion (RRF):** складывать не скоры, а `1 / (60 + rank)` из каждой выдачи. Устойчиво к разным шкалам. Подробно — в AIL-22, где RRF нужен для гибрида; здесь можешь начать с простого объединения и потом переключиться.

Важно, чтобы **исходный вопрос тоже участвовал** в поиске как один из запросов — переписывание иногда ухудшает.

### Техника 3: HyDE (Hypothetical Document Embeddings)

Идея: попросить LLM **написать гипотетический ответ** — фрагмент, похожий на документацию, — и искать по эмбеддингу этого фрагмента, а не вопроса. Эмбеддинг «выдуманного документа» лежит ближе к реальным документам, чем эмбеддинг короткого вопроса (вспомни AIL-18: вопросы и пассажи живут в немного разных регионах пространства).

```
вопрос: "как в окх указать сторону позиции в хедж режиме"
HyDE:   "posSide — Position side. Required in long/short mode. Values: long, short.
         In net mode it is optional ... POST /api/v5/trade/order"
поиск по эмбеддингу HyDE-текста
```

Важная тонкость: гипотетический документ **может содержать выдумки** (неправильные значения параметров) — это не страшно, он используется только для поиска и **никогда не показывается пользователю** и не попадает в контекст ответа. Минусы: дороже и медленнее (генерация 100–200 токенов), и на совсем незнакомых модели темах выдумка может увести поиск не туда.

### Техника 4: извлечение фильтров (self-query)

Из вопроса извлекается структурированное условие для метаданных: биржа, тип API (REST/WebSocket), продукт (spot/futures). Затем фильтр применяется к поиску (AIL-20). В вопросе «у бинанса лимит на ордера» биржа очевидна — а без фильтра в топ-5 попадут чанки про лимиты Bybit и OKX, которые семантически почти идентичны.

Двухступенчатый подход — сначала правила, потом LLM:

```python
import re

ALIASES = {
    "binance": ["binance", "бинанс", "fapi", "dapi"],
    "bybit":   ["bybit", "байбит"],  # not "/v5/": it is a substring of OKX's "/api/v5/"
    "okx":     ["okx", "окх", "окекс", "/api/v5/"],
    "gate":    ["gate", "гейт", "/api/v4/"],
}

def detect_exchange_rules(q: str) -> str | None:
    ql = q.lower()
    hits = {ex for ex, words in ALIASES.items() if any(w in ql for w in words)}
    return hits.pop() if len(hits) == 1 else None  # 0 or 2+ matches: undecided
```

Правила дешёвые, предсказуемые и тестируемые. LLM подключается, когда правила не решили, и одновременно с переписыванием — один вызов возвращает и запросы, и биржу.

Правила фильтрации:

- **Биржа не определена → без фильтра.** Ошибочный фильтр хуже, чем никакого: он гарантированно исключает правильный ответ.
- **Упомянуты две биржи** («чем отличается funding у bybit и okx») → либо два поиска с разными фильтрами, либо фильтр `exchange IN (...)`. Для сравнительных вопросов важно, чтобы в контекст попали куски обеих бирж.
- **Значение фильтра валидируется по списку** допустимых (`bybit|okx|binance|gate`). LLM может вернуть `"Binance Futures"` или `"bitget"` — такое либо нормализуется, либо отбрасывается.

### Один вызов LLM со структурированным ответом

Структурированный вывод (JSON по схеме) ты уже изучал раньше в плане — применяй его здесь. Иллюстративный вызов в стиле официального SDK Anthropic:

```python
# Illustrative: model name comes from .env; check the current Anthropic docs
import json, os
from anthropic import Anthropic
from pydantic import BaseModel, field_validator

EXCHANGES = {"bybit", "okx", "binance", "gate"}

class QueryPlan(BaseModel):
    exchanges: list[str]          # empty = unknown
    queries: list[str]            # 2-3 search queries in English

    @field_validator("exchanges")
    @classmethod
    def only_known(cls, v):
        return [e.lower() for e in v if e.lower() in EXCHANGES]

SYSTEM = """You turn a user's question about crypto exchange APIs into search queries
for an index of official API documentation (Bybit, OKX, Binance, Gate), written in English.
Return JSON only: {"exchanges": [...], "queries": [...]}.
- exchanges: only those explicitly mentioned or unambiguously implied; [] if unsure.
- queries: 2-3 different English queries using API terminology (endpoint names,
  parameter names, error codes). Keep exact identifiers from the question unchanged."""

client = Anthropic()  # reads ANTHROPIC_API_KEY from the environment

def plan_query(question: str) -> QueryPlan:
    msg = client.messages.create(
        model=os.environ["REWRITE_MODEL"],
        max_tokens=300,
        system=SYSTEM,
        messages=[{"role": "user", "content": question}],
    )
    return QueryPlan.model_validate_json(msg.content[0].text)
```

Для переписывания достаточно маленькой и быстрой модели: задача простая, а вызов стоит на горячем пути каждого вопроса. Обязательно обработай ошибку парсинга: fallback — исходный вопрос без фильтра.

### Другие техники (знать названия)

- **Step-back prompting** — сначала задать более общий вопрос («как устроены лимиты запросов у OKX»), потом конкретный.
- **Декомпозиция** — разбить составной вопрос на подвопросы и собрать ответ из частей (зачаток агентного RAG).
- **Query routing** — решить, нужен ли поиск вообще («привет» — не нужен) и в какой индекс идти.
- **Conversational rewriting** — в чате переписать «а у OKX?» в самостоятельный вопрос с учётом истории. Понадобится, если делаешь бота с диалогом.

### Как мерить

Метрика та же, что в AIL-19: **hit rate@k** на golden set. Расширь его до **20 вопросов**: обязательно включи жаргон, русский язык, вопросы без названия биржи, вопросы с кодом ошибки или именем параметра, один-два сравнительных вопроса. Сравнивай варианты:

| Вариант | Что делает |
|---|---|
| baseline | исходный вопрос, без фильтра |
| + filter | исходный вопрос + фильтр по бирже |
| + rewrite | multi-query, без фильтра |
| + rewrite + filter | multi-query + фильтр |
| + HyDE (опц.) | гипотетический документ (+ фильтр) |

Так ты увидишь вклад каждой техники отдельно, а не «стало лучше в целом». Кроме hit rate, запиши **латентность** и **стоимость** на вопрос: rewrite добавляет вызов LLM на горячий путь.

Помни про шум: на 20 вопросах разница в 1 вопрос — это 5 процентных пунктов, и она может быть случайной (например, LLM переписал иначе при повторе). Смотри на разницу в 3+ вопроса и разбирай конкретные изменения: какие вопросы починились, какие сломались.

## DeepSeek и Ollama: как это сделать у нас

Для переписывания нужен один короткий вызов LLM с JSON на выходе. Здесь провайдеры заметно расходятся: **у DeepSeek есть JSON-режим, но нет JSON по схеме**, а у Ollama схему можно передать прямо в запросе. Плюс у DeepSeek по умолчанию включено рассуждение, и это бьёт по латентности и воспроизводимости.

### DeepSeek: JSON-режим + выключенное рассуждение

Факты на ноябрь 2026 (по [JSON Output](https://api-docs.deepseek.com/guides/json_mode), [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode) и [справке Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion)):

- `response_format={"type": "json_object"}` гарантирует только «валидный JSON», а не твою схему. Варианта `json_schema` документация не описывает. В промпте обязательно слово «json» и пример нужной структуры, а `max_tokens` должен быть с запасом.
- Если модель не смогла выдать валидный JSON, API заменяет содержимое пробелами: `content` бывает **пустым** при `finish_reason == "stop"`. Это надо обрабатывать: повтор или fallback.
- Рассуждение (thinking) включено по умолчанию. В режиме рассуждения `temperature` **не действует** (ошибки нет, значение просто игнорируется). Для переписывания рассуждение не нужно: выключай его через `extra_body={"thinking": {"type": "disabled"}}`. Тогда и вызов быстрее, и `temperature=0` снова работает, что важно для воспроизводимых evals.

```python
# Illustrative: DeepSeek via the OpenAI SDK; key and model name come from .env
import json, os
from openai import OpenAI

ds = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"], base_url="https://api.deepseek.com")

SYSTEM_JSON = SYSTEM + """
Output json only, exactly like this example:
{"exchanges": ["okx"], "queries": ["OKX place order posSide long/short mode", "posSide parameter hedge mode"]}"""

def plan_query_deepseek(question: str) -> QueryPlan | None:
    resp = ds.chat.completions.create(
        model=os.environ["REWRITE_MODEL"],              # e.g. deepseek-flash
        messages=[{"role": "system", "content": SYSTEM_JSON},
                  {"role": "user", "content": question}],
        response_format={"type": "json_object"},
        temperature=0,                                  # has effect only with thinking disabled
        max_tokens=400,
        extra_body={"thinking": {"type": "disabled"}},  # DeepSeek-specific switch
    )
    text = (resp.choices[0].message.content or "").strip()
    if not text:                                        # documented: may come back blank
        return None                                     # caller falls back to the raw question
    try:
        return QueryPlan.model_validate_json(text)      # schema is enforced HERE, not by the API
    except ValueError:
        return None
```

### Ollama: схема прямо в запросе

У Ollama нативный параметр `format` принимает JSON Schema, и вывод модели ограничивается этой схемой ([Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)). Pydantic даёт схему одной строкой:

```python
# Illustrative: small local model, e.g. qwen3:4b (~2.5 GB; tools and thinking per the Ollama library)
import ollama

def plan_query_ollama(question: str) -> QueryPlan:
    resp = ollama.chat(
        model=os.environ["REWRITE_MODEL_LOCAL"],
        messages=[{"role": "system", "content": SYSTEM},
                  {"role": "user", "content": question}],
        format=QueryPlan.model_json_schema(),   # output is constrained to this schema
        options={"temperature": 0},
        think=False,                            # thinking models: no reasoning for a rewrite task
    )
    return QueryPlan.model_validate_json(resp.message.content)
```

Валидация Pydantic всё равно нужна: схема гарантирует форму, а не смысл (`"exchanges": ["bitget"]` пройдёт схему со списком строк, но не твой валидатор). Про `think`: по [документации Ollama](https://docs.ollama.com/capabilities/thinking) `false` просит модель не рассуждать, а модель, которая не умеет выключать рассуждение, использует минимальный уровень.

**Память.** У тебя M2 с 8 GB, и на нём же работает арбитражное приложение. Поэтому по умолчанию бери модель класса 4B: `qwen3:4b` (скачивание ~2.5 GB, по странице библиотеки Ollama). В памяти модель занимает примерно свой размер плюс контекст. `qwen3:8b` (~5.2 GB) — только когда всё остальное закрыто и автоторговля не включена; модели 14B и больше на этом Mac не запускай. Для переписывания запроса 4B-модели обычно хватает, но проверь это цифрами на golden set. Если модель ошибается в JSON или в бирже — это аргумент за DeepSeek: для этой задачи (публичные доки) он подходит. Ставь модель заранее через `ollama pull`.

### Сравнение провайдеров для этой главы

| Что нужно | Claude | OpenAI | DeepSeek | Ollama |
|---|---|---|---|---|
| JSON на выходе | Structured outputs / tool use (смотри актуальную документацию) | `response_format` с `json_schema` (структурированный вывод по схеме) | Только `json_object`: валидный JSON без схемы | `format` = JSON Schema (нативный API) |
| Гарантия схемы | Да, в режиме structured outputs | Да, в strict-режиме | **Нет** → Pydantic + повтор/fallback | Форма ограничена схемой; смысл проверяет Pydantic |
| Пустой ответ | — | — | Возможен (документирован) → обработать | — |
| Рассуждение по умолчанию | Зависит от модели и параметров | Зависит от модели | **Включено**; выключается `thinking: disabled` | У thinking-моделей; `think=False` |
| `temperature` | У новых моделей есть ограничения (смотри документацию) | Зависит от модели | Игнорируется в режиме рассуждения | Работает через `options` |
| Латентность rewrite | Сеть | Сеть | Сеть + рассуждение, если не выключено | Без сети, но зависит от Mac |

### Что использовать в практике

- **Основной путь:** DeepSeek `deepseek-flash` с выключенным рассуждением. Данные — публичная документация и твои вопросы о ней, поэтому отправлять их можно. Вопросы не должны содержать ничего из торгового приложения (сделки, балансы, ключи).
- **Офлайн-вариант:** Ollama с `format` = схема — сравни hit rate и латентность с DeepSeek на тех же 20 вопросах.
- **Для сравнения (по желанию):** Claude или OpenAI со structured outputs — исходный код из «Теории».
- **HyDE** — любой из генераторов; гипотетический документ и так никуда, кроме поиска, не идёт.

## Маршрут изучения

1. Перечитай раздел «Обработка запроса» в [AIL-59](AIL-59.md) и свой разбор промахов из [AIL-19](AIL-19.md) (≈10 мин). Выпиши, какие промахи были из-за формулировки вопроса — их ты и чинишь.
2. Найди и прочитай статью, которая ввела HyDE: «Precise Zero-Shot Dense Retrieval without Relevance Labels» (Gao et al., 2022, arXiv) — абстракт, введение и рисунок с общей схемой (≈25 мин). Вынеси: почему гипотетический документ, а не вопрос, и почему фактические ошибки в нём не мешают поиску.
3. Открой [Eugene Yan: Patterns for Building LLM-based Systems](https://eugeneyan.com/writing/llm-patterns/) → в разделе RAG найди место про HyDE и про сочетание поиска с фильтрами (≈15 мин).
4. Открой [DeepSeek: JSON Output](https://api-docs.deepseek.com/guides/json_mode) и [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode) (≈20 мин). Вынеси: `json_object` без схемы, требование слова «json» и примера в промпте, пустой `content` как документированный случай, как выключить рассуждение и какие параметры в режиме рассуждения не действуют.
5. Открой [Ollama: Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs) и [Thinking](https://docs.ollama.com/capabilities/thinking) (≈15 мин). Вынеси: `format=Model.model_json_schema()`, `model_validate_json` на выходе, параметр `think`.
6. Для сравнения — документация по structured outputs у [Anthropic](https://docs.anthropic.com) или [OpenAI](https://platform.openai.com/docs) (≈15 мин). Запиши, чем «JSON по схеме с гарантией» отличается от JSON-режима DeepSeek.
7. Документация твоей векторной БД (sqlite-vec из AIL-20) по фильтрации — освежи, как фильтр ставится внутрь KNN-запроса (≈10 мин).

## На что обратить внимание

- **Переписывание теряет точные идентификаторы.** LLM «улучшает» `-2019` до «margin error» или `posSide` до «position side» — и поиск по точному термину ломается. В промпте явно: «сохраняй коды ошибок, имена эндпоинтов и параметров без изменений». Полностью проблема решается гибридным поиском (AIL-22).
- **Ложный фильтр.** Модель «догадалась», что речь о Bybit, хотя биржа не названа — фильтр исключает правильный ответ. Лучше без фильтра, чем с неверным.
- **Алиасы-подстроки дают ложные срабатывания**: `"gate"` найдётся в «aggregate trades», `"/v5/"` — в путях и Bybit, и OKX. В боевом коде ищи по границам слов (`re.search(r"\bgate\b", ...)`) и покрой это тестом.
- **Не выкидывай исходный вопрос** из multi-query — переписанные запросы иногда хуже.
- **HyDE-текст не идёт в ответ.** Он может быть выдумкой; только для поиска.
- **Латентность.** +1 вызов LLM на каждый вопрос: 300–1500 мс. Для чата терпимо, для автодополнения — нет. Маленькая модель, короткий `max_tokens`, кэш одинаковых вопросов.
- **Невалидный JSON / неизвестная биржа.** Всегда валидация (pydantic) и fallback на исходный вопрос.
- **Недетерминизм.** Один и тот же вопрос может переписываться по-разному между прогонами. Для eval фиксируй температуру низкой и/или кэшируй планы запросов на диск, чтобы сравнения были воспроизводимы.
- **Утечка golden set в промпт.** Не вставляй в промпт переписывания примеры из golden set — получишь завышенные цифры. Few-shot примеры бери из других вопросов.

## Ответы

1. Язык (русский вопрос, английские доки), жаргон и шум в вопросе; короткий вопрос и длинный пассаж — разные по форме тексты и лежат в разных регионах пространства эмбеддингов.
2. Rewriting даёт один «чистый» запрос, multi-query — несколько разных, по каждому ищут и объединяют результаты. Страхует от неудачной интерпретации и покрывает составные вопросы.
3. LLM пишет гипотетический фрагмент-ответ в стиле документации, и поиск идёт по его эмбеддингу. Он используется только для поиска: важно, что он «похож» на нужный документ по теме и терминам, а неточные значения не попадают в ответ пользователю.
4. b). Неверный фильтр гарантированно исключает правильный ответ; без фильтра нужный кусок ещё может найтись.
5. Переписанные запросы иногда хуже исходного (потеряли деталь, неправильно поняли смысл); исходный вопрос — страховка.
6. Он требует удалить коды и идентификаторы — а это самые точные сигналы для поиска по докам API (`-2019`, `posSide`, имя эндпоинта). Нужно наоборот: сохранять их без изменений. Также не указан формат вывода и не учтены фильтры.
7. Четыре прогона на одном golden set: baseline, только фильтр, только переписывание, переписывание + фильтр. Разница baseline→filter и baseline→rewrite показывает вклад каждого по отдельности.
8. Задача простая, а вызов стоит на горячем пути каждого вопроса: латентность и стоимость важнее максимального качества.
9. Нет: разница в один вопрос на 20 — в пределах шума (в том числе из-за недетерминизма LLM). Нужна разница побольше, повторные прогоны и разбор конкретных изменённых вопросов.
10. Распознать две биржи, сделать два поиска (по фильтру каждой) или фильтр `IN (bybit, okx)`, и следить, чтобы в итоговый контекст попали куски обеих бирж.
11. Когда примеры из тестового набора попадают в промпт (few-shot) — модель «видела ответы», и метрики завышены, не отражая качество на новых вопросах.
12. Первая: рассуждение включено по умолчанию, поэтому `temperature=0` игнорируется (переписывание недетерминировано), а вызов медленнее и дороже. Нужно `extra_body={"thinking": {"type": "disabled"}}`. Вторая: JSON-режим не проверяет схему; нужны слово «json» и пример в промпте, валидация Pydantic и обработка пустого ответа.
13. В промпте может не быть слова «json» и примера (требование DeepSeek); `content` бывает пустым — `json.loads` упадёт; схема не проверяется (может не быть ключа `exchanges`); `[0]` падает на пустом списке, а неизвестная биржа не отбрасывается. Нужны `QueryPlan.model_validate_json`, проверка пустоты и fallback на исходный вопрос.
14. b). Ollama ограничивает генерацию переданной схемой, а JSON-режим DeepSeek обещает только синтаксически валидный JSON (и иногда пустой ответ). Смысл значений в обоих случаях проверяет твой валидатор.
