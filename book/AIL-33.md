# 8.3 · Эксперимент: модели и реранкер  (AIL-33)

> **Неделя 8** · Evals · ⏱ ~4–5 ч · Проект

## Зачем это AI-инженеру

Выбор модели — решение, которое инженер принимает постоянно, и почти никогда ответ не «самая сильная». Задача — найти конфигурацию, которая достаточно хороша при приемлемой цене и задержке. Вопрос «как вы выбирали модель?» на собеседовании ждёт ответа с цифрами: «маленькая модель с реранкером даёт ту же correctness в пределах шума, в 5 раз дешевле и вдвое быстрее».

## Теория

### Три оси: качество, цена, скорость

У каждой конфигурации три числа:

- **качество** — correctness, faithfulness, hit@k с твоего набора;
- **цена** — стоимость 100 вопросов (только система, без судьи);
- **скорость** — латентность p50 и p90 от вопроса до готового ответа.

Обычно они тянут в разные стороны. Задача — не максимизировать одно, а найти **фронт Парето**: конфигурации, у которых нельзя улучшить одну ось, не ухудшив другую. Всё, что хуже какой-то другой конфигурации по всем осям, отбрасывается сразу.

```
 качество
   ▲
   │                 ● большая + реранкер
   │         ● маленькая + реранкер
   │                        ● большая
   │   ● маленькая
   │                                  ✕ большая, длинный промпт (хуже и дороже)
   └──────────────────────────────────────► цена
```

### Сначала требования, потом выбор

Без требований выбрать нельзя: «лучшая» конфигурация зависит от того, что важно. Запиши их до эксперимента, как будто это продуктовые требования к твоему ассистенту по докам бирж:

- **порог качества**: correctness не ниже baseline минус разброс; faithfulness ≥ 0,9 (ассистент по API не должен выдумывать параметры);
- **бюджет**: например, не дороже $X на 1000 вопросов;
- **латентность**: p90 не больше N секунд (бот в Telegram, пользователь ждёт).

Правило выбора: **самая дешёвая (или самая быстрая) конфигурация, которая проходит порог качества**. Это сразу превращает спор «какая модель лучше» в проверку условий.

### Как читать внешние рейтинги

**[Artificial Analysis](https://artificialanalysis.ai)** — сравнивает модели по агрегированным бенчмаркам качества, цене за токены и скорости (время до первого токена, токены в секунду) у разных провайдеров. Полезно для **короткого списка кандидатов** и оценки порядков цен и скорости.

**[LMArena](https://lmarena.ai)** — рейтинг по попарным слепым голосованиям людей в чате. Отражает, какие ответы людям нравятся в общем разговоре; на него влияют стиль, длина и форматирование.

Ни один из них не отвечает на твой вопрос: как модель работает **на твоей задаче** (ответ по найденным кускам документации бирж, с цитатами, с отказом, когда ответа нет). Модель, лидирующая в рейтинге, может хуже следовать инструкции «отвечай только по документам» и чаще выдумывать. Рейтинги — для выбора кандидатов, твой eval — для решения.

### Из чего складывается стоимость

```
cost per question = Σ по вызовам: input_tokens × price_in + output_tokens × price_out
```

Для RAG основной вклад — **входные токены**: системный промпт плюс k кусков контекста. Поэтому:
- k=10 против k=5 почти удваивает стоимость ответа;
- реранкер, сокращающий 20 кандидатов до 4 лучших, может **уменьшить** стоимость генерации, даже если сам стоит денег;
- prompt caching снижает стоимость повторяющейся части (системного промпта), но не кусков, которые разные для каждого вопроса;
- переформулировка запроса из [AIL-60](AIL-60.md) — ещё один вызов модели, тоже считается.

Цены бери со страниц цен провайдеров на дату эксперимента (они меняются, и у разных моделей одного провайдера отличаются в разы) и записывай дату в журнал. Модели называй точными идентификаторами из документации.

### Из чего складывается латентность

```
latency = rewrite + retrieve + rerank + (time to first token + output_tokens / tokens_per_sec)
```

- Маленькие модели обычно быстрее и по времени до первого токена, и по скорости генерации.
- Реранкер-кросс-энкодер на CPU для 20 пар может занимать заметное время; API-реранкер добавляет сетевой вызов.
- Длинный ответ медленнее: выходные токены дорогие и по цене, и по времени.
- Латентность API шумит по времени суток. Меряй варианты вперемешку, а не «утром A, вечером B».

Если продукт стримит ответ (как обычно делают в чатах), для пользователя важнее время до первого токена; для пакетных сценариев — полное время.

### Реранкер: что он меняет

Как работает реранкер (cross-encoder против bi-encoder), ты разобрал в [AIL-22](AIL-22.md). Здесь важно, что он меняет в экспериментальном смысле:

- **Поиск**: широкий отбор (топ-20/30 гибридом), затем реранкер выбирает топ-k. Растёт MRR и hit@3/hit@5 при той же итоговой длине контекста.
- **Генерация**: модель получает более точный контекст, меньше отвлекающих кусков. Маленькой модели это обычно помогает сильнее, чем большой, потому что она хуже игнорирует мусор в контексте. Это гипотеза, её и проверишь.
- **Цена/скорость**: локальный реранкер ничего не стоит в деньгах, но стоит времени; API-реранкер — наоборот.

Локальный кросс-энкодер через Sentence Transformers (иллюстративно):

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L6-v2")  # small English model; check sbert.net for multilingual ones

def rerank(question: str, chunks: list[dict], top_k: int) -> list[dict]:
    ranked = reranker.rank(question, [c["text"] for c in chunks])  # sorted by score
    return [chunks[r["corpus_id"]] for r in ranked[:top_k]]
```

Учти язык: многие популярные кросс-энкодеры обучены на английском, а часть твоих вопросов на русском при английской документации. Проверь срез по языку.

### Дизайн эксперимента: 2×2

Два фактора (модель ответа, реранкер) — четыре конфигурации:

| | без реранкера | с реранкером |
|---|---|---|
| маленькая модель | S | S+R |
| большая модель | L | L+R |

Это лучше, чем две отдельные пары, потому что видно **взаимодействие**: например, реранкер почти не нужен большой модели, но сильно помогает маленькой. Тогда S+R может оказаться на фронте Парето.

Что фиксировано во всех четырёх: индекс (лучший из [AIL-32](AIL-32.md)), промпт ответа, судья, набор, k на входе в модель.

**Судья не меняется.** Если судья из того же семейства, что одна из моделей-кандидатов, учитывай самопредпочтение (из [AIL-27](AIL-27.md)): проверь на своей разметке, нет ли перекоса.

**Промпт ответа** может по-разному подходить разным моделям. Честный вариант — один промпт для всех; если маленькая модель явно ломает формат (например, не ставит ссылки), это результат, а не повод тайно подкручивать промпт только ей. Отдельная настройка промпта под модель — отдельный эксперимент.

### Подсчёт и представление

Скрипт из [AIL-29](AIL-29.md) уже пишет `usage` и латентность по вопросу. Для эксперимента нужна сводная таблица:

| Конфиг | hit@5 | correctness | faithfulness | $ / 100 вопросов | p50, с | p90, с |
|---|---|---|---|---|---|---|
| S | | (разброс) | | | | |
| S+R | | | | | | |
| L | | | | | | |
| L+R | | | | | | |

И парные сравнения ключевых пар (L против S+R, S против S+R) по правилу значимости из [AIL-62](AIL-62.md). Полезный график — точечная диаграмма «качество против цены» с подписями точек: на ней фронт Парето виден сразу.

### Рекомендация

Финальный продукт задачи — рекомендация в 5–8 предложениях, например в форме:

> Для продакшена беру S+R: correctness 0,8x (разброс ±0,02), в пределах шума от L+R (расхождения 5/4, p ≈ 1), faithfulness 0,9x, стоимость в N раз ниже ($a против $b на 100 вопросов), p90 латентности x с против y с. Реранкер дал маленькой модели +Z п.п. correctness (расхождения 10/2), большой — в пределах шума. Ограничения: набор 58 вопросов, мелкие различия не различимы; на comparative-вопросах (n=12) L+R выглядит лучше, проверить на расширенном наборе. Финальная цифра на holdout: …

Здесь же финальную выбранную конфигурацию впервые прогоняешь на **holdout** (один раз) — это та честная цифра, которая пойдёт в README.

## DeepSeek и Ollama: как это сделать у нас

На нашем стеке этот эксперимент становится самым интересным в Проекте 3: **локальная модель против DeepSeek**, с реранкером и без. Сверено в ноябре 2026 по [api-docs.deepseek.com](https://api-docs.deepseek.com), [docs.ollama.com](https://docs.ollama.com) и [ollama.com/library](https://ollama.com/library); id моделей, цены и теги проверь перед экспериментом.

### Кандидаты под твоё железо

У тебя Apple M2 с 8 ГБ памяти, и на нём же работает арбитражное приложение. Это определяет «маленькую» модель:

| Роль в дизайне 2×2 | Модель | Комментарий |
|---|---|---|
| S (маленькая) | локальная модель класса 4B в Ollama, например `qwen3:4b` (веса ≈2,5 ГБ по странице модели, ноябрь 2026) | помещается рядом с приложением; бесплатно; данные не покидают Mac. Тег пиши явно: просто `qwen3` — это `qwen3:8b` (≈5,2 ГБ) |
| L (большая) | `deepseek-flash`, thinking выключен | дёшево, контекст 1M, быстрее твоего Mac на длинном контексте |
| (опционально) L+ | `deepseek-v4-pro` или `deepseek-flash` с thinking | что даёт ещё более сильная модель или рассуждения и сколько это стоит |
| (для сравнения) | одна модель Claude и/или OpenAI | на тех же публичных вопросах: где DeepSeek на фронте Парето относительно рынка |

7–8B локально — только закрыв всё остальное и не держа автоторговлю включённой (и это отдельный прогон, не смешивай его с остальными по латентности); 14B и больше на 8 ГБ не помещаются. **Не гоняй локальные прогоны, пока автоторговля включена**: модель, реранкер и арбитражное приложение будут делить 8 ГБ, приложение может начать тормозить, а ты получишь латентность, которая меряет своп, а не модель.

### Судья не меняется — и именно здесь самопредпочтение опасно

Судья во всех конфигурациях — `deepseek-v4-pro` без thinking (глава [6.4 · Скрипт оценки: retrieval + faithfulness](AIL-29.md)). Локальная 4B-модель судьёй быть не может: она слабее обоих ответчиков. Но судья из семейства DeepSeek сравнивает ответ DeepSeek с ответом qwen — ровно тот случай, где самопредпочтение искажает вывод «S против L». Поэтому:

- вопросы, где S и L разошлись (обычно 10–20), разметь сам, не глядя на вердикты судьи, и посчитай согласие судьи отдельно на этих вопросах;
- (опционально) прогони на них же судью другого семейства — Claude или OpenAI (данные публичные).

Если судья систематически оценивает DeepSeek лучше, чем ты, — это результат, его пишут в журнал, а не прячут.

### Честное сравнение: контекст, прогрев, очередь

У облачной модели и локальной разные ловушки, и каждая может «подарить» победу не той стороне:

1. **Контекст.** Ollama на Mac с памятью меньше 24 ГБ по умолчанию даёт модели 4k токенов. Системный промпт + 5 кусков по 600–800 токенов + вопрос туда не помещаются, хвост молча обрезается, и S проигрывает не из-за ума, а из-за обрезки. Подними контекст (`OLLAMA_CONTEXT_LENGTH` при запуске сервера или `num_ctx` в нативном API; через OpenAI-совместимый эндпоинт размер контекста задать нельзя) до нужного, но на 8 ГБ осторожно — например 8k — и проверь `ollama ps`: CONTEXT и то, что модель целиком на GPU (PROCESSOR). Если не влезает, это тоже результат: «на 8 ГБ S работает только с k=3».
2. **Прогрев.** Ollama выгружает модель через 5 минут без запросов (`keep_alive`), и первый запрос включает загрузку модели в память. Сделай прогревочный запрос и не учитывай его в латентности.
3. **Очередь.** По умолчанию Ollama обрабатывает запросы к модели по одному; параллельный прогон меряет ожидание в очереди. Локальную конфигурацию гоняй последовательно.
4. **Сеть и часы пик DeepSeek.** Латентность DeepSeek включает сеть до серверов в Китае и нагрузку; цена зависит от окна пик/вне пика. Гоняй конфигурации вперемешку и в одном окне цен.
5. **Квантизация.** Теги Ollama по умолчанию — квантизованные веса. Записывай точный тег (`qwen3:4b`, а не «qwen 4B»): другой тег — другая модель.
6. **Режим рассуждений.** `qwen3` в библиотеке Ollama помечена как модель с thinking. Сравнивай S и L в одинаковом режиме (обе без рассуждений) или делай режим отдельным фактором; как выключить рассуждения у конкретной модели в Ollama, смотри в её документации (параметр `think` / `reasoning_effort`, поддержка зависит от модели).

### Стоимость: что писать для локальной модели

У Ollama $0 за токены, но «бесплатно» не значит «без цены». В таблице пиши для S «$0 API» плюс латентность на твоём M2 и пометку «модель на устройстве пользователя». На графике «качество против цены» S окажется на нулевой цене; добавь второй график «качество против p90 латентности» — там картина честнее. Для DeepSeek считай `cost.py` из главы 6.4 (кеш-попадания, пик/вне пика). Порядок для L без thinking: ответ ~3500 входных + 300 выходных токенов — около $1,4 на 1000 вопросов в пик и вдвое меньше вне пика (оценка; сверь с фактом).

### Реранкер на 8 ГБ

Реранкер остаётся локальным кросс-энкодером из sentence-transformers. Маленькая модель вроде `cross-encoder/ms-marco-MiniLM-L6-v2` занимает мало памяти, но обучена на английском. Многоязычные кросс-энкодеры (например, у организации BAAI на Hugging Face есть серия `bge-reranker`) заметно крупнее; рядом с Ollama и арбитражным приложением на 8 ГБ проверь, что всё помещается, и меряй время реранкера отдельно. Скачивай модели только из официальных организаций на Hugging Face и закрепляй ревизию.

### Сравнение провайдеров для этой главы

| Ось сравнения | Claude | OpenAI | DeepSeek | Ollama (4B на M2 8 ГБ) |
|---|---|---|---|---|
| Качество на RAG по докам | сильные модели, проверяй на своём наборе | то же | Flash/Pro — проверяй на своём наборе | заметно слабее; чаще ломает формат и отказы |
| Цена | по странице цен | по странице цен | центы на сотню вопросов; пик и вне пика | $0 API, платишь памятью и временем |
| Латентность | сеть + нагрузка | сеть + нагрузка | сеть до Китая + нагрузка | твой Mac: прогрев, контекст, очередь, своп |
| Контекст | большой | большой | 1M токенов | 4k по умолчанию на 8 ГБ, поднимать осторожно |
| Приватность | облако | облако | серверы в Китае | всё локально |
| Где на фронте Парето вероятнее | качество | качество | цена/качество | только «приватно и офлайн» |

Последняя строка — гипотеза, а не вывод: эксперимент как раз и проверит, есть ли у локальной 4B-модели место на фронте для публичных доков или её ниша — только приватные данные и офлайн.

## Маршрут изучения

1. Открой [Artificial Analysis](https://artificialanalysis.ai) → страницу сравнения моделей (≈20 мин). Найди 2–3 кандидата: одну сильную модель и одну-две маленькие/дешёвые у провайдера, которым пользуешься. Выпиши цену за 1M входных/выходных токенов, время до первого токена, токены в секунду. Сверь цены со страницей цен самого провайдера.
2. Открой [LMArena](https://lmarena.ai) → лидерборд (≈10 мин). Посмотри, где твои кандидаты. Запиши для себя, почему рейтинг людей в чате ≠ качество ответа по документам.
3. Открой [Sentence Transformers: Cross Encoder usage](https://sbert.net/docs/cross_encoder/usage/usage.html) (≈15 мин). Метод `rank`, порядок результатов, заметка про масштаб оценок. Посмотри список предобученных кросс-энкодеров на sbert.net, есть ли многоязычные.
4. Перечитай в [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval) раздел про реранкинг (≈10 мин): какой эффект там получен и какой ценой по латентности.
5. В [What We Learned from a Year of Building with LLMs](https://applied-llms.org) найди советы про выбор модели и маленькие модели (≈15 мин).
6. Документация цен своего провайдера: страница pricing и раздел про prompt caching (≈10 мин).
7. Открой [DeepSeek: Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing) (≈10 мин): цены Flash и Pro с кеш-попаданием и промахом, окна пик/вне пика. Перенеси в `evals/prices.json` с датой.
8. Открой [ollama.com/library/qwen3](https://ollama.com/library/qwen3) и [Ollama: Context length](https://docs.ollama.com/context-length) (≈15 мин): размеры и теги модели, сколько она занимает, как контекст зависит от памяти. Выбери тег, который помещается в 8 ГБ рядом с арбитражным приложением.
9. Открой [Ollama: FAQ](https://docs.ollama.com/faq) → разделы про `keep_alive` и параллельные запросы (≈10 мин): отсюда прогрев и последовательный прогон.

## На что обратить внимание

- **«Возьмём самую сильную модель»** без измерения — дорого и не обязательно лучше на твоей задаче.
- **Сравнение моделей с разными промптами** — сравнение промптов, а не моделей.
- **Цена из памяти или из старой статьи.** Только со страницы цен, с датой.
- **Средняя латентность вместо p90**: пользователь Telegram-бота запоминает медленные ответы.
- **Латентность меряется в разное время суток** — шум API выдают за разницу моделей.
- **Реранкер на английском** для русских вопросов может ухудшить выдачу; смотри срез.
- **Маленькая модель ломает формат** (нет ссылок `[1]`, нет отказа на unanswerable). Это часть качества; проверь assertions из [AIL-27](AIL-27.md) (наличие ссылок) отдельной метрикой.
- **Rate limits.** Параллельный прогон 4 конфигураций может упереться в лимиты; ретраи искажают латентность. Записывай число ретраев и исключай время ожидания из латентности или гоняй последовательнее.
- **Holdout — один раз**, только для финальной конфигурации.
- **Локальная модель проиграла из-за обрезанного контекста**, а не из-за качества. Проверь `ollama ps` и `prompt_eval_count` до того, как писать вывод.
- **Холодный старт и очередь Ollama в латентности.** Прогрев, последовательный прогон, первый запрос не учитывать.
- **Прогон локальной модели при включённой автоторговле** на 8 ГБ — риск для арбитражного приложения и мусорная латентность. Только при выключенной автоторговле.
- **Судья DeepSeek сравнивает DeepSeek с qwen.** Самопредпочтение искажает именно вывод «S против L»; проверь согласие на разошедшихся вопросах.
- **«$0» у локальной модели на графике цены** выглядит как безусловная победа. Добавь ось латентности и качество.

## Ответы

1. Множество конфигураций, у которых нельзя улучшить одну ось (качество, цена, скорость), не ухудшив другую; всё, что доминируется, отбрасывается.
2. LMArena отражает предпочтения людей в общем чате (с влиянием стиля и длины), а не следование инструкции «отвечай только по документам» и точность фактов в твоей предметной области.
3. **b.** Каждый вопрос несёт системный промпт и k кусков документации, это тысячи токенов против сотен на выходе.
4. Он позволяет отдавать модели меньше, но более точных кусков (например, 4 вместо 8) при том же или лучшем качестве, и входных токенов становится меньше.
5. Видно взаимодействие факторов: эффект реранкера может зависеть от модели (сильно помогает маленькой, почти не помогает большой).
6. Скорее маленькую: 6/4 — шум, разница не установлена, и требования, вероятно, выполнены. Проверить: порог качества с учётом разброса, faithfulness и формат (ссылки, отказы), срезы (не проваливается ли тип вопросов), латентность, и подтвердить на holdout.
7. Изменено несколько переменных: разные промпты и k, поэтому сравниваются не модели. Судья из того же семейства, что L — возможное самопредпочтение. Нет разброса и парного сравнения.
8. Латентность API колеблется по времени суток и нагрузке; если гонять A утром, а B вечером, разница сети будет приписана моделям.
9. Иначе требования подгоняются под понравившийся результат; заранее заданные пороги превращают выбор в проверку условий.
10. Dev использовался для выбора, поэтому его цифра оптимистична; holdout даёт честную оценку. Повторные прогоны с подстройкой превратили бы holdout во второй dev.
11. Не обрезан ли контекст: на Mac с 8 ГБ Ollama по умолчанию даёт 4k токенов, длинные куски молча отбрасываются. Посмотреть `ollama ps` (CONTEXT) и `prompt_eval_count`, поднять контекст (осторожно) или уменьшить k и перепрогнать.
12. Судья из семейства DeepSeek может выше оценивать ответы своего семейства, и это искажает ровно сравниваемую пару. Нужна своя разметка разошедшихся вопросов (и, по желанию, судья другого семейства на них).
13. Ollama по умолчанию обрабатывает запросы к модели по одному, поэтому параллельные запросы меряют ожидание в очереди; после 5 минут простоя модель выгружена, и первый запрос включает её загрузку. Плюс на 8 ГБ параллельность увеличивает память и может вызвать своп.
