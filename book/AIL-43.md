## Зачем это AI-инженеру

Четвёртый проект в портфолио. Рекрутер и инженер на скрининге проводят над репозиторием 2–5 минут: за это время README должен показать задачу, архитектуру, пример результата, цифры evals и то, что ты думаешь о безопасности. Агент с доступом к торговым данным, у которого безопасность продумана и измерена, — сильная история именно потому, что большинство демо-агентов об этом молчат.

## Теория

### Главное правило публичного репозитория

**Ни одного байта реальных торговых данных.** Ни копии базы, ни логов, ни реальных отчётов, ни скриншотов с твоими позициями, ни ID форм, ни сумм, ни дат конкретных сделок. Публичная демо-версия работает **только на фейковых данных**, которые генерирует скрипт. И, конечно, никаких ключей: ни LLM-провайдера, ни бирж (бирж в проекте вообще нет).

Что можно публиковать из реальной работы: агрегированные метрики агента (точность, шаги, токены, стоимость) без торговых подробностей — или, проще и чище, прогони evals ещё и на фейковом наборе и публикуй их. Реши заранее и напиши в README, на каком наборе получены цифры.

### Генератор фейковых данных

Фейковые данные должны быть **правдоподобными**, иначе демо ничего не покажет: те же таблицы, что в реальной схеме (минимально нужные колонки), согласованные ноги, логи, которые подтверждают историю, спреды вокруг закрытия.

```
scripts/make_fake_data.py
  ├─ fake Forms: 6 pairs, invented symbols (FAKEUSDT, DEMOUSDT...) or common majors
  ├─ fake Positions: 40 positions = 80 legs, scenarios by closedBy:
  │     auto (spread hit closeSpread), manual, liquidation+hedge, naked, adl, unknown
  ├─ fake SpreadBuckets around open/close times, shaped by scenario
  └─ fake logs: lines in the same format as the real log, consistent with the scenario
```

Подход: для каждого сценария пишешь функцию, которая генерирует согласованный набор (ноги + спред + строки лога) от случайного стартового времени. Фиксированный `random.seed(42)` — чтобы демо было воспроизводимым и отчёт в README совпадал с тем, что получит читатель. Не делай фейк копированием реальных строк с заменой цифр: в «заменённом» логе легко оставить реальный ID ордера или время.

Сценарии из генератора одновременно становятся **публичным golden set** для evals: ты знаешь ожидаемую причину каждого случая по построению.

### Структура README

1. **Заголовок и одна фраза:** «Read-only AI agent that investigates why a crypto arbitrage position was closed, using an MCP server over a snapshot of the trading database».
2. **Демо за 30 секунд:** GIF или блок с командой и фрагментом отчёта (на фейковых данных).
3. **Задача:** какую проблему решает (2–4 предложения): позиция закрылась, причин много (auto-close по спреду, ручное закрытие, ликвидация и хедж второй ноги, защита от голой ноги, ADL), разбирать руками долго.
4. **Архитектура:** схема (GitHub рендерит Mermaid-диаграммы в markdown) и пояснение: агент → слой политики → MCP-сервер → снимок SQLite + логи; управление контекстом; проверка доказательств.
5. **Пример разбора:** полный отчёт по одному фейковому случаю: таймлайн, причина, доказательства, пробелы.
6. **Evals:** таблица из AIL-42 (open/blind, success, pass^k, шаги, токены, $ на случай, время), на каком наборе, сколько прогонов, модель, дата. Плюс 2–3 строки о типичных провалах и что исправлено.
7. **Безопасность (отдельный раздел, не мелким шрифтом):**
   - только чтение: SQLite открыт в `mode=ro` + `query_only`, тест доказывает, что запись падает;
   - работает только со снимком базы (`VACUUM INTO`), не с живой;
   - нет торговых инструментов и нет сетевых запросов к биржам, ключей бирж в проекте нет;
   - слой политики: whitelist read-only инструментов, отказ по умолчанию, human-in-the-loop для всего прочего;
   - встроенные инструменты фреймворка выключены (если используется SDK);
   - prompt injection: логи считаются недоверенным вводом; результаты твоих атак из AIL-64 и lethal trifecta — каких ног нет;
   - честные ограничения: что не проверено.
8. **Быстрый старт:** 3–5 команд от клона до отчёта на фейковых данных.
9. **Как это устроено / решения:** почему агент, а не workflow; почему свой цикл или выбранный фреймворк; что бы сделал дальше.
10. **Лицензия.**

### Проверка перед push

Самая неприятная ошибка — реальные данные в **истории** git, даже если в последнем коммите их нет.

- Начни публичный репозиторий **с чистой истории**: новый репозиторий, куда переносятся только нужные файлы, а не рабочая папка со всеми коммитами экспериментов.
- Проверь, что в индекс не попало лишнее: `git status --ignored`, `git ls-files` — нет `*.db`, `*.log`, `.env`, `runs/`.
- Поиск по всей истории: `git log -p --all | grep -iE "api[_-]?key|secret|token|arbitrage\.db"` и по своим реальным символам и ID форм.
- Сканеры секретов (например, gitleaks) полезны, но это сторонняя программа: по твоему правилу — проверить источник, версию и подпись перед установкой.
- Прочитай README глазами незнакомца: всё ли понятно без контекста твоего приложения.
- Push делаешь ты сам, после финальной проверки.

## DeepSeek и Ollama: как это сделать у нас

Публичная часть проекта целиком на фейковых данных, поэтому здесь провайдер — вопрос удобства читателя и честности README, а не приватности. Что меняется (проверено по документации 13 ноября 2026):

- **Быстрый старт без ключа.** Дефолт демо — локальная Ollama: читатель клонирует репозиторий, делает `ollama pull qwen3:4b` и запускает агента, не регистрируясь нигде. DeepSeek (и, для сравнения, Claude/OpenAI) — опция через `LLM_PROVIDER`.
- **`.env.example`** — только имена: `LLM_PROVIDER=`, `LLM_MODEL=`, `DEEPSEEK_API_KEY=` (и `ANTHROPIC_API_KEY=` / `OPENAI_API_KEY=`, если оставил варианты для сравнения).
- **Раздел «Models & privacy» в README.** Коротко: на реальных данных агент работал только с локальной моделью (Ollama, `OLLAMA_NO_CLOUD=1`), облачные модели видели только фейковые данные; почему (данные о сделках не покидают машину; DeepSeek обрабатывает запросы на серверах в Китае). Это убедительнее любой фразы «secure by design».
- **Таблица evals** с колонками «Модель», «Провайдер», «Набор» (fake), «Дата», «Цены на дату» для DeepSeek. Модель Ollama указывай с тегом (`qwen3:4b`) — веса под тегом со временем обновляются.
- **Требования к железу** в Quick start: «`qwen3:4b` ≈ 2.5 ГБ, работает на Mac с 8 ГБ; окно 16k (`OLLAMA_CONTEXT_LENGTH=16384`)» — читатель с таким же ноутбуком должен знать, что демо у него пойдёт.
- **Ссылки на установку** — только официальные: ollama.com и docs.ollama.com; в README можно напомнить про проверку подписи приложения (`codesign -dv`, `spctl -a -vv`).

Пример фрагмента Quick start с Ollama:

````markdown
## Quick start (fake data, local model, no API key)

```bash
ollama pull qwen3:4b              # ~2.5 GB, from ollama.com
uv sync
python scripts/make_fake_data.py --seed 42
LLM_PROVIDER=ollama python -m agent.run FAKE01 3
```
````

## На что обратить внимание

- **Реальные данные в фейке.** «Почти фейковые» логи с реальными ID ордеров или временем сделок — это утечка.
- **История git** хранит удалённые файлы. Чистая история надёжнее, чем чистка.
- **`.env.example` с настоящим ключом** — классика. Только имена переменных.
- **Скриншоты** приложения: на них балансы, пары, позиции. Не публикуй.
- **Цифры без контекста.** «90% accuracy» без размера набора, числа прогонов и модели ничего не значит и вызывает недоверие.
- **Нерабочий быстрый старт.** Проверь его на чистой машине или в новом виртуальном окружении: склонировал → 4 команды → отчёт.
- **Закреплённые версии** зависимостей в `pyproject.toml`/lock-файле: через полгода `pip install` без версий сломает демо.
- **README о безопасности должен быть правдивым.** Не пиши «полностью защищён от prompt injection» — пиши, какие ноги треноги отсутствуют и что проверено.

## Ответы

1. Задача, архитектура, пример разбора, цифры evals, меры безопасности (плюс быстрый старт и ограничения).
2. Удалённые файлы остаются в истории; чистка истории сложна и легко пропустить что-то. Новый репозиторий с переносом только нужных файлов надёжнее.
3. Реальный (или похожий на реальный) ключ — должны быть только имена переменных; и путь указывает на живую торговую базу вместо демо-данных/снимка.
4. При замене цифр легко оставить реальные ID ордеров, время сделок, символы и другие идентифицирующие детали; генерация с нуля гарантирует отсутствие реальных данных.
5. Воспроизводимость: читатель получает те же данные и тот же отчёт, что в README.
6. Размер набора, на каком наборе (фейковый/реальный), число прогонов на случай, модель и дату, режим (open/blind), было ли кэширование.
7. b.
8. Ожидаемая причина каждого случая известна по построению, получается публичный golden set без реальных данных.
9. `git ls-files` и `git status --ignored`, поиск по `git log -p --all` по расширениям `.db`/`.log`, ключевым словам и реальным идентификаторам; при желании сканер секретов.
10. Без них через время новые версии SDK сломают API, и быстрый старт перестанет работать.
11. Читатель запускает демо без регистрации и ключа, бесплатно и офлайн; к тому же это тот же путь, что и для реальных данных, — README показывает рабочую конфигурацию, а не облегчённую.
12. Правду и конкретно: реальные данные обрабатывала только локальная модель (Ollama, облако выключено), облачные модели (DeepSeek, по желанию Claude/OpenAI) видели только фейковые данные; цифры evals в README — на фейковом наборе с указанием модели, провайдера и даты.
